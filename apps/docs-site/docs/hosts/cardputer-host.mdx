## B1 测试候选

Cardputer Host `1.0.0` is included in Product Build `1.0.56.0` as a team-test
candidate. Product Assembly supplies the ESP32-S3/Cardputer ADV pin profile,
runtime limits, and Assembly identity; the Host does not choose those values.

The current source uses ES8311 DAC unity gain (`0x32 = 0xBF`, 0 dB).
User volume remains software-controlled (default 2/10), with a one-block gain
ramp and explicit mute/stop silence. Codec `0x40` is −63.5 dB, not 25% volume;
that prior configuration could report Running while being effectively inaudible.
This source correction does not amend the frozen test snapshot or establish
physical acceptance. A fresh immutable candidate is required for final A1 testing.

Playback startup keeps the DAC powered down (`0x12 = 0x02`) while I2S clocks
start and silent DMA prewarm drains. The hardware-unmute transition then powers
the DAC up before restoring codec gain and clearing mute. This avoids enabling
the BCLK-derived DAC before its clock is established; no additional startup
delay or permanent mute is used. Register-order tests do not prove analogue
silence: short listening checks on the source candidate are separate from the
fresh immutable Build and sustained A1 acceptance still required.

Build with the pinned EIM-managed ESP-IDF environment:

```bash
scripts/cardputer-host.sh configure
scripts/cardputer-host.sh build
```

The Host now exposes the bounded `lmdj.cardputer-transfer.v1` receiver over
the ESP32-S3 USB Serial/JTAG endpoint and hands only committed, identity-
verified content to the Runtime Host. This candidate has no public Release,
deployment, Channel promotion, or physical A1 acceptance; a real computer
producer must exercise the complete transfer sequence, while combined-load
measurements and the complete A1 journey remain required.

## Audio service diagnostics

Current development source records separate microsecond distributions for DMA
wait, delivered-EOF wakeup, Core render, PCM conversion, driver submission and
combined service elapsed time. Counters include failed/partially executed
attempts. The control owner can read a snapshot only after the audio task has
finished; there is no live mutable snapshot or audio-thread logging. Read-only
USB extraction is not yet wired.

Each distribution reports its count, maximum and exact nearest-rank p99.9 while
the count is below 512000 and all observations are representable. After that
limit, or a bad clock observation, the percentile is explicitly unavailable;
count and maximum are not silently reset. The six fixed retained tails add
12288 payload bytes plus metadata to the Host's resource cost. They do not use
the platform reserve as an unreported budget.

Service elapsed excludes DMA wait, includes preemption and timer-call costs,
and is not an isolated task-CPU measurement. Accumulator overhead is reported
separately as a count and maximum; its surrounding clock calls and final
counter update are outside that observation. Startup prewarm and final drain
are not steady-service samples. Delivered callbacks cannot establish physical
DMA timing during masked/delayed interrupts, so these diagnostics alone cannot
prove zero underruns, the 30-minute combined-load target or physical latency.

## Resource observations

Development source also provides a control-owner sampler for internal 8-bit,
DMA 8-bit and external 8-bit heaps. It retains free bytes, largest free block
and the SDK's sum of per-region low watermarks. These capability sets overlap;
do not sum them. Queries are sequential, not an atomic system snapshot, and
begin/end timestamps include their collection interval. The sampler also reads
the calling control task's stack high water in bytes, without word scaling.
It must not run in the audio render callback or an ISR.

The audio worker separately records its own stack high water after driver
cleanup and before publishing completion. The control owner can read it only
after that completion barrier. It is unavailable before a worker completes or
if task creation failed; an observed zero remains a valid value. A new start
clears the old result. The measurement excludes later task deletion code, and
completion does not prove that FreeRTOS's idle task has reclaimed its memory.
Neither sampler supplies a per-cycle heap minimum or a reclamation verdict.
Identity-bound extraction and actual load/play/stop/unload/reload resource
measurements remain pending; these APIs do not establish device acceptance.
