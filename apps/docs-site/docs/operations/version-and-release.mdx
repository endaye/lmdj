## 四条版本轴
Product Build 使用四段式；Core Module、Host 与 Provider 使用独立 SemVer；Contract 使用稳定 ID + Contract SemVer。

## Host changelogs

[Creator 独立日志](./creator-changelog.mdx) 与
[Web Runtime / Lab 独立日志](./runtime-changelog.mdx) 从各 Host manifest 和结构化
`CHANGELOG.md` 生成。没有日志时显示暂无记录，不补写历史版本。条目只说明 prepared，
不说明已经测试通过、部署、发布或晋级；认证回执展示仍待接入。

版本准备 PR 修改 Host 输入后，在 `apps/docs-site` 运行 `npm run changelogs`，
将静态页面一起提交，再按 Product 分配规则冻结快照。构建仅检查投影是否一致，
不会自动改写源码或历史快照。此展示功能不启动版本准备、部署或发布。

## 手动 canary 版本评估入口

`Canary Assessment`（`.github/workflows/canary-assessment.yml`）提供独立的手动
评估路径，不按日期运行，也不阻塞 PR 合入或主干自测。它只产生 Host 版本与
changelog 建议及失败报告，**不分配 Product Build、不创建版本 PR、不发布、不部署**。
自动的结果驱动调度、版本进度和后续交付仍是单独的实施与验收任务。

新评估默认禁用。启用 `CANARY_ASSESSMENT_EXECUTION_READY=true` 前，运营方必须验收
专用 disposable VM/microVM、受保护的 `canary-assessment` Environment，以及
`tools/canary/executor_policy.json` 中固定 SHA-256 的 root-owned 原生工具。
执行器使用 `lmdj-ai-isolated` 标签，不能同时承担普通 CI/pool 或部署任务；标签、
私有目录、单独用户或 readiness 变量本身都不是隔离证据。工作流不安装工具，
不读取机器上的登录态，只使用显式配置的 GLM/Kimi coding key 与 Grok coding auth。
工具缺失或校验失败不会运行 PATH 中的替代程序。GLM → Kimi → Grok 全部失败时保留
blocked 结果，由后续报告步骤提 Issue，不在 CI 内修复。

所有操作只能从 `main` 发起新的第一次运行。每次 dispatch 都必须提供完整 `storage`
JSON：顶层恰好是 `assessment`、`outbox`；两项各包含 `repository`、`issue_number`、
`issue_node_id`、`bot_node_id`、`workflow_id`、`epoch`。ID 必须从实际 GitHub API
读取；两项使用相同仓库、工作流及 Bot 身份，但 Issue number/node ID 不同。
epoch 分别以 `canary-assessment-inputs-`、`canary-assessment-outbox-` 开头。
不能复用现有 scheduler、report 或 review journal，也不会自动新建或初始化存储。

- `init-assessment` / `init-outbox`：一次只初始化一个已明确预留的独立 Issue，
  `request` 为 `{}`；Issue 必须没有评论，正文精确为
  `<!-- lmdj-ci-journal-uninitialized-v1 -->` 加一个换行。不是清空或重置命令。
- `claim`：`request` 为 `{"base_sha":"<完整 SHA>","target_sha":"<完整 SHA>"}`。
  检查完整 main 历史后，先持久领取并保留完整输入 artifact，再释放短写锁执行 AI。
  `base_sha` 是明确选择的版本评估起点，不会自动采用主干测试进度。单次输入超限会
  拒绝，不截断或假装全覆盖；后续协调器仍需实现大区间的完整覆盖方案。
- 原运行终止后，在**新 dispatch** 中使用 `settle`，`request` 为
  `{"input_digest":"<原控制器摘要中的完整 digest>"}`。它校验原 run/attempt/control、
  producer job、上传步骤和完整结果，再持久记录；不会重新调用模型。
- `report` 使用同一个 digest 和 storage，先 reconcile 原结果，再通过独立 durable
  outbox 提 Issue 或恢复已有回执。未知 POST 不能盲目重发；不自动修复、关闭 Issue。
  已持久结果不依赖 artifact 继续存活。原结果缺失、损坏或过期则报告待核对义务，
  不能重置领取、用新 control 重新 claim 来冒充恢复。

恢复与报告不受新任务 readiness 开关影响。原执行中的结果保持 pending；原终止运行
没有成功上传时保留领取并要求核对。有效 blocked 结果先成功上传，由独立可见性 job
标红，这不代表结果遗失。Artifact 保留 30 天，应及时 settle/report；本手动入口
尚不自动接收完成回调或排空报告积压。源码和本地夹具测试不代表上述远端前置条件已验收。

## Release cut

Product Build 从 `main` 切出，不在分支上组装。功能、Host、Provider、deploy workflow 与发布脚本先各自经普通 PR 当前 head 评审合入 `main`；control-plane 按可评审性和真实依赖拆分，不再要求 Integration Queue。切版 PR 只携带分配材料：`version.json` Build 分配、必要时的 `assembly.json` 与 `assembly.lock.json`、该 Build 的 immutable Portal snapshot 与 release-evidence 文档，经评审后 squash 合入。squash 产生的精确 `main` SHA 就是该 Build 唯一合法的 release target；之后的 `main` 提交不进入该 Build。发布后的修复走 PATCH：从已发布 tag 拉短命 `fix/<task>`，分配下一 PATCH，同一修复经普通 PR 回 `main`；仓库不设 `release/*` 或 `hotfix/*` 长期分支。规则全文见 `docs/governance/git-workflow.md` §6。

## Channel promotion

晋级只改发布记录，不改 GitHub Release。ledger 里 Product intent 的 `channel` 固定为发布时的 Channel，发布后不可变并继续决定 `prerelease` 与 `latest`；晋级写入可选的 `promotions` 列表，每条记录目标 Channel、UTC 时间、证据路径、各 Host 部署 run 与其 `evidence.json` 的 SHA-256。当前 Channel 等于最后一条记录。晋级严格向前、一次一档、不超过 policy 的 `promotion.max_channel`（M1 为 `dev`）。`dev` 的门禁是可判定的：intent 已发布、full exact-main CI 成立、profile 的每个部署 Host 各有一次成功的 `workflow_dispatch` 部署 run 且其保留证据记录同一 tag、target revision、Product Build 并全部 `passed`。`beta` 另需人工验收文档。`stable` 被工具拒绝，因为 D8 禁止切换已发布 Release 的 `prerelease`；这是开放问题。入口是 `scripts/release.sh promote TAG CHANNEL --deployment-run HOST=RUN_ID ...`，只向工作区写一份证据文档和一条 ledger 记录，再作为 docs PR 经当前 head 评审 squash 合入。规则全文见 `docs/governance/version-management.md` §3.1。

## Product Build 权威与诊断

`products/lmdj/version.json` 是当前 Product Build 的唯一源码权威。CMake、Runtime identity、
Portal facts 与 current-repository tests 都从它派生；`assembly.json` 的 Product Build 仍是经过
review 的 exact Assembly 声明，release intent、build-specific current prose 与 immutable
snapshot 也继续保存各自的精确事实，不能由 mutable HEAD 自动重写。

版本、Assembly、compiled assembly、lock 或 generated Runtime identity 漂移时，最早可判定的
gate 会报告 authority、expected、found 与 consumer path；生成物 stale 还会给出稳定的
`scripts/version.py lock` 或 `tools/web-runtime/generate_runtime_identity.py` remedy。修复命令只
恢复派生物，不会自动修改 reviewed Assembly、release intent、snapshot 或分配新 Product Build。

## Git 与发布
Task commit、push、PR、squash merge、signed product tag、Release、部署和 Channel promotion
分别保留证据。Task 请求覆盖正常交付；一次整体发版请求覆盖其发布序列，不重复逐段询问。
每段验证通过才继续；门禁失败、外部认证 / 必需审批、范围缺失或显式限制仍须停止。

编排默认配置已定义为 `web-hosts-dev`：canary publication、Runtime / Creator 两个 Host、
验证后晋级 dev，以及 GitHub Release / doc-site 两份同源 changelog。配置解析拒绝未知范围、
缺少任一 Host / changelog 目标、越权 Channel 与无界重试。它目前只是经过校验的默认范围，
不是发布授权，也不表示 run / resume 总控、非交互签名或双端 changelog 发布已经实现。

三个发布／部署 workflow 已提供可选的 `request_id`（固定 operation 的 64 位小写十六进制摘要）。
携带它时，preflight 在现有门禁前生成并上传 `release-dispatch-correlation`，记录 exact inputs、
repository / actor / run numeric ID、首次 attempt，以及 event / workflow / tooling revision。
它只证明请求被该运行接收，不证明签名、发布、部署或授权；缺省时保留原有手动路径。
关联回执生成或上传失败会停止该 preflight，不进入后续发布／部署。消费端仍须认证实际
API run、留存 artifact 及可信源码；未知 POST 不得凭回执文件、run-name 或最新成功盲目重发。
回执生产端及 exact-run 只读认证消费者已实现：消费者核对真实 API run / actor / workflow、
完整 jobs / artifacts、成功的回执上传步骤、ZIP digest 与冻结输入，并回读运行身份。
它还核验受信 producer、workflow 与 tooling 在受保护 main 上的源码祖先关系。
发布失败或仍在执行的运行也可能拥有真实关联回执，因此返回关联信息不表示发布成功。
只读 discovery 已提供完整分页运行查找：以原 operation journal 在唯一 POST 前保存的
完整 run-ID 清单排除旧运行，再读取新运行的认证输入。不能用事后扫描补造这个基线。
跨 control revision 的重复 operation 同样报 conflict；候选不可读、零匹配或清单变化报
unknown，只有单一认证匹配返回 correlated。任何结果都不允许重发，也不表示发布成功。
内部 durable POST 控制器已接通：新 operation 私有目录保存固定 scope；首次 POST 前将
完整 run-ID 基线与写意图原子落盘。已有意图只允许读取认证回执，不因超时、重启或
缺失结果重发。原授权失效、writer 被替换、状态损坏或丢失会阻断写入；已有目录不会被
重新初始化为“未发送”。POST 前还核对 numeric actor / repository / workflow 和 main SHA。
原授权每次都需复核，首次发送的 readiness 条件只在写入前检查；恢复不能要求已公开的
Release 重新变成 Draft，也不能因此重发。
父级 driver 的重复请求准入会在原 journal writer lock 下查找同仓库的未完成请求。
新 transport ID 若仍属于同 actor、policy、control revision、mode 和 exact tag，
会恢复原请求；新的 main 观察值与授权引用不覆盖旧基线或旧授权。新请求和原授权均须
重新认证，返回的是原 request ID，不创建第二条发布流程。新 ID 会以私有、不可重绑的
alias 记录绑定完整输入与原 request ID / digest，在继续执行前原子落盘并 fsync。
原流程完成后，同一 ID 的重投或 resume 仍解析到原流程，不再次分配版本。alias 恢复
再次认证两份原始授权；缺失目标、损坏关联、同 ID 同时为 alias 和原记录均拒绝。
alias 不允许链式引用，也不能用 create 转为新发版。相同 ID 的所有字段仍须完全
一致；不同范围、多条未完成记录、损坏或读取中变化的清单均拒绝。已完成历史不阻止新发版，
但既有请求的未知写意图仍只核对结果，不再次执行。此能力只在同一受信 journal 目录内生效，
不替代生产入口认证、原请求 adapter 构造、跨目录去重或全局 Site 互斥。
候选输入检查已能从 exact Git commit 冻结完整 path / mode / object 清单及 Product
manifest 身份。它复用受信版本解析器与禁止 fetch、replace refs、grafts 的 Git 读取，
不执行候选脚本，不读取本地脏文件作为版本真相。重新计算原基线，再要求新 main 是其
后代且冻结清单一致；源码变化即使没有更新 Assembly lock 也会拒绝。缺对象、浅克隆、
歧义路径或伪造的冻结记录均不当作有效输入证明。
仅明确的文档路径可前进：`docs/` 中除 governance/release-evidence/quality 之外的文件，以及
current docs-site 的 docs、diagrams、static/diagrams。版本快照、构建/测试/控制工具、
治理、正式质量证据与发布分配记录、未知新增路径仍属于候选输入。软链接直接引用的
仓库内文件或目录也纳入冻结，即使原本属于文档排除范围；拒绝绝对/越界/悬空链接、
链式或中间路径链接，以及目标目录内的链接和 Gitlink，不读取工作区链接目标。

受控工作区和 writer lock，不能将本地生成当作完整发布验收。

## 标准 Release 控制面

源码 Product Build 与匹配的 immutable snapshot 可以先完成分配，此时允许没有 release intent；
零 intent 不授予任何 release 权限。Release intent 是独立 reviewed authorization，必须等该 Task
经 protected `main` squash merge、精确 squash SHA 已存在后才能绑定；branch-only 或 pre-squash SHA
无效。当前 Product Build 只允许零或一个 intent，重复 intent 会被拒绝；一旦 intent 存在，原有的
exact-target、merged-main Proof、完整 CI 与 protected-main ancestry 门禁仍全部适用。

仓库已实现四段正常路径：`scripts/release.sh prepare TAG` 只准备并验证本地状态，
`scripts/release.sh push-tag TAG` 只 push/reconcile 一个 exact tag，
`scripts/release.sh create-draft TAG` 只创建或补全一个 Draft，最后由 dispatch-only
`publish-release.yml` 发布同一个已验证 Draft。整体发版授权覆盖各段；发布 job 在 publication 后以
`scripts/release.sh verify-published TAG RELEASE_ID PLAN_SHA256` 按 numeric Release ID 读取并验证 live
Release，其他 mutation 后重新运行 `scripts/release.sh audit --remote --tag TAG`，通过后继续已授权的下一段。Audit 从 policy、release intent ledger 与 live
Git/GitHub 重建真相；historical exception 只能由 audit 显式报告，不能满足新的 prospective gate。

单入口顺序总控的命令面已交付：`scripts/release.sh run --authority REF` 从已认证的 canonical control 冻结一份
release request 并交给唯一的顺序 driver，`scripts/release.sh status [REQUEST_ID]` 只读取本地 request
journal 的进度记录，`scripts/release.sh resume REQUEST_ID` 用同一 ID 继续同一请求。journal 在
`<git-dir>/lmdj-release-requests` 下独占写入：intent 在任何外部写之前落盘，未解决的 intent 不允许
重放，恢复时逐步重新验证 far side，本地记录不被当作外部证明。请求、actor 身份、pinned control
revision 与 orchestration policy digest 一并冻结，`--base-revision` 与 control 一样必须在 canonical
main 历史内可到达，重复运行同一 scope 幂等。`status` 只读该本地记录：它不联系网络、不重建材料、
不授予任何权限，其可见范围就是该目录当前账号权限（0700/0600，无凭据）。

各步仍由该步自己的 far-side 验证器确认；尚未接入某一步 carrier 时，`run`/`resume` 在创建请求前
拒绝启动并逐项列出缺失步骤，不用 fixture、空结果或 completed 标记代替真实验收。

当前 `complete-test-v2` 要求 Owner 在 reviewed intent 中恰好引用一种来源：旧
`self-test-v1` 的 `self_test_evidence`，或增量 full 批次的 `batch_test_evidence`。
两者都必须是 exact target 的完整 16-suite passed verdict，包括 TSan 与 Release stress。旧 14-lane
`full` scope 不能再授权 prospective 发布。自测不阻碍 PR merge；正式版本仍由人手动发布。
现成同 SHA 的完整通过结论（包括有效历史日测或 node 证据）可复用，不要求重复补测。

证据同时绑定稳定 workflow ID / path、canonical repository、control 与 target 各自的 main
历史、run / attempt、全部 required 结果、适用 policy 和摘要；动态展示名不是 authority。
`run.head_sha` 是可信 control，可与 candidate target 不同。闭合 `self_test_evidence`
reference 由已验证事实写入独立 reviewed intent，并纳入 release plan digest，不自动授予发布。
新的内部发布元数据 `release plan marker v2`（不是产品 Contract）永久保留完整 CI reference，fresh remote audit 逐项比对；
给旧 v1 发布记录补填 intent 字段不会使它获得新自测资格。

增量来源还独立认证原 origin/admission controller artifacts 的 durable-claim attestation
（不是重放最新 journal），以及 verdict/execution/needs 三文件与真实 API jobs；current、
frozen control、actual executor 的 policy 必须一致。focused/none、债务、未知来源、过期
或跨 SHA 拼接不能作为候选证据。完整 batch reference 与真实 `executor_event` 永久写入
内部发布元数据 `release plan marker v3`（不是产品 Contract）；不能从 request kind 推断 event，也不能用 v1/v2 marker
证明新增 batch 引用。旧 markers 与 intent 不迁移、不自动补填。

Verdict artifact 保留 30 天。缺失、过期、错误 SHA、失败、skip 或混合 attempt 一律不能
通过候选验证。恢复须另行授权在 ref `main` 上 dispatch `self-test-report.yml`，选择
`batch_operation=reconcile`，输入闭合
`batch_request={"id":"<new-stable-request-id>","kind":"candidate","target":"<exact-main-SHA>"}`，
`journal_config` 留空使用可信源码固定调度器，再独立更新 intent。
显式诊断改用 `kind=node`，同样强制完整 16-suite。两种请求共享重型预算，固定目标
不会被持续合入替换，也不推进自动 processed。重送同 ID 同目标恢复原请求；真正重测
需要新 ID。不使用 SHA 作为 ref，不 Re-run jobs（当前只允许 attempt 1）。
旧 `ci.yml` 手动／每日 producer 退役以新 producer + consumer 真实演练为前置条件，
不能以本地测试冒充；历史来源 reader 保留。
已 published 的新旧协议均保留只读历史，继续核验不可变 tag、签名、Release、asset 与
plan marker；artifact 到期不改写历史。完整字段与切换规则见版本治理。
新协议 published 审计读取 recorded attempt；后续 rerun 不会覆盖历史，但新候选仍检查 latest。
仅实际 `Disposition.PUBLISHED` 可使用增量历史 provenance 路径；仍须 tag、signer、Release、
assets 与 v3 marker 全部通过，不把 allocated/abandoned/superseded 当作已发布。
消费者支持不是一次真实全量通过证明。手动精确 full 能力保留在统一增量控制器入口，
每日产品测试和每日缺测告警则退役；轻量健康巡检不按日期生成产品请求。

签名发生在可信本地边界；GitHub workflow 只持有 public trust anchors。公开 publication 必须由
精确输入的 workflow dispatch 显式授权，并通过受保护的 `release` Environment。当前单人维护者
模式要求零 required reviewer、不启用 prevent-self-review，并且只允许 exact `main` branch
policy。Publish 以一次 PATCH 设置 Draft、
prerelease 与 make-latest policy，前后重新验证 exact tag、numeric Release ID、plan digest 和闭合
资产；这是并发漂移检测，不宣称 API 提供强条件更新。Runtime deployment 是另一个 manual-only
exact-tag dispatch，之后的 Channel promotion 仍需独立证据；整体授权覆盖这些步骤。仓库中已有 release/deploy
tooling 不表示当前 Product Build 已经 released、deployed 或 promoted。

## PATCH、Assembly 与证据链

PATCH may not change Product Assembly identity or `assembly.lock`. Any module/provider/Host/dependency identity change allocates a new BUILD. Historical `1.0.16.x` events remain historical facts and are not rewritten；它们用于解释为什么规则被收紧，不构成再次偏离的先例。New Product tags require merged-main Proof first，且该 Proof 必须绑定未来 tag target 的精确 `main` revision、Product Build 与 lock hash。

权威链必须逐环核验并分别记录：Product Build -> signed tag -> tag revision -> merged PR -> source revision -> snapshot provenance/witness -> merged-main Proof revision -> evidence-only documentation revision。branch-local Proof、快照、CI、tag 或后写的证据文档都不能替代链中其他一环。
## 不可变性
已发布 tag 不移动；交付测试或正式发布的文档快照按 Product Build 冻结，current 文档持续跟随 main。普通 PR Preview 不创建永久快照。
schema-2 快照冻结 41 页源码、sidebar、十张图的 20 个 HTML/SVG 资产、源提交与 source projection；后续 current 或 diagram 变化不能改写已冻结版本。生成前允许的脏路径仅限该 Product Build 的精确生成边界，提交后还必须验证 introducing commit、时间顺序以及 direct-parent 或获准的 squash-equivalent projection。

## Runtime Host 公共发布

Runtime Host 的两阶段发布工具和 workflow 定义已经存在：不持有 Netlify credential 的
