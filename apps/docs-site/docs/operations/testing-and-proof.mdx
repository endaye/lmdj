## 测试层级
unit/component 验证局部边界，integration/e2e 验证组合，stress 验证锁自由/并发，Proof 验证 Headless Core 交付链。
## 稳定命令
`scripts/core.sh test dev full` 运行除 stress 外的完整层级；stress 必须显式运行；`scripts/core.sh proof` 也不包含 stress。

## Version identity fixtures

验证 active repository 的测试从 `products/lmdj/version.json`、Assembly 或 generated Runtime
identity 派生当前 Product Build，并用独立 mismatch fixture 证明 consumer 不能漂移。只验证
透传、报告、状态机或错误处理的 pure behavior tests 使用命名 synthetic Product Build；它不
代表已分配或候选身份，下一次 allocation 不修改这类 fixture。历史测试与 reviewed exact
release/snapshot 记录继续保留原版本语义。

Creator Host/package conformance 以 `apps/creator-web/module.json` 为 Host SemVer 与 npm name
权威，并要求 `package.json`、`package-lock.json` 顶层及 `packages[""]` 的 version/name 全部
一致；expected npm name 由 module ID 派生。每个 drift 直接报告 expected、found、authority 与
consumer，不依赖 `npm install` 副作用，也不会自动改写 lockfile。Product Build 与 Creator
Host SemVer 是不同版本轴。

## Release 验证边界

发布保持人工选择、手动操作。获授权的候选可以复用受信完整自测（包括有效历史证据），但必须由发布
验证器证明同一 exact main-history target、可信控制修订、完整固定 suite 集合、
精确 run/attempt、全部必需结果与未过期的 artifact；测试绿色不自动选候选或发布。
具体协议、兼容旧证据和拒绝条件以 [版本与发布](/operations/version-and-release/) 为准，
不能由 PR merge、局部测试或缓存推断。缺失/过期的证据必须通过新的获授权请求补齐，
不把旧 run 的部分重跑拼成完整通过。已发布历史仍按不可变 tag/Release/assets 审计。
当前 `complete-test-v2` 恰好接受旧完整 16-suite self-test 或新 full passed 16-suite
增量批次；focused/none、AI 标签、缺少 suite 或带债务的 batch 都不能授予候选资格。
增量来源还验证原 controller admission attestation、完整三文件重算、真实 API jobs 与
current policy。整个 reference 和实际 executor event 绑定永久 v3 marker；这不改变
自动触发、不自动选择版本，也不等于已经取得真实平台 full-passed 候选证据。

发布控制面的自动化覆盖四段：`scripts/release.sh prepare TAG`、
`scripts/release.sh push-tag TAG`、`scripts/release.sh create-draft TAG` 与 dispatch-only
`publish-release.yml`。每段只证明自己的 postcondition；Draft verification、publication 和后续
deployment 不能由前一段推断。每个 mutation 前后都以
`scripts/release.sh audit --remote --tag TAG` 读取 live state；audit 报告中的 historical exception
只是显式旧事实，不是当前 gate PASS。

Publication job 在显式 dispatch 进入 exact-main-only `release` Environment 后，仍须重新验证
exact Draft；当前单人维护者模式没有 required reviewer，人工授权边界就是这次独立 dispatch。
workflow 成功也不自动触发 Runtime deployment。Runtime deployment 保持 manual-only exact-tag
dispatch，部署 evidence 与 Channel promotion 再分别验证。测试、workflow 或工具已进入仓库，
都不表示当前 Product Build `1.0.46.0` 已经 released、deployed 或 promoted。

## PR review 与乐观合并

本页 CI 切换说明仅在明确授权的 O2 窗口、T5a 和保护规则切换后生效；未合入草案不替代
当前 main 规则。main 是允许暂时有缺陷的集成分支，可发布性属于明确选择并完整验证的
候选。PR 仍需要授权、Task 范围测试、真实冲突处理、当前 head 的 review 与必要对话。
没有冲突时不因 main 前进而 update，不排 Integration Queue，不等产品全量测试绿色。

AI review 是反馈，不是机器正确性门禁。缺凭据、超时、失败、格式损坏或旧 head 结果
不能当作 clean。人工/agent 接管须实际检查当前 diff，并记录 reviewer、head、原因、
findings 处置和未覆盖范围；处理 thread 不等于未经检查自动清空。新 push 后要审查新 head。
`main` 保留 `required_conversation_resolution`，未解决的 findings 仍须有实际处置；
这不是模型对 merge 的自动裁决，clean review 不应产生阻塞用的 inline thread。
实际 merge SHA、review 证据和动作授权分别核验；空 check 列表和 NEUTRAL 不是通过。

`pr-review.yml` 按 GLM → Kimi → Grok 有界回退；获得一次有效 findings 与范围结果即停止，
发现代码问题不触发换模型。三者均不可用时保留真实失败并通过 outbox 报告 Issue，
不能伪造 clean。模型只读取可信控制代码与作为数据的 PR diff，不 checkout 或执行
PR head，也没有 PR 写权限。短 publisher
校验结构化结果及当前 head，用固定 `commit_id` 发布 COMMENT review；模型不生成
合并授权。可信发布器绑定 repository、PR、head、run、attempt 和 backend，liveness
核对同一身份的模型、publisher 与 bot review。发布过程中 head 移动会留下旧 commit
的历史反馈并报告失败，不能冒充新 head 已审查。clean 结果不创建 inline thread；
真实缺凭据、API/模型故障及人工 resolve 的远端验收仍分别记录，不从本地测试推导。
若线上仍要求旧 required contexts 或 strict，报告切换未完成，不借普通 shipping 权限绕过。

## 主干增量批次与手动全量

main push 唤醒 `self-test-report.yml` 的轻量控制器。同一时间最多一个自动批次；
新合入只更新 pending，不取消当前固定目标。下一轮汇总 processed 到最新 main 的
全部 first-parent 提交与有效审查记录，不只读取两端净 diff。确定性旧／新策略下限与
head／policy 绑定的 AI 建议取并集，标签仅展示；合入后不再调用 AI。

合规无消费者说明文档可为 none；局部改动执行相关 Host／模块及行为和依赖测试；
底层、广泛或无法可靠分类的改动为 full。完整集合仍含全部 16 suites，包括 sanitizer
和两组 stress。独立 suite 在其他 suite 失败后继续收集结果，构建阻断如实记录。
共享重型锁继续保护真实资源容量；短控制器锁不得跨重型执行持有。
processed 只是处理进度：none／focused 成功不能清除历史失败或未覆盖债务。

自动 push／完成回调／健康检查只是一条“重新观察持久状态”的通知，不是独立测试命令。
它们在 workflow 层共用 `self-test-report-wakeup-automatic`，保留当前运行和最新一个
pending；后续通知只替换尚未运行的通知，不取消正在执行的控制器或产品测试。
每次手动 dispatch 用独立 run ID 构成入口组，因此不会与自动通知或其他手动命令互相替换。
所有实际写入仍经过 job 层的 `self-test-report` 短锁，保留 `queue: max` 及平台队列上限；
入口合并组不是写锁，不能阻止手动 settle／report 在重型执行期间获取短锁。
自动报告／评审发现通知会等待当前自动 workflow（包括其产品 DAG）结束；这是减少
重复后台读取的取舍，并不承诺长批次期间的自动报告延迟不变，必要时可使用手动报告。
空闲时，已认证批次完成回调独立读取 main；只有 main 与 durable processed 不同才恢复
原调度流程，覆盖完整未处理区间。父运行取消、未取得 claim 不等于 main 没有变化，
也不是测试通过证据。已有其他 active executor 时无关回调不结算、不抢占；
无变化的空闲回调不写 journal、不启动重测试。遗漏通知仍由独立健康检查恢复。
替换 pending 在平台上属于取消，也可能产生既有 completion relay；这些回调同样合并，
但不宣称 relay 工作量归零，远端验收需同时观察回调数量与写锁队列。
切换前已创建的运行按旧配置排空，不因新策略手动取消；本地队列模型不等于远端
突发通知、手动请求保留或完整测试→报告闭环已通过验收。

手动诊断／候选使用同一 workflow 的 `batch_operation=reconcile` 与闭合
`batch_request={"id":"<stable-request-id>","kind":"candidate","target":"<exact-main-SHA>"}`；
诊断改用 `kind=node`，ref 保持 `main`，`journal_config` 留空使用可信固定配置。
两种请求都强制完整 16-suite，目标不随 main 漂移，不推进自动 processed。重送同 ID
恢复原请求；真正重新测试使用新 ID，而不是混合 Re-run jobs 的不同 attempt。

每日产品 cron 与每日未启动告警均已退役。独立轻量健康巡检按 UTC 每小时
7、22、37、52 分运行，用于恢复已有 pending、请求和报告，不能因日期启动产品测试。
完成接续采用只读 `Incremental Completion` 中继，`Self-test Report` 不直接监听自己。
中继 artifact 关联精确父 run／attempt，原控制器重新核验中继与父运行身份，并检查
父运行是否对应 durable active executor 后才结算。若已空闲，则独立确认 main 新变化
后复用原控制器接续；中继不是第二调度器，不写状态或启动测试。
早先直接自订阅被真实 GitHub HTTP 422 拒绝；随后 PR #904 已合入中继修复。
该修订的实际 main push 运行 `34188723712/1` 已启动控制器且控制器成功，证明入口
已运行，不代表产品测试全绿或 O2 通过。跨 workflow 完成接续及链上限后的恢复仍须
真实平台验收，不能用本地测试、控制器成功或 artifact 存在替代。

完成通知链有平台深度上限，巡检提供独立恢复；必须保留真实链到上限→独立巡检
恢复已有尾部→追平→无变化不启动重型任务的完整证据。平台可能投递有界轻量
relay／idle 外壳，但父运行身份本身不能授权新 admission；空闲新 main 的独立核验
才允许原调度器恢复，不能借此结算别人的在途批次，也不承诺
无限即时循环。Actions 延迟或不可用时不能承诺 15 分钟内接续，保留手动恢复入口。
无变化、无待执行请求或显式恢复则不跑重测试。

校验器。目标可以晚于控制修订；两者分别验证属于 main 历史，不要求目标是控制修订的

与兼容 dispatch 尚未选择新自测时不会被误报为缺少 verdict；请求记录已保留却没有

每个 run 单独证明控制修订不早于该 producer 且属于 main 历史。旧控制修订即使新
rerun 也明确跳过，部署后的启动失败仍可见，未知祖先关系不当作 legacy 吞掉。

上文的 durable node／candidate 请求和新 ID，明确选择固定 SHA；不要 rerun 旧执行。

先保存意图和写入 claim，再核验业务 receipt；响应丢失先查证，不盲目重复 POST。

这两个复用字段在该操作中表示 Core CI 来源。`report_config` 留空使用固定 pair。

PR Review 完成不再直接唤醒自测控制器；已发布的 findings 与 scope 仍由审查发布器保存，
main push、原 scheduler health tick 的非执行轮仍可恢复报告，实际批次完成 relay 保持及时通知。
另外，UTC 每小时 `9,24,39,54` 分的 report-only health tick 使用独立的合并等待组，
不再等待长时间运行的产品 workflow 结束；与原 `7,22,37,52` 分的测试恢复巡检分开。
它沿用同一受信任 controller job 和短写锁，只收集已持久记录的失败及 review 观察，
不执行 control、不输出测试请求，也不直接启动产品测试。Python 入口校验两种精确 cron，

这是恢复既有工作的巡检，不是定时全量测试或每日部署。原测试恢复巡检保持不变。
每次 discovery 保留完整历史 metadata 轮扫，另给至多一个新／未解决 attempt 公平机会：
按持久注册或最近 disposition 的 generation 轮转，永久错误和仍运行的 review 也消耗其轮次，
不会独占优先路径。历史成功记录不占这个额外预算；历史重扫仍负责发现旧 run 的 later attempt。
自动发现使用 `--background`：已持久保存、仅剩待扫描窗口／轮次或 pending attempt 时，
日志诊断为 `pending`，步骤成功但完整报告仍为 `incomplete`；保留义务等待接续。
日志只输出有限状态与计数，不输出来源正文。它不证明产品健康、完整覆盖或 Issue 已送达。
手动发现仍严格：任何 incomplete 返回非零，精确 attempt 不允许 background 模式。
这不是 15 分钟投递保证：inventory 缺口、不可读来源、metadata 错误、控制池不可用仍明确报错；
过期 evidence 不冒充成功。精确 `report-review`／`report-discovery` 手动恢复入口保持可用。
旧终态 run 的未知 rerun 仍由与历史 ID 数量相关的完整轮扫发现，不承诺全局 artifact 保留期内送达。
执行轮不做附带报告扫描；非执行轮及独立报告巡检做有界报告和发现，积压留待接续。
`report-drain` 只恢复已入队意图；即使没有 pending，也不能证明 scheduler 中所有失败均已入队。
每次自动收集至多一条新 batch 观察，但完整历史鉴权的 API 工作并非一条请求。
新增巡检每小时四次机会，其完成仍经过现有 relay，须统计完整链路的 API 和 runner 成本。
relay 可以独立恢复真实的新 main 工作；不能把“报告巡检本身不运行测试”解释成整个间接链
永远不会唤醒 scheduler。调度延迟、runner 或来源不可用时不承诺严格 15 分钟送达。
源码回归不替代远端调度和完整积压验收。
控制器、报告、review discovery 和 completion relay 的 Python 入口输出
API observation 脱敏诊断行（不是产品 Contract）：`rest`、`graphql` 是共享客户端真实的
GitHub opener 请求尝试，`artifact` 是不带凭据的下载起始次数，不包含其内部所有重定向。
每完成 100 次 opener 尝试输出累计 checkpoint，正常退出（包括返回错误）输出 final；
按 run/attempt/job/step/process 区分进程，每个进程只取最后一条，不能累加累计 checkpoint。
`responses` 表示 HTTP 连接响应类别，不表示业务 JSON、证据或写入已通过校验；
`transport_errors` 表示 opener 的传输错误，响应体读取或解析错误仍按原入口报错。
`minimum_remaining` 只保留合法数值的 core/GraphQL/search 配额低点；配额重置、共享 token
的其他工作使它不能直接代表本次消耗。未发请求的入口没有计数；强制终止可能只有部分
checkpoint，缺少 final 不能当成零成本。日志不包含 URL、请求正文、凭据或异常原文。
这些数字不包含 Git checkout、其他 Actions、模型 API、存储重定向全链或账单；
结合真实 relay 来源、job 时间及 runner 类型做成本验收，不能据此声称总账单为零。
报告器不合并 PR、不创建版本、不发布或部署。

分配 Product Build 或引入 snapshot 的 Task 在合并后核验实际 introducing SHA 的
provenance。缺失 squash witness 时用官方 `architecture-portal.sh witness` 生成并通过
独立授权的 commit/PR 补交；不可手改冻结数据。只在受影响 Task 承担该条件性责任，
不能把完整门户构建变成所有 PR 的隐形 pre-push 门禁。

## 测试结果驱动的 Canary 规划入口

`Canary Planning`（`canary-planning.yml`）支持 main 首次 attempt 的手动
`workflow_dispatch`，以及默认关闭的 `Self-test Report` 完成唤醒。
它连接真实 scheduler 的只读历史重放与独立规划 journal，
不运行 AI 或产品测试，不分配版本、不创建版本 PR，也不发布、部署或晋升。
后续评估／交付协调和真实环境启用仍未完成；入口源码不代表线上自动流程已验收。

自动入口须经独立验收后显式设置 `CANARY_PLANNING_AUTOMATIC_READY=true`，并提供
`CANARY_PLANNING_STORAGE` 的已审查存储配置。没有开关时不分配 runner；没有配置、
初始化或 bootstrap 时拒绝写入，不创建 Issue 或猜测首次基线。完成事件只是唤醒提示，
入口核对真实来源身份后仍读取完整持久 scheduler 结果，不根据 callback 的绿／红状态
决定部署。重复或漏掉事件由下一次唤醒或手动 `reconcile-next` 恢复；现有报告健康巡检
也提供后续唤醒机会，但多层 `workflow_run` 链不保证每次投递。没有新增每日测试或部署。
自动提示只保留最新待处理唤醒且不取消正在运行的工作；手动命令使用独立准入身份，
不会被自动提示替换。两类入口仍共用 controller 的短写锁，不给产品测试加锁。

手动输入 `operation`、`storage` 和 `request`。`storage` 是事先审查的独立规划
Issue 六字段配置：`repository`、`issue_number`、`issue_node_id`、`bot_node_id`、
`workflow_id`、`epoch`，epoch 使用 `canary-planning-` 前缀；不得复用 scheduler、
报告或评审发现存储。配置中的身份仍须通过实际 API 验证，不是用户填写就获得信任。

- `init`：仅初始化精确预留、无评论且 body 匹配空模板的 Issue；不能重置已有 journal。
- `bootstrap`：显式保存初始独立进度，`request={}`。空基线保守选择 bootstrap/full，
  不表示历史站点从未部署；本入口不接受缺少真实 receipt 的非空进度导入。
- `adopt-version-baseline`：仅手动调用，`request={}`。从冻结 control 的
  `tools/canary/first_version_baseline.json` 读取已批准的首次基线，核对其 main 第一父链
  和该修订的两份真实 Host manifest；不接受调用者提供 SHA、版本或 receipt。
  必须已 bootstrap，且尚无观察或 active／pending／未完成计划。采用事件保留完整配置、
  manifest 字节和 Git blob 身份，只设置 `version_accounted`；站点／formal 指针仍为空，
  scheduler、失败和债务不变。相同完整回执重试不重复追加，改变回执或迁移已有计划均拒绝。
  这不修改 Host 版本或 changelog、不回填历史，也不证明测试通过、站点部署或版本发布。
- `observe-result`：`request={"source_request_id":"<exact-scheduler-request-id>"}`，
  从可信 main 配置读取 scheduler，完整核验已持久结果；失败、缺证据、无需测试及
  非自动来源不产生计划。成功的局部测试只是唤醒，不能缩减各站点累计测试范围。
- `recover`：使用同一个 `source_request_id`，恢复已存在的原始 intent；不存在则拒绝，
  不偷偷建立新计划。初始化／bootstrap 都不会自动发生在读取失败的处理分支。
- `reconcile-next`：`request={}`，与自动入口共用同一逻辑。优先恢复未完成的原始
  intent；否则从真实 scheduler 的稳定顺序中发现一个尚未记录的终态结果，保存完整
  观察后才视为已处理。重复唤醒不重写已有观察，后续调用继续下一项；没有工作则返回 idle。
  失败、缺证据、无需测试及非自动来源保留为忽略观察，不启动 AI，也不伪装成测试通过。

完整决策先通过大小检查，再把 main、control、scheduler 身份、独立进度和预期结果
摘要写入小 intent，随后保存完整分块计划。中途失败只按冻结输入重建并核对原摘要；
写入结果未知时先核验原请求，不能盲目重复 POST。scheduler 有未完成 append 时，
规划器拒绝修复其 checkpoint，交由原 scheduler 恢复。完整计划已保存后，恢复不再
读取 scheduler 或已过期 artifact，更新后的 main／control 不能覆盖原计划。

一个 active 计划保持固定，新成功目标只合并为较新的 pending；迟到旧结果不覆盖它们。
返回记录的 `slot` 是观察当时的位置，不代表该记录此刻仍占有 pending。此阶段没有
完成 active 或推进后续版本／站点进度的命令；首次基线采用不是这些完成操作，
须等后续协调器能验证真实完成证据。
`planning.json` 保留完整观察且 `admission_evidence=false`；artifact 存在不是交付许可。
本地重启／丢响应测试不证明线上锁、凭据、配额、存储启用或部署验收已完成。
未采用时，空版本基线保留 `None` 和 bootstrap/full 范围；采用后，实际版本区间从
持久化的已批准基线开始，不能把某轮测试的 base 当作版本已记账的起点。站点 bootstrap
的全量测试下限不会随版本采用缩小，也不能将 active 计划解释为评估执行许可。
`reconcile-next` 遇到早于已采用首次版本基线的成功 auto/bootstrap 结果时，先完整核验
测试来源、保留 verdict 和 main 第一父链，再保存 `historical` 观察及完整采用收据，
不计算反向版本区间、不生成计划，也不占用 active/pending。只有版本进度仍等于该首次
采用收据、所有站点及 formal 进度仍为空时适用；缺少收据、进度不符或证据损坏仍报错。
等于基线的结果正常规划：版本区间为空，首次站点部署仍保留 bootstrap/full 下限。
每次只持久化一个完整观察，下一次继续发现后续结果；丢响应时先恢复原 intent 和完整
决策，不能重置 scheduler、丢弃来源、重复未知 POST 或伪造站点进度。历史观察不是
测试覆盖、版本评估完成或部署收据。该源码策略不等于线上历史积压已协调完毕；
真实存储、基线采用和自动 readiness 启用仍须单独验收。

## Web Runtime Host Proof
`scripts/web-runtime-host.sh configure|build|test|proof|serve|clean` 是正式 Host 的稳定入口。`proof` 先在明确的非 clean-room 阶段运行现有 Chromium AudioWorklet conformance，再以固定 emsdk 连续执行两次 clean build，并逐字节比较两份 dist 后才运行 Python/Node/C++ Host 测试；它验证带 ownership contract 的 canonical manifest、完整生产资产清单，以及无 source/map/fixture/server/dev dependency 的精确 dist inventory。fixture generator 使用真实 native C++ compiler 对 active `realtime_engine.hpp` 常量求值，确定性再生 48 kHz mono PCM fixture；clean-room 阶段只把第二份 dist 与批准的 WAV/metadata pair 复制到 `mktemp -d`，从临时 dist 启动 proof-only server，并禁用 Playwright 的 source-tree toolchain webServer。Chromium 阶段从 Git tracked inventory 选择全部 `web_runtime_host_*.spec.mjs`，因此 source-shell lifecycle、manifest gate 与完整 packaged 创作/restart/failure journey 都属于稳定 Proof；随后单独运行 WebKit capability smoke。全程清除 `NODE_PATH`/`PYTHONPATH` 并禁用 package fetch；`clean` 只删除解析后的 `build/web/host` 子树。

Packaged Chromium 还用真实 capability Worker 覆盖 2.5 秒 delayed result 与 test-only shortened deadline：前者必须保留三项 OPFS capability 并进入 `audio-suspended`，后者必须精确报告 `HOST_TIMEOUT`，两者都验证 Worker/Blob cleanup。Issue #166 的 branch/PR proof 之外还要求一个 pinned Linux runner 在同一固定 CPU + file-I/O contention session 中连续三次完整 `scripts/web-runtime-host.sh proof` 全部通过；不得从更大样本挑选成功运行。

Chromium diagnostic journey 验证 Project v4 fixture、500 个 paced Trigger、frame-stamped Sequence begin/event/flush/stop、next-Bar switch、跨窗口 status/observer/busy、idempotent receipt replay、owner-loss recovery，以及既有 Snapshot/lifecycle/terminal failure paths。Host 不含 Take operation、Project parser、quantizer 或 fallback sequencer。

WebKit smoke 只有在所有 mandatory primitive 可用时才运行 protocol、OPFS、restart 与 lifecycle；否则必须输出结构化 `UNSUPPORTED_WEB_RUNTIME` limitation。当前 Playwright WebKit 缺少 `opfsSyncAccessHandle` 与 `opfsWritableReplace`，因此是明确限制记录，不是完整 PASS。

## Web 分发 HTTP 门禁
proof-only server 在 bind 前运行完整 dist verifier；它以 dynamic port、新进程 PID 和一次性 nonce 的 ownership record 建立 readiness，端口已被旧进程占用时不能误判为成功。每次读取都用目录文件描述符、`O_NOFOLLOW` 和同一已 `fstat` 的文件描述符，并再次匹配启动时的资产 hash，因此符号链接、路径交换和普通文件替换均不会被服务。所有响应设置精确 COOP/COEP/CORP/CSP 与 `nosniff`，Wasm 为 `application/wasm`；仅 index/manifest 为 `no-store`，内容哈希资产为 immutable。Traversal、目录、Range 与未知路径返回 404，不支持的方法返回 405。EXIT/INT/TERM 都清理 Host 所拥有的 server PID 与临时 readiness 目录。该服务只用于本地 Proof，不是生产发布入口。
## 构建输入与依赖门禁
`scripts/verify-core-dependencies.sh` 校验 `third_party/` 下 vendored 的两个 pinned 依赖，全程离线：缺文件或哈希不符即 fail closed，并保留对 PicoSHA2 interface-library CMake 的结构断言。`cmake/LmdjDependencies.cmake` 同样只读本地副本，因此 configure 与该门禁都不在运行时依赖 `github.com` 可达性——2026-08-12 的边缘限流曾使这两处在受信池与托管 runner 上同时假红。上游 URL、版本、pinned 身份与更新流程记录在 `third_party/README.md`；vendored 字节是 pinned 输入，不是可编辑源码。
pinned emsdk 与 Playwright 浏览器由 `actions/cache` 按 pinned 修订/版本与 lockfile 哈希缓存；未命中时走原有安装步骤并回填。缓存只提供**输入**：emsdk activate 始终执行，因此生成的 `.emscripten` 不会带上他机的工作区路径；Formal Web Runtime Host 仍校验 emsdk HEAD、releases tag 与 `emcc --version`，错误或损坏的缓存会让 lane 失败而非被静默使用；两次 clean build 逐字节一致的确定性门禁不变，它持续证明产物不依赖缓存状态。GitHub 按分支隔离缓存作用域，PR 分支写入的缓存 `main` 读不到，因此加速在合并后的下一次 `main` push 才显现。

CI 不再依赖 Docker：CI-only 主机没有 daemon，共享主机的 runner 用户也不在 `docker` group，CI 因此永远无法触及运行生产的 socket。CI Contract lane 相应改用按 SHA256 校验的 actionlint release 归档而非 container action，版本不变；digest 指定的是确切字节，而它取代的 Docker tag 只指定版本。

匹配池满载时仍然只排队，不转向付费 runner。若始终没有匹配的 runner 上线，job 保持 queued，并在 GitHub 的 24 小时排队上限后被自动取消——终态是 cancelled 与 runner 可用性告警，而不是无限等待，也不是静默账单。

runner 证据始终分开报告：注册与 online 不等于被选中，被选中不等于成功。真实 `runner_name`、排队秒数、执行秒数、计费 worker time 与 run wall-clock 各自单独记录，任何一项都不能替代另一项。

Web Runtime Lab 是第四条、也是最后一条切换到专用 CI-only 角色的 Web lane。它与前三条不同：它不使用共享的 `web-ci-proof` composite action，而是一条短而稳定的 Node/Python 套件，不在主机上安装任何东西，因此切换只改变执行位置——checkout、Python 3.11、Node 22 与 `scripts/web-runtime-lab.sh test` 的步骤序列不变，也不继承 `web-runtime-host` 那条为量级完全不同的 lane 设置的 75 分钟 hang 检测上限。Formal Web Runtime Host 是继 Web Toolchain 与 Creator 之后第三条切换的 lane，也是这套专用容量最初要解决的对象；它的 Emscripten 身份校验、LFS fixture 补水与 proof 步骤都未改动，只有执行位置改变，因此角色上的持久 toolchain 也无法绕过固定编译器身份检查。Creator lane 是继 Web Toolchain 之后第二条切换的 lane。它此前明确留在 GitHub-hosted Ubuntu：完整 Wasm/OPFS fault matrix 时序敏感，曾在异构共享自建池上超出限定测试预算。那是确定性决策而非容量决策，因此增加 runner 槽位或 toolchain 缓存至今都不构成迁移理由；真正成立的是另一条论据——专用 CI-only 角色消除的是异构本身，且只对已用真实运行证据逐条验证过的 lane 成立，Web Toolchain 先切换并给出证据，Creator 随后按同一方式验证。契约测试现固定其角色路由、trust 条件与 lane 输入，同时保留这段时序敏感的历史理由，避免后续成本或确定性回顾把该迁移误读成容量决策或原样退回。Package 现在完全不经由 hosted 执行，因为已没有 fallback 可走。所有 CI CMake build 均限制为 3 路并行。Linux 原生任务无条件共享 `ci-core` 主机上 checkout 外的持久 `ccache`，Emscripten 与 Package 明确绕过；M1 原生任务使用本机持久 `ccache`，GitHub-hosted macOS fallback lane 不依赖 runner 本地缓存。

macOS Core Proof 与 native ASan 继续优先带 `lmdj` 标签且在线的受信 self-hosted runner。外部 fork、状态密钥缺失、Runner API 失败、机器离线/缺失/标签不符时直接选择 GitHub-hosted macOS；busy 则排队，理由与 Linux 池相同且分量更重——GitHub-hosted macOS 单价是 Linux 的 10.3 倍，在 2026-08-01..13 的 Actions 支出中以 11% 的分钟数占了 57% 的金额。离线仍按可用性条件处理：单台笔记本 runner 睡眠时若排队，会延迟完整自测批次。self-hosted lane 只有在 checkout、加速/`ccache` setup、通信中断或 30 分钟上限导致未发布终态时，才执行一次 GitHub-hosted fallback；加速 setup 成功后已发布的准备、Proof 或 sanitizer 失败是最终语义结果，不触发 fallback。对外 check name 仍为 `core (macos-latest)` 与 `core-asan-macos`。

排队、执行、资源锁等待和端到端时长分别报告；未自动采集的阶段作为明确观测缺口，
不能拿本地耗时代替远端实测。SLO 是容量观察，不把慢但成功的 job 改成失败；
测试自己的行为 timeout 和独立 job hang 上限仍有效。编译、Proof、sanitizer、
Coverage 不自动 retry；缓存统计只是诊断。O1/O2 的真实触发、backend、报告与并发
合并演练须保留实际 URL/run/target/attempt，源码和单测通过不代表远端已验收。

Hosted 用量是预算目标，不是未经验证的保证。观察周必须按 PR updates 与 merges 归一化，把 routine hosted minutes 与旧的无条件 PR/main 矩阵基线对比，分开记录 PR review、完整自测、控制面与显式候选重测成本。Routine hosted minutes 不得持续高于可比基线；任何持续回退都先修正路由或合并 job，无法在不削弱证据的前提下修正时回滚永久迁移，不用增加预算或 retry 掩盖。

本地 Mac 可以在 push 前承担额外的 focused、Proof 或浏览器预检，但这些结果不替代绑定具体 target 的完整自测或发布证据。

由 Core Nightly reusable workflow 承担的两个 native suite——Release stress 与 TSan——都以字面标签集合 `self-hosted`、`Linux`、`X64`、`lmdj-linux`、`lmdj-linux-pool`、`ci-core` 路由，并同时加入仓库级 `lmdj-native-heavy` 队列：只点 `ci-core` 角色不足以串行化它们——该角色跨越同一台物理主机上的多个 runner service，两者会在同一秒启动、彼此并行。run `33838737018` 在 2026-09-04 正是如此且两者皆败，使当时的 TSan probe 结果不可用：它测到的是争用，而非主机能否执行 TSan runtime。Release stress 仍最多连续运行 20 次并在首次失败时停止，不把失败重试成绿色。定时 TSan 曾长期留在 GitHub-hosted `ubuntu-24.04`：run `33905688022` 在容量队列生效、probe 独占运行的条件下仍以 `FATAL: ThreadSanitizer: unexpected memory mapping` 在 0.03–0.12 秒内死亡。#693 查明原因在主机而非 runner 或编译器：6.8 内核默认 32 位 `vm.mmap_rnd_bits`，任何 TSan runtime（GCC 13、LLVM 18、LLVM 22）都无法在该布局下直接启动，只能以关闭 ASLR 重新 exec，而 runner unit 的 `LockPersonality=true` 禁止这样做——LLVM 22 因此给出明确 FATAL，LLVM 18 的共享 runtime 则 9/10 次静默死亡（即 #676 探针 B″ 的"0.01 秒无输出"）。Owner 决定由 `scripts/ci/host/configure-sanitizer-aslr.sh` 把 `ci-core` 主机的熵封顶为 28（与 GitHub hosted 镜像一致，保留 ASLR），同 revision 的 probe 随后在 netcup 上通过，定时 TSan 据此迁至 `ci-core`，probe job 与其 dispatch 输入一并删除。该 lane 在构建前以固定的 Clang 22、与 Core 一致的共享 TSan runtime 和 rpath 编译最小双线程程序，要求连续十次启动全部成功，首次失败即停止并保留 infrastructure verification debt；随后以 `CC=clang-22` 显式配置并执行完整 stress suite。`vm.mmap_rnd_bits` 是 root-only（0600）接口，普通 runner 不再通过读取它判断兼容性；预检不修改主机权限或 ASLR。契约测试固定这一路由、实际 runtime 预检、失败分类与编译器 pin。
