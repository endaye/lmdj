## 1. 目的与非职责
事务式保存/加载 Project Truth、导入/导出 portable Project Bundle，并维护 Sequence journal overlay、flush receipt 与 recovery artifact；不 Cook、渲染或拥有 Host UI。
## 2. 当前实现状态
Project I/O 的 Store、Sequence Journal、streaming Bundle parser/packer、旧 Contract 读取与当前 Contract 写出、Sound Set Store、Catalog transport 与缓存、Workspace Cache 和 crash-safe publication 已实现。`persisted_projection` 写出 v5；v1/v2/v3/v4 读取保留原有迁移纪律，打开本身不回写。Bundle envelope 及 native/Python reader 同步接受 v5，并继续接受旧 envelope 版本。v4 上的旧 Lineage 在下一次持久化原样保留，capability_adoption 必须属于 v5。完整 Slice lineage 随 Asset 进入 checkpoint 和事务 payload；同一内部 command ID 的 replay 比较原始完整 payload，任一证据变化拒绝 collision，重开后保留分析源 revision 和独立物化 Artifact 身份。Workspace Job 状态、terminal 文件与候选生命周期不混入 Project。journal 现在是 session-kind aware：`SessionKind::sequence` 与 `SessionKind::performance` 分别标注 active journal 与 flush record，`ActivePerformanceJournal` 独立承载 performance fingerprint、flush 序列、pending events、rebase 记录、transient checkpoint 与最后一次 launch acknowledgement。Performance 侧另有独立于 Sequence 的 draft 生命周期：`begin_performance_draft` 在 journal 自身的锁内以 begin/complete 两段方式登记草稿，`save_performance_draft`/`discard_performance_draft` 结束草稿，`stop_performance_session`、`apply_performance_recovery`/`discard_performance_recovery` 与 `bind_performance_recording` 各自返回带 identity 的 receipt，owner loss 通过 `preview_performance_owner_loss` 先给出 transient closure 预览再 seal。flush 以 manifest replacement 为 commit point，并把 command/session/flush identity 与 committed revision 写入可幂等重放的 receipt；同一 `command_id` 的 replay/collision 始终比较不可变 original canonical payload，相同 append 返回原 record，冲突 payload 在写入前失败。completion 只更新独立 effective recovery residual，不能改写 command identity；sealed payload v2 同时要求两者，Sequence active/recovery 已直接采用新内部格式，旧或未知 Sequence 格式拒绝读取并保留原文件。当前 source 在每个已接受 Sequence Pad event acknowledgement 前 append 单调、checksummed canonical tail；flush record 消费同一 tail。若较早 flush 在 commit point 前失败，后续 flush 必须 canonical 覆盖全部 unresolved batch 与最新 tail。任一 receipt 可见时，Project I/O 按同 session/pattern/expected-revision 的 canonical key/value coverage 双向 resolve：较晚 completion supersede 被覆盖的较早 batch；较早 completion resolve 精确等价的已耐久 retry，并从非等价较晚 batch 及当时最新 durable pending tail 扣除精确 committed event、保留新增或同-key 新值 residual。即使没有较晚 flush，owner loss 也 seal 未提交事件与未完成 admission 状态；tail 的单调 sequence metadata 与 canonical 顺序不被过滤重置。所有普通 authoring mutation 仍在持有 writer lease 后重读 active Sequence Journal；存在 active journal 时只有 `UpdateSequenceSettings` 属于既有白名单，其成功提交由 Store 同步 rebase journal。
Pad playback 的 writer 总是写出五个 `5.0.0` 键，`5.1.0` 回放对齐键只在偏离缺省值时写出，因此不使用它们的 Project 字节不变、仍能被 `5.0.0` reader 读取。reader 要求五个基础键、接受对齐键的任意子集、仍拒绝未知键；`lmdj.project.v5` 之前级别的 checkpoint 拒绝对齐键，而交易日志与撤销历史由当前 writer 写出、始终接受它们，所以撤销一次对齐编辑会恢复每一个字段。范围校验来自共享的 `domain::is_valid_playback`。`5.2.0` 的 attack_ms、release_ms、tone 与 eq 遵循同一规则：只在偏离缺省值时写出，缺席的 EQ 段不写。reader 要求每段的键完全匹配，`kind` 只能是 `shelf` 或 `cut`；checkpoint 必须是 canonical 形式，所以显式写出的空 `eq` 被拒绝。
`5.3.0` 的 Asset `category` 与 Pad `colour` 覆盖色同样只在有值时写出，见下文“Pad 颜色与 Asset 类别”。
## 3. 所有权与依赖
依赖 Foundation 与 Authoring Domain；平台适配不能改变领域语义。
## 4. 架构与数据流
Facade 提交 Project、Bundle stream、bounded Sample bytes 或 Sequence flush；Project I/O 在 writer lease 下验证 journal overlay 和 authoring admission，原子发布当前 Project revision，再完成 receipt。Store 只暴露已提交 Project Truth；未提交 overlay、owner-loss recovery artifact、waveform cache 与不可变 Runtime Snapshot 生命周期彼此独立。active journal 的拒绝错误携带 session identity 和 stop-or-reconcile remedy，不允许调用者从无锁内存观察推断 authority。
`ProjectBundleTransfer::duplicate` 在调用方提供的新 Project ID 下复制一个本地 Project：全程持有源与目标 writer lease（其他进程或标签页持有任一方时返回 `project_busy`），源有 active Sequence 或 Performance Journal 时以 `sequence_session_active` / `performance_session_active` 拒绝；随后读取已提交 Project Truth，把每个被引用的 Asset 与 Performance 录音 Artifact 按 SHA-256 与长度校验后复制到 staging，以 revision 0 写出全新 history 并完整重载验证，最后在同一目标 lease 下 `publish_directory_if_absent`。副本不携带源 history、sealed recovery 或未引用 blob；Lineage 中的源 revision 原样保留为溯源。拒绝、失败或取消都不发布任何目录，staging 由同一次调用或启动清理删除。
## 5. API 与 Artifact 边界
只持久化 Project Truth 与原始 WAV Artifact；`lmdj.project-bundle.v1` 只定义 transfer envelope；Workspace waveform cache 可丢弃重建，Runtime Snapshot 明确禁止持久化为创作真相。

`ProjectStorageRangeReader` 是可选 C++ companion，不改变既有 storage platform
vtable。`read_range(path, uint64 offset, span<byte>)` 返回实际写入的前缀长度，最多为
调用方 buffer 大小；短尾、EOF 和空 buffer 保留未写部分，空读仍验证文件路径。
Native 复用安全打开与共享文件锁，在 `pread` 后复核 metadata；OPFS 每次取得新的
File，只读取 `slice` 窗口。每次调用独立，失败后的 buffer 内容不可信，没有跨调用快照。
平台所有者必须在使用 companion 期间保持存活；缺少能力时没有整文件读取 fallback。

这些是未校验的原始字节，不证明 Artifact digest、Performance 引用、writer authority
或耐久性。已保存录音须通过下述 ProjectStore 扫描校验其 owner 和完整输入；WAV
元数据可由 Project Cooker 的有界流式检查器解析；Facade/Host 查询仍属于后续任务，
Host 继续只使用 Application Facade。

`ProjectStore::scan_performance_recording` 在既有 history guard 和单次 writer lease
内核对 Project ID、Performance ID、预期 Project revision 与精确录音 ArtifactRef，
入口固定 bundle/selector 快照，回调改写调用方请求对象也不会改变本次读取身份；
只扫描该录音；不执行 authoring recovery/scavenge，也不读取其他音频。它用1MiB heap
buffer、连续 uint64 offset、完整 SHA-256、前后长度和 EOF 检查验证全部输入，结束时
重新核对 committed owner/revision/binding。既有 vector reader 的64MiB限制不适用于
这项有界扫描，原 reader 行为保留。

同步 consumer 收到的是临时、未校验 span，不能保留或用于重入/修改 Project；失败后必须
丢弃 consumer 状态。只有最终 `PerformanceRecordingVerification` 回执证明完整输入
匹配该 owner 下的 Artifact，回执携带 Project/recording revision 和精确引用。缺少
range companion 时返回 typed I/O unavailable，不退回全量读取。这项扫描不证明 WAV
编码、录音完整性或演出 elapsed。consumer 可将窗口交给 Project Cooker 的
`WavMetadataInspector`，保留格式错误并继续完整 hash；最终回执成功后才发布元数据
或 unsupported encoding。摘要/owner 校验失败须丢弃 provisional parser 状态。
真实 OPFS 测试分别验证有效静音、已校验但不支持的编码和尾部摘要损坏，并在两次
实际重开后核对完整身份与元数据。Facade/SDK 异步查询与 owner retirement 已实现；实际 Take Host consumer 仍待。

保存草稿／绑定 Performance 录音时，原有 writer lease 与 history guard 内的
`verify_managed_wav_artifact` 也在 Native／OPFS 上使用1MiB heap 窗口，逐块校验
完整 SHA-256、前后长度和 EOF，避免 OPFS 整文件分配后再复制成 C++ vector。
短读继续推进；零进展、错误计数、读取失败、文件增长／截断或摘要不同均保留原有
`performance_recording_artifact_unverified` 拒绝，不发布录音引用，停止草稿可重试。
没有 range companion 的旧自定义平台保留既有 complete-read 行为；已提供 companion
的读取失败不会回退整文件读取。这只验证原始 Artifact 身份，不验证 WAV 编码、
录音完整性或演出总时长，也不改变 Save／bind 的幂等与 writer 生命周期。

这三处有界读取（录音扫描、Save／bind 校验与发现摘要）共用1MiB窗口。OPFS 每次 range
读取都有固定的挂起与 handle 查找成本：64KiB窗口下，一段三十分钟录音需要约5,300次调用，
校验耗时约10秒且主要花在调用开销上；1MiB窗口把调用次数降到约330次，校验时间回到以
SHA-256 为主（#2477）。窗口仍与录音长度无关，每个字节仍被完整校验。

## 6. 状态、错误与生命周期
本地 `list_local_projects` 的完整 inventory 摘要使用1MiB heap 窗口、前后长度和
EOF 检查。history guard 覆盖 Project load 与全部 hash；能取得 writer 时持有到扫描
结束。foreign writer 繁忙时保留 `ProjectStore::load` 原有的已提交只读读取，不能因此
恢复、修改或取得对方的 writer 权限，也不承诺跨 owner 的原子文件系统 snapshot。
读取失败或观察到长度／EOF 变化仍拒绝，不发布部分摘要。单个已打开工程不会仅因
其 writer 被占用而让整个列表失败；显式打开该繁忙工程仍保留原 `project_busy` 拒绝。
它保留原有 summary keys 和 canonical digest；生产 Native／OPFS 可发现包含长录音
的本地工程，不在发现阶段套用 Bundle 传输的单文件／总 payload 字节限额。
路径、条目数量和整数溢出检查保留；读取失败不发布部分摘要，已有 range reader
失败不回退整文件读取。旧平台的小文件 complete-read 路径保留，大文件缺少有界
能力时在分配前明确拒绝。此发现回执不授权传输：Bundle 导入、commit 与复制仍保留
原64MiB／512MiB 限额，未改变格式或持久化 Contract。

故障矩阵验证验证、取消、超时与发布中断恢复；typed error 区分输入、平台、busy 与提交失败。

## Web writer ownership across worker realms

同一 `ProjectStoragePlatform` 对同一 canonical Project 的真实 leases
共享已取得的物理 writer。Control 和 durable I/O child 各自拥有本 realm 的授权 token；
child 不再尝试第二次获取独占 OPFS lock。路径仍按原 C++ lexical normalization 与
JS component 规则处理，原 `bundle/../bundle` 等价路径保持不变。

父 realm 最后一个本地 token 释放后，若 child 的真实 pin 仍存在，物理锁保留；父 realm
不再有 mutation authority，但同平台可重新取得引用。不同平台或独立 Module 仍需真实
物理排他。child 先移除自己的 exact token 再退还共享 pin，释放不等待 Control event loop
或代理；物理 owner 在总 pin 实际归零后关闭。JS 独立持有共享记账内存，直到真实关闭
发布 receipt，避免最后 C++ 引用在 child 销毁后 owner 的 pending drain 读取悬空内存。
错误 realm、token 或 generation 保留 cleanup debt，不冒充释放。

`createSyncAccessHandle` 成功即登记物理 custody，即使初始化／recovery 后失败且关闭
也失败，handle、共享内存和 module-wide physical count 仍保留。恢复完成前不授予新的
mutation authority；关闭异常仍是真实失败。该修复未改变 storage vtable 或持久化格式。
新增真实 pthread／OPFS 跨页面旅程覆盖 parent reset、child-only 写入、物理 busy、
无 Control service 的 release、natural join、完整字节／长度／SHA 和独立重开。

## Durable Pattern recording admission

Sequence Journal 在同一 writer lease 和 checksummed record 流中保存 preparation、
带原始 press correlation 的候选、两个独立不可变 admission/cutoff fence、closure，
以及带逐候选 SHA-256 receipt 的 transfer。它们属于恢复元数据，不进入 Project Truth；
存储不判断声音是否播放，不重放 live enqueue，也不改变成功、失败、未知的输入结果。

当前 staged source 的 Sequence active journal 与 recovery snapshot 均使用私有 v3 格式；
它们不是跨语言注册 Contract。
preparation 保存初始 Quantize/Swing；不可变 timing profile 保存 Command ID、下一个
control watermark、Pattern/publication、revision 以及 frame/精确 tick numerator/BPM
锚点。调用方必须在后续候选前持久化实际历史设置；相同 Command ID 的不同 payload、
改写已保留输入或早于已转换 checkpoint 的新锚点均拒绝。active 重读和 sealed snapshot
保留完整 profile history，并重验锚点不早于 watermark 边界之前仍保留的候选或
transfer checkpoint；后续 transfer 与 terminal cutoff 不反向限制历史设置。
append 回应未知时精确重试仍须完成真实 sync。
相同 session 的重复 `set_state` 也在原 writer lease 内对现有有效前缀执行空追加与
真实 sync；可读的 `owner_lost` 状态不能代替耐久确认。持续 sync 失败保留失败，
不在每次重试时追加相同 state 记录。

S6 staged parser 在 worker 线程内保留单个已验证前缀，只有一次 fresh complete read 的
完整字节包含逐字节相同前缀时才复用其派生解析状态；新增记录仍校验 envelope、
checksum、顺序和 admission codec，修改或截短前缀会完整重验。真实 replay 得出的未解决
canonical candidate bytes 传给 writer；transfer 只扣掉实际消费的 prefix，历史精确重试
不占新预算，碰撞仍拒绝。
当前 manifest 与它派生的 checkpoint 每次完整重读；只有 path 与完整字节相同才复用原
解析事实，调用者 Project ID 每次比较。Journal、manifest、checkpoint 的 retained raw
字段共用原 1 MiB 上限，余量不足就冷解析；读取、解析或身份失败会清掉该私有解析缓存。
这不是峰值内存上限，也不替代 ProjectStore 的完整 authoring/history 校验。writer lease
与真实 append/empty-append sync 保持独立；缓存不持久化，也不进入 Project Truth。
这些优化旨在减少重复解析和一次 layout 检查中的重复路径遍历，不证明写入耐久、
deadline 成功、音频效果或 ACK。

Native 的可选 `ProjectJournalLayoutValidator` 独立于现有 storage base，不新增原 vtable
槽。仅 Sequence checked read 发现该能力：不支持时执行完整原 helper，支持但失败时直接
保留失败；Sequence begin 的入口 layout 检查、sealed document 校验与 Performance 仍走
原 helper。begin 已有的 active-Sequence 错误详情查询仍按 Sequence checked-read 路由。
每次调用重新安全
打开根目录、递归拒绝整个 managed tree 中的 symlink、特殊文件及 hardlink，并检查原八个
目录及真实打开、共享锁内重核身份和非负长度的 manifest。同一次调用复用临时父目录
descriptor；返回前重新按名字安全打开根目录，比较 device/inode/type 以拒绝根替换。
该能力不缓存 descriptor 或成功结果，不授予 writer lease、耐久 ACK 或全树原子视图；
后续实际完整读取、writer lease 与 sync 保持原路径。OPFS 保留原 fallback。新测试以真实
文件系统反例检查缺失／错误类型、未使用的危险条目及有效根替换，并以独立真实文件
锁检查共享共存、排他拒绝和返回后释放。

可选 `ProjectStorageTextReader` 为 Sequence Journal、manifest 与 checkpoint 的每次完整
读取提供保持全部字节的字符串缓冲区，避免先构造、销毁逐字节 vector 再复制成字符串。
它不解码 UTF-8、不转换换行或截断 NUL，也不缓存文件内容。Native 与原 `read_complete`
共用安全路径遍历、regular-file 检查、共享锁、完整 `pread`、读取后 metadata 校验及原
replacement-transient 重试；只有返回缓冲区的表示不同。原 storage vtable 不变，不支持
该 companion 的平台继续走完整 byte-vector 回退路径；支持但失败时直接传播原错误。
Performance 保留原 byte-vector 路径。该能力不授予写入、耐久或 ACK 权限。

v1/v2/未知 Sequence discriminator 拒绝读取并保留原字节，不自动迁移或删除；
Performance journal 与 Project Truth Contract 不因这些字段改变。

未解决候选上限为 1024 条及 1 MiB canonical candidate bytes；每次 transfer 独立预留
1 MiB，两个 fence 加 closure/completion 预留 64 KiB control space。最后一个 count/byte
slot 的候选与 capacity closure 属于同一 durable record transition。5000 ms deadline
由 coordinator 的单调时钟执行，存储只校验政策并保留显式 closure，不持久化墙钟期限。
这些限制约束未解决候选和单条记录，不代表整个 recording file 固定大小；不可变 transfer
history 随现有 session 生命周期增长。

普通录制切换通过 `retain_admission_switch` 先持久化已确认的目标 Pattern、publication
generation 和实际 activation frame，再 flush/source switch；没有确切 authority 时在
写入 switch 前拒绝。一次只允许一个尚未完成 journal reconciliation 的边界，S 之前的
source 候选先 drain，S 及之后的 target 候选可保留跨越 source flush/switch。独立 switch
history 与 `S<F` cutoff receipt 必须一致，`S>=F` cancellation 不能被改写成 applied。
checkpoint 同时保存 Pattern 与 publication generation；P→Q→P 是不同 segment，不能
复活旧 P 的 owned presses。切换不制造 event/release 或推进 input sequence。
streaming preflight 在 DOM 分配前检查包括未知 envelope/payload 字段在内的记录边界，
active tail/flush 的 events 必须为 array；historical receipts 不受整会话固定大小上限。

transfer 在一次 append 中替换完整 canonical recoverable tail、保存 checkpoint 和 receipt、
消费确切候选前缀。已消费候选仍可通过 receipt 检查 exact retry；相同 identity 的不同 payload
拒绝。无输入贡献的 prefix 不推进 journal input sequence，也不修改 checkpoint。
显式 terminal transfer 在两个 fence、closure 已耐久且无剩余候选时，原子保留 Facade
提供的既有 unreleased-note finalization 和空 owned-press checkpoint；它不制造 release
或新 input sequence。terminal 后只接受旧 transfer 的 exact retry；完成还要求 canonical
flush 已知完成。

active reread、sealed snapshot/list 和 owner-loss reconciliation 都保留 admission，
即使 pending event list 为空。旧 runtime 的 fence 缺失时仍为 unresolved recovery，
不猜测 Pattern/origin/switch 结果，也不自动启动 playback。只读失败保留不支持的旧格式、
未知格式和 torn suffix 的原始字节；没有 migration reader 或自动删除路径。

Web 构建的栈是 256 KiB（`-sSTACK_SIZE=262144`）。`ProjectState` 把 64 个 Pad 内联存放，所以 load/flush/recover 这些深路径的栈需求随 Pad 大小增长：`5.1.0` 的回放对齐键把 wasm32 上的 `ProjectState` 从 4 424 B 加到 6 472 B，曾经超出原来的 128 KiB。[#1720](https://github.com/endaye/lmdj/issues/1720) 让这些路径少持有副本：

- `load_project` 在堆上返回已加载的 Project，`commit_loaded` 接收它的所有权；
- checkpoint 读取、每条交易的重放和 head checkpoint 比对各自放在短帧里；
- `foundation::Result::success` 按引用接收值，不再在调用方帧里留一份副本；
- `describe_artifact` 的 64 KiB 读缓冲改到堆上。

实测最深路径的栈高水位从 175 624 B 降到 98 208 B。

#1667 的音色对齐字段又把 `ProjectState` 加到 10 568 B，门限因此失败：每个动作的峰值都按 4 096 B 的整数倍增长，说明最深处仍同时活着 9–13 个 `ProjectState` 大小的值。[#1771](https://github.com/endaye/lmdj/issues/1771) 在字段合入前清理了这些副本：

- `foundation::Result::emplace_success` 在结果里原位构造组合值，不再先在返回帧里造一个临时对象；
- Authoring Domain 的每个命令处理只保留自己的工作副本，`applied()` 按 `&&` 接收状态并原位构造结果，`create_project` 直接在调用方的返回槽里建 Project；
- `parse_project` 在堆上返回解析结果，提交前的 round-trip 校验原地规范化状态；
- 一致性测试的 harness 不再在自己的帧里持有 `ProjectState`：原来 `mutate_sample_cache` 的测试帧就占了该动作峰值的四成多。

清理后 `main` 上最深的动作是 71 972 B（`history_roundtrip`）；叠加 #1667 的字段后最深是 112 932 B，约为栈的 43%。Project I/O Web 一致性测试在每个原生动作结束时报告栈高水位，任何动作超过栈的一半都会失败，并写明原因与补救。

### Real OPFS evidence and remaining gaps

`project_io_web_conformance.spec.mjs` 的 S2 fixture 调用实际 C++ journal API，
在真实 OPFS 上验证 candidate、fence、transfer 持久化后的回应丢失：
操作成功且观察到 storage flush 后，测试 Worker 发布绑定 bundle、session、operation、
完整 record/checksum 的 marker，在回应前停住；测试关闭其页面以终止 Worker，再在同一
origin/bundle 重开、精确重试并再次重开。断言比较完整 canonical tail、原始 press
correlation、journal input sequence 和不可变 transfer receipt。重试的零字节 flush
不算新增记录；这证明 after-durable/before-response 边界，不覆盖 flush 内任意时刻掉电。

fixture-only 包装复用现有 storage-condition 注入，在实际 append 前抛出 quota 或
invalid-state 错误。Chromium 断言没有新 flush、字节和状态不变、重开后只有已持久化前缀，
随后精确重试成功；这是注入错误处理证据，不是物理磁盘耗尽测试。另有最后一个候选 slot
原子关闭、缺失 fence 的 owner-loss seal/list 重开、预留 fence/terminal transfer，以及
普通 P→Q 切换经过 source commit、target generation/checkpoint、terminal completion
和已提交 Project Truth 重开的证据。浏览器没有据此宣称 P→Q→P 重复身份回归已覆盖。

双浏览器的 OPFS 能力仍是硬性断言。当前锁定 Linux WebKit 未暴露 storage API，
不能把 unsupported 当作成功；已有环境限制也不由 fixture 模拟补齐。Chromium 的关闭后
追加、旧/未知格式与损坏 suffix 拒绝用例验证返回结构化失败并保留字节。Project IO 的
Emscripten 构建为该模块及消费者启用 `-fexceptions` 编译和链接，修正这些生产校验路径
原先因禁止异常捕获而 abort 的缺陷；这不代表依赖模块的 catch 支持或产品性能已验收。
隔离 WebKit 2361 的真实持久化上下文已执行相同存储旅程；它不等同于锁定版
WebKit、Apple Safari 或真实设备验收。标准 proof 自动解析独立安装的测试浏览器，
也保留 `LMDJ_WEBKIT_OPFS_EXECUTABLE` 显式覆盖入口，仅影响 Project IO 的 WebKit
上下文。每个测试使用新建的持久化目录，保留同一测试内关闭页面、终止 Worker、
重新打开和重试的全部步骤；不复用用户配置，不模拟 OPFS，不修改默认依赖。
未安装隔离浏览器时，proof 在构建前报告安装指令，不退回缺失能力的浏览器或跳过 S2。

安装器依赖和完整性摘要独立锁定于 `tests/platform/web/opfs-browser/`，浏览器缓存位于
工作区 `build/toolchains/opfs-webkit/`，不覆盖共享缓存。设置了 `LMDJ_BROWSER_CACHE_ROOT`
的 self-hosted runner 把它装进该根目录下独立的 `opfs-webkit-<版本>` 目录并加锁，
工作区路径改为指向它的链接，避免每次 checkout 清理后重新下载约 100 MB（#2279）。CI 仅为 web_toolchain lane
执行同一安装入口；系统依赖安装仍服从 runner 原有授权配置。Linux 本地示例：

```bash
bash scripts/prepare-opfs-webkit.sh
# 需要安装系统库且已获机器管理权限时，安装命令增加 --with-deps。
scripts/web-toolchain-conformance.sh proof
```

主测试客户端仍是锁定的 Playwright 1.62.1，SDK 仍须满足标准工具链检查。
每项测试附带实际 executable 路径和持久化目录；覆盖浏览器可执行文件后，
不能把锁定客户端报告的版本当作该浏览器的构建身份。测试目录保留供排查。
完整 proof 结果需单独记录，不能用分开运行的通过结果拼成一次完整 proof 通过。

Facade 转换 fixture 进一步链接实际 Application Facade：由保留的输入/历史设置计算
transfer，耐久后在回应前终止 Worker，再重开、精确重试、terminal、seal，并经公共
`apply_sequence_recovery` 恢复到原 Pattern 或已存在的另一 Pattern。断言完整事件、
revision、transfer receipt 与再次 Apply 后 Truth 不变。它没有模拟 Facade 恢复，
但输入和已知 fence 仍由 fixture 提供，不证明 prepared owner、真实设置锚点获取、
未知 cutoff 恢复或 Creator 全局录放已经接入。
Facade 对 sealed admission 的消费及 runtime/Creator 接入仍是后续工作；这些存储测试
不证明 UI Apply、安全恢复已接入、声音接受或自动恢复 playback。

## Performance live-control Journal profile

`lmdj.project.v5` `5.4.1` 的 headered Performance 录音在 Performance Journal 内以显式
discriminator `live_control_profile: "header_input_sequence"` 分支（内部 Journal/recovery
ID 保持 v1；旧 grammar 不接收新字段或新 record kind，discriminator 不从新增字段隐式猜测）。
begin 记录耐久写入不可变 header（`initial_live_state`）与初始空 admission ledger；每条 tail
携带扩展 checkpoint（`open_filter` logical gesture、完整当前 `live_state`、open Pad 的原 press
序号）与当前 ledger；新 record kind `admission_complete` 只携带 kind/performance_id/tail_seq/
expected_revision/receipt，匹配唯一 pending 的 identity+fingerprint 后推进
`next_recording_sequence`，不分配音乐序号、不重写事件。

admission ledger 每 session 最多 1 条 pending + 最近 1 条 completed：receipt 绑定原
request ID、raw-request SHA-256、冻结 tick、`input_sequence`、phase/result 与事件序号列表；
`prepared`/`not_published` 与 `completed`/`published`|`no_audio` 是闭合配对。写入结果未知时
按 present/absent 显式恢复（exact 重读证明或同 prefix 有界重写），不静默降级；owner-loss 收尾
经原 exclusive writer/reconcile 验证完整 prefix 与原 identity 后只做 metadata-only 逻辑关闭与
seal：原 prepared ledger 保持 unknown，closure 事件序号从已验证 durable high-water 唯一派生，
PadHit 复用原 press 序号。terminal 旧 pending 不占用新 session 的窗口；legacy receipt 不会被
自动升级为 ledger。

## Verified Asset owner read

`ProjectStore::read_asset_artifact` 接受 Project 路径、Project ID、Asset ID 和完整
ArtifactRef。在一个 writer lease 内检查元数据所有权、完整引用以及选中音频的 SHA-256
和 byte length，返回独立字节副本；不扫描无关音频，不调用 recovery 或 staging 清理。
错误身份在读取 Artifact 前拒绝；缺失文件与内容不匹配可区分，后者使用显式 storage
condition，由 Facade 归一化为 `IO_ERROR/input_artifact_mismatch`。
既有普通 Project load 仍校验全部 Asset 字节。Host 不直接调用这一存储 API。

`ProjectStore::inspect_committed` 在 owner lease 内返回已提交的 Project 状态，
不执行 authoring recovery 或清理未发布文件。Candidate 分析使用这个入口取得
Project/Asset/revision 绑定，再通过上述 verified owner read 获取音频；成功或拒绝
都保留中断创作留下的文件，由显式 authoring load 负责处理。

## Atomic Candidate adoption

`ProjectStore::adopt_candidates` accepts a distinct `CandidateAdoptionRequest`.
The public writer and persisted reader share the source profile check:
`audio/wav`, at most 16 MiB. Unsupported but accurately bound sources refuse
before publication, leaving the original Project readable.
Under the Project writer it checks current Project/revision/source identity and
source bytes, then applies one `AdoptCandidates` command and stages every derived
artifact through the existing atomic publication pipeline. The persisted command
includes the full source binding and every target Asset/lineage; replay during load
validates that complete identity. Legacy inputs promote through the current writer.

The public method checks freshness before any receipt can be returned. Old-revision
requests fail, including after a committed response was lost. Prepublication failures
roll back all newly published blobs and metadata; restart follows the manifest and
retains exactly the committed revision. `candidate_adoption_test.cpp` exercises
multi-artifact failure points, pre/post-publication crashes, source checks and
persisted identity tampering. Workspace eligibility remains the Facade owner's
responsibility and must span this call.

## Authoring history publication and retention

Every Store sharing a Facade uses its session `AuthoringHistory`. The commit path
prepares a typed delta, retains both possible outcomes before manifest publication,
and moves history only after publication. An unknown response is reconciled against
the committed revision and fingerprint before another action. Exact command retries
reuse their receipt; failed, replayed and content-identical writes add no entry.

Undo/Redo are durable `HistoryRestore` transactions using the normal journal,
checkpoint and manifest path. They persist restored Truth, never the session stacks.
This new private transaction command requires the updated Project I/O reader;
portable Project Bundle and Project Truth schemas are unchanged. A transferred
managed Project may contain these durable transaction commands and therefore also
requires the updated reader. The session stack itself is never exported.

The session keeps at most 100 user actions. Active multi-commit recording retains
the displaced Redo branch and, at capacity, one displaced oldest action until the
group is saved or cancelled. Cancellation restores those entries. All retained
history and unresolved publication outcomes protect original Artifact hashes from
unreferenced-file scavenging. Redo verifies the complete Artifact identity and
reuses those bytes; it does not rerun a Provider or import.

Active recording journals and unresolved recovery disable restoration. A different
committed revision/fingerprint or lost writer ownership invalidates the session.
`project_io.authoring_history` covers publication faults, unknown outcomes, retries,
no-op/fork, retained bytes, reopen, external changes, capacity, Pad clearing and
Performance draft cancellation/save. The real OPFS authoring-history fixture covers
import, Undo, scavenging, exact retry, byte-identical Redo and a fresh-page reopen.


## 分 Pad Sound Set 获取

Sound Set 的 `acquire_slot` 校验完整原始 manifest、许可、总字节声明与所有 descriptor，仅获取指定槽的 Artifact，并在独立不可变 slot cache 原子发布。该缓存不出现在完整 Set 的 list/read 中；缓存重开仍校验内容哈希。`install_soundset` 的空目标前置条件在 writer lease 内、精确 receipt 重放识别后检查，拒绝覆盖已有素材。

## Pad deletion and retained history

`ProjectStore::execute(DeletePad)` persists canonical null-`AssignPad` commands,
so deletion needs no new transaction dialect. A changed binding/playback is one
`Clear Pad` history action; an already empty/default Pad adds no history action.
Undo restores the complete Pad contents, Redo clears them again, and both preserve
Pattern events and retained Asset bytes. Revision and writer/journal admission
still run at the durable boundary.

## Pattern event edits

`ProjectStore::execute(EditPatternEvents)` persists an internal
`EditPatternEvents` transaction; the command log is not a Contract. Before
persisting, the Store sorts `remove` and `put` into canonical order. It only
reorders: a repeated key still reaches the Domain, which refuses it. Because a
reload's Pattern parser sorts events, this keeps the encoded command identity
stable, so a retry after reopen still replays.

Each edit is one `Edit Pattern` history action, and Undo and Redo restore its
events exactly.

## Pattern length and copy

`ProjectStore::execute` persists `ResizePattern`, `DoubleUpPattern` and
`CopyPattern` as internal transactions in the same command log (#1823). Reload
replays them through the Domain, so a retry after reopen still replays.

Each is one history action, labelled `Change Pattern Length`,
`Double Up Pattern` or `Copy Pattern`. Undo restores the prior Pattern exactly,
including events a shortening removed or truncated; for a copy it removes the
new Pattern and frees the slot it took. Redo reapplies them. A resize to the
current length is refused by the Domain, so it records no revision and no
history action.

## Pad 颜色与 Asset 类别

`lmdj.project.v5` 5.3.0 的两个可选键只在有值时写出：Asset 的 `category`（`drums`、`bass`、`melodic`、`vocal`、`texture` 之一）与 Pad 的 `colour`（调色板索引 0–4，即用户覆盖色）。因此没有类别、也没有覆盖色的 Project 保持 5.2.0 字节。v5 checkpoint 不记录 MINOR，所以与回放对齐键一样，每个 `lmdj.project.v5` checkpoint 都接受这两个键，v4 及更早级别的 checkpoint 拒绝它们。reader 还拒绝空 Pad 上的 `colour`、超出调色板的索引，以及未知类别（包括 `none` 与 `other`）。打开旧 Project 不回写；旧 Asset 保持未分类，旧 Pad 没有覆盖色，也不回填。

撤销历史的 Pad 与 Asset 编码按同一规则携带 `colour` 与 `category`，因此 Undo/Redo 精确恢复整个 Pad。Domain 的历史 delta 准入拒绝把覆盖色恢复到空 Pad 或调色板之外的结果。事务里的 Asset 编码也携带 `category`，所以 Sound Set 安装重放后仍保留每个 slot 角色对应的类别。Facade 把 `map_soundset` 提议中的类别传给 `SoundSetInstallSlotRequest`。

`ProjectStore::execute(SetPadColour)` 持久化内部 `SetPadColour` 事务（`colour` 为索引，或为 `null` 表示恢复类别缺省）。它按 `expected_revision` 与 `command_id` 重放，每次修改是一个 `Set Pad colour` 历史动作。`replace` 重装 Sound Set 时保留 Pad 的覆盖色，并为新 Asset 写入新的类别；删除 Pad 会清除覆盖色，撤销删除会恢复它。`project_io.project_store`、`project_io.authoring_history` 与 `project_io.soundset_install_commit` 覆盖以下情形：各种组合的往返、旧 checkpoint 拒绝、非法值、旧 Project 打开、保存后重开、设置/恢复/删除的 Undo/Redo，以及在覆盖色上重装 Sound Set。


## Committed Project 的只读校验

`ProjectStore::inspect_committed(bundle)` 在 owner lease 下读取 committed Truth，
不执行 interrupted-write recovery 或 unpublished-file scavenging；原有 selector
查询继续延后完整 Asset 字节校验。需要完整 Snapshot 准备的调用方使用
`inspect_committed(bundle, true)`：复用 `load` 的全部 Asset 摘要／长度验证，
包括未分配到 Pad 的 Asset，同时仍不恢复或清理文件。

lease 必须在实际调用 realm 取得并释放。独立读取者使用私有 Store/history，不能
把 live Application 的 history mutex 或控制线程取得的 writer token 借给 worker。
只读返回值不构成 Journal／发布完成；最终使用前仍需校验原 Project/revision。
