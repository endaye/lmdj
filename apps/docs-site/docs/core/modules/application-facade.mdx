## 1. 目的与非职责
提供 Host 唯一 Core 入口并编排模块；不承载 Host UI、协议或产品特例。
## 2. 当前实现状态
Application Facade 提供 Host-neutral Sequence begin/event/flush/stop/switch/status/settings/recovery、Pattern create、Pattern Slot assign/clear/move，以及既有 Project/Bundle/Sample/Runtime/Provider surface。本 Build 追加 Host-neutral 的 Sound Set 操作集，共五个：`soundset.catalog.list`、`soundset.inspect`、`soundset.map.preview`、`soundset.install` 与 `soundset.audition`；配套追加 `SoundSetCatalogSource`、`make_workspace_soundset_catalog`、`SuppliedSoundSetCatalog`/`make_supplied_soundset_catalog`，以及 `SoundSetStoreLimits` 别名——Host 由 Facade 配置 Set Store 上限，因此不必也不允许直呼 Project I/O 类型。`ApplicationConfig` 相应在**末尾追加** `soundset_catalog_transport`、`soundset_catalog_source` 与 `soundset_store_limits` 三个成员：仓库内每一处 brace 初始化都是位置式，中间插入会按类型静默改绑 Host 的协作者。上述 Sound Set surface 在引入时属于兼容追加。Stage 12 L3 的 typed ProjectState 返回值暴露新的 lineage variant，因此此次 Facade 分配 MAJOR；C ABI 形状与 api_version 保持不变。本版新增 Host-neutral 的 Performance 操作集，共二十个：`performance.record.begin`、`performance.record.event`、`performance.record.launch-request`、`performance.record.flush`、`performance.record.status`、`performance.record.stop`、`performance.recording.bind`、`performance.save`、`performance.discard`、`performance.list`、`performance.inspect`、`performance.rename`、`performance.delete`、`performance.replay.begin`、`performance.replay.status`、`performance.replay.stop`、`performance.recovery.list`、`performance.recovery.apply`、`performance.recovery.discard`、`performance.resample.commit`。`ApplicationConfig` 相应接受一组 Facade 自有协作者接口：`PerformanceClock`（权威音乐时间，一次成功 admission 恰好消费一次读取）、`PerformanceInputSequencer`（权威 admission 次序，replayed receipt 不消费序号）、`PatternLaunchAcknowledger`（Core Runtime 拥有小节边界次序与 exactly-once outcome，Host 不解析 Slot）与 `PerformanceReplayController`（含 `ReferencePerformanceReplayController` 与 `PerformanceReplayRuntimeSink`）。`make_engine_performance_adapter` 把这些协作者聚合成 `EnginePerformanceAdapter`，`make_headless_performance_runtime_bridge(make_steady_performance_time_source())` 为 headless Host 提供同一组协作者与一个 `service` 泵。`sample.quota` 以 Project Truth 和目标 Pad 为输入，返回计算所用 revision、Bank/Project target-exclusive 用量、有效剩余额度与目标 Bank 的逐 Pad 占用；查询不读取 Runtime publication residency。Facade 统一持有 writer lease、录音 session、选择性 rebase、幂等 receipt 与 recovery policy。每个 Sequence event 先把 completed events 与未释放 press 的 240-tick 默认形态组成 canonical tail 并耐久 append，成功后才更新内存 state 与 acknowledgement；release 的后续 snapshot 替换真实 duration。运行中的 session 会在 journal append 后保留 exact in-flight flush；post-commit 返回失败的重试先完成该 identity，只消费 immutable original command payload，后到事件仍等待新命令。effective recovery 依 flush 顺序合并 incomplete residual、最后合并最新 durable tail，使同-key acknowledgement 覆盖旧值；active/recoverable status、list 与 apply 共享这一 canonical unique batch，因此 completion 过滤不改变 replay identity、不会恢复已提交事件或重计重叠输入。当前 source 还向匹配的 active session owner 提供带单调 generation 的 immutable pending-overlay projection；它是 Runtime 派生输入，不是 Project Truth、revision 或 receipt。Performance 侧遵循同一分层：`performance.record.status` 返回的权威状态（未闭合的 Pad/FX 手势、HOLD 位、最后一次已确认的 Pattern launch）由 Facade 与 Core 拥有，Host 不得用本地预测替代；`performance.replay.*` 消费 Project Cooker 的 `PerformanceReplayProjection` 并回报 `ReplayState {playing, stopped, complete}`、event cursor、event count 与 resolved revision，这些同样是派生状态，不是 Project Truth。只有 `performance.save`/`rename`/`delete`/`recovery.apply`/`recording.bind`/`resample.commit` 这类提交路径才改变 Project Truth，并且照旧经由 writer lease、幂等 receipt 与 `expected_revision` 完成。Flush/Stop mutation result 保留 committed Pattern identity，使 Host 能在 Project commit 后的 Runtime publication failure 上通过 exact receipt replay 恢复，而不重做 Project mutation。非 Sequence authoring 的本机会话检查、孤儿 journal reconciliation 和 Store mutation 位于同一个 Project-scoped admission critical section，消除 begin-vs-authoring 的检查/使用间隙。选择性 rebase 是封闭白名单：除 BPM、Quantize/Swing 外，只允许 Sequence begin 时登记的空 Pad Capture 以同 session、同 Pad、同 expected revision 提交。Project publication 前先 durable 记录原 command/asset/artifact identity；publication 中断后的 retry/restart 只有在 transaction、receipt、revision、Asset 与 Pad Truth 精确吻合时才完成原提交。未发布时，checked Discard/disarm 仅在无 receipt 且 Project Truth 未变时追加 durable abort。durable marker 存在期间 settings 以 `armed_capture_recovery_pending` 拒绝；所有路径都保留 pending events 并在冲突时 fail closed。
新版 Sequence admission 的恢复边界：现有 event-only Apply 只接收已有 durable
terminal transfer 的录制记录；仍含未转换输入或未结束按压 checkpoint 的记录返回
`sequence_admission_unresolved`，保留原始 sealed journal 和 Project Truth，
不会创建替代 active journal。显式指定目标 Pattern 也不能绕过此检查。terminal
transfer 后尚未 flush 的 canonical tail 仍可正常恢复，不要求 admission 已完成
Project 提交；主动 Discard 与 Apply 分开。这里仅保护恢复边界，尚不代表全局
transport 的输入转换、历史 Quantize/Swing 权威信息和恢复 UI 已接入。

## 3. 所有权与依赖

现有 Sequence 的 Pad 事件计算由内部 `PatternEventReducer` 统一实现：
量化/Swing、同 Pad 重触发、duration 截断、canonical tail 与未释放按键的
240-tick 收尾继续复用 Domain 规则。它只是受调用方串行保护的同步 overlay
视图，不拥有 journal、writer lease 或音频时钟；持久化失败的回滚仍由
Sequence owner 负责。可选 press correlation 为后续 admission 转换提供匹配
能力，现有 Sequence 仍按 Pad 匹配 release。该 reducer 提取本身没有新增公共 API、
存储格式或模块依赖。

后续内部 `build_admission_transfer` 从已耐久的候选、fence、timing profile 与
owned-press checkpoint 计算同一 canonical tail；`commit_admission_transfer` 经
Project I/O 写出绑定逐候选 SHA-256 的不可变 receipt，只有 append 已知耐久才返回成功。
回应丢失后精确重试同一 transfer，不重放 live input、不追加第二份事件。
原始 admission origin 保持 tick zero；历史 BPM/Quantize/Swing 按 watermark 选择，
后续 Pattern segment 缺少时间锚点时拒绝转换。cutoff 后 release 不伪造收尾时间，
terminal 沿用普通 240-tick 默认完成。

同一转换还有第二个入口 `project_admission_overlay`：它把进行中的 admission
投影成"若此刻结束将贡献的 Pattern 事件"，供 Host 在录制未关闭时发布 pending
overlay，使录进去的一遍在下一圈即可听见。该投影是纯读取——不改 journal、不推进
watermark、不铸造 receipt identity，因此无论投影多少次，之后 close 提交的
transfer 完全不变，提交仍恰好一次。它与 `build_admission_transfer` 共用同一段
转换，录音听到的叠录与其提交所保留的必然一致。未激活、已完成、已封存的
admission，以及尚待 switch 协调的候选前缀，都投影为空而非失败：这些都是在录
状态的寻常情形，不得污染 transport engagement。候选为空时投影已转换的 pending
tail，因此刚协调完的 segment 不会在两次 transfer 之间失声。

内部 `PatternAdmissionOwner` 消费上述转换函数：closed prepare/activate、
admission fence 之后才保留 post-enqueue 候选，fence 前、closure 后与 owner-loss
输入保持 live-only。容量耗尽由 journal 在最后一槽原子关闭；fence-wait deadline
在处理下一候选前于 watermark B 关闭；存储失败保留已知前缀并报告不确定后缀。
关闭后的延迟 cutoff 仍可 drain 该前缀一次。drain 走 `commit_admission_transfer`，
并可经 T0 执行端口提交。内部 `PatternTransportCoordinator` 按六格表解析
Play/Stop 与 Record：journal 由 Facade 拥有，只播放从不创建；Record 在无 active
journal 时由 coordinator 懒创建（load Project 取 bars/fingerprint/当前 revision，请求
携带的 expected_revision 不符则拒绝且不建），并兼容骑在显式已开 journal 上的形态；
停止态 Record 用 start 收据激活 admission；播放中 Record 用 fence 且 origin 不变；录音中 Record 关闭准入并保持
播放；录音中 Play/Stop 先停调度再关闭准入。请求校验 session/project；关闭录音时先耐久 cutoff 再 acknowledge 收据。
close 在 ack 之后失败时保持已应用的音频状态，并以 flushing 重试同一 close，
不把 Record-off 报成成功。Record-off 把 pending 或已应用的 Pattern switch 交给 cutoff fence：S ≥ F 取消，
延迟读过 S 也不应用被取消的 Pattern；S < F 先 `retain_admission_switch` 再 cutoff，
journal 保留 `applied_before_cutoff` 与实际 S；先 drain S 之前的源前缀并 flush，
再 `switch_pattern` 推进 `segment_generation`，然后 drain 目标段候选并 flush，最后 close。
cutoff 前未应用 switch 的 close（普通 Play/Stop 双停、Record-off 与 S ≥ F 取消）在同一
close 内把当前 Pattern 段的剩余候选经同一 canonical-tail transfer drain 并 flush 提交
Project Truth、推进 committed revision，并在 closure 耐久后保留 terminal transfer 作为
admission 输入已全部解析的结算收据；cutoff 收据应用后、close 未决期间到达的输入保持
live-only，不再进入候选集。close 中途存储失败保持 flushing 重试且不重复提交。
`Application::make_pattern_transport_controller` 把每个存活 controller 的 session 登记为
该 Project 的已知 Sequence owner：transport journal 打开期间，Sample 类提交保持 legacy
busy 守卫（`sequence_session_active` 类型化拒绝），owner-loss 和解不再误封存活 journal；
直接 legacy `begin_sequence` 只在 transport journal 打开时被拒绝（闲置或已结算的
controller 不阻塞）；controller 销毁即注销登记。owner 消失的未决 transport admission
（controller 未结算即销毁、Host 崩溃）在 recovery 列出时被密封为 owner_lost 并列入
`sequence.recovery.list`；其 apply 以 `sequence_admission_unresolved` 诚实拒绝，discard
正常释放；存活 owner 的 journal 永不被列出操作密封。
结算完整（terminal receipt、tail flush 恰好提交一次、complete）后移除已结算 journal，
与 legacy stop 的 remove_active_if_complete 一致；再次 Record 走同一懒创建路径开新
journal。submit 被 Engine 拒绝（如未命名的 pending publication）发生在任何音频效果之前，
但 admission preparation 已 durable：同身份重试在 generation 未变时幂等复用，
generation 已变则冲突拒绝，未决 journal 留给 owner-loss 恢复面；Host 侧以前置守卫保证
pending publication 应用前不写 journal。收据应用失败若是确定性的
authority/identity 不符（端口不报当前 Pattern 而 engagement 背后的 Pattern 已换；
报告时绑定已在打开 journal 时重锚，见下），重读同一保留收据永不解决，
coordinator 停驻 error phase：continuation 变 no-op、新命令被诚实拒绝（不为 busy），
恢复路径是 Project 重开 + owner-loss recovery listing。
cutoff 前已应用 switch 的 close 保持原语义，尚无 terminal transfer。它仍不是 Creator
opt-in、settings/rebase 或未知 cutoff 恢复。测试用生产
`RealtimeEngine` 收据，不是 Creator 或听感验收。
同一生产转换函数已有 native 进程终止及 Chromium/独立 WebKit OPFS 回应丢失后
重开、精确重试、原 Pattern/实际存在的另一 Pattern 恢复旅程；这些旅程从已知 cutoff
开始，不能替代未知 cutoff 的恢复验收，也不是 Creator、听感或设备验收。
新增时间历史属于 Project I/O 的私有 Sequence v3 journal 元数据，不写 Project Truth。

`pattern_transport_ports.hpp` 提供 staged 的单单元异步执行端口：ticket 绑定
Runtime generation、transport epoch、Command ID 和单调 step；请求与结果 metadata
各有固定上限。重复请求不重新执行，未消费的 immutable completion 占用容量，
异常/不合规结果保留为 `unknown`，不能据此重试副作用。work owner 的创建、执行、
writer lease 释放全部在同一非音频线程，控制侧 submit/inspect 不等待 IO。
shutdown 请求只停止接收新工作；已接收操作继续结算，调用方观察 stopped 后才销毁。
该端口尚未接入全局 transport coordinator，既有 Sequence admission 行为不变。

`pattern_transport_controller.hpp` 把上述 coordinator 包装成 Host 可消费的公开
`facade::PatternTransportController`，由 `make_pattern_transport_controller(audio, config)`
构造，形态与 `make_engine_performance_adapter` 先例一致：Host 只提供实现公开
`facade::PatternTransportAudioPort` 的音频端口（submit/inspect/acknowledge/
pattern_generation/pending_switch/current_pattern，全部只含 Audio Runtime 与
Foundation 类型；`current_pattern` 有默认实现，返回 `std::nullopt` 表示没有
重锚信息），
controller 在 Facade 编译单元内自持 Sequence Journal 与 Project Store，公开签名
不出现任何 Project I/O 类型，因此浏览器 Host 在不越过 Host 源码边界的前提下驱动
transport。`request`/`inspect`/`continue_operation` 都是串行 control lane 短步：
request 只解析一次 toggle 并保留 command/epoch，continuation 由 Host 在自己的
control lane 上重入（无收据时立即成功返回，绝不等待），不得搬到 executor 工作线程；
audio port 与 engine 的 submit/inspect/acknowledge 共享同一 serialized control
owner，音频线程不调用。一个 controller 绑定一个 runtime/session/Pattern；过期
runtime generation 按 stale 拒绝。Pattern 一腿不再是冻结身份：打开新 journal 的
Record 先把绑定重锚到 `current_pattern()` 报告的引擎当前 Pattern（#1403），
playing 状态下已在 Bar 边界应用的 switch 因此不再让 admission fence 与
preparation 错配；端口报告 `std::nullopt`（无当前 Pattern 或端口不知道）时保持
vendored 绑定，下述确定性停机语义不变；journal 活跃（录制中）时永不重锚，跨
switch 的结清仍由上文 `retain_switch`/reconcile/drain 的 close 机制拥有。

自由函数形态的 controller 用默认 storage platform 全新实例自持 Journal/Store；
原生/OPFS 的 bundle writer 锁按 open file description 生效，因此当 Host 已经过
`Application::acquire_project_writer` 持有 lease 时，自由函数 controller 的首次
admission 写入会得到 `project_busy` 拒绝（释放对方 lease 后同一 command identity
可恢复）。真实 Host 形态应改用 `Application::make_pattern_transport_controller(audio,
config)` 成员工厂：controller 的 Journal/Store 共享该 Application 的单一
storage_platform 实例，同实例 writers_ 注册表允许同进程共享 lease，Host 持有的
writer lease 与 transport 录制写入不再互斥；Host 依然只拼 Facade/Audio 类型。

同一公开头还提供候选注入 seam `admit(const PatternTransportCandidate&)`：Host 在
enqueue 接受处给 live input 打上单调 watermark 与 engine rendered_frames，经该
Facade 层类型（watermark/runtime_frame/`domain::PadSlotId`/pressed/velocity/
correlation）进入 prepared admission，依旧不命名任何 Project I/O 类型。correlation
恒有值：press 以自身 watermark 为归属标识，release 复用同一值闭合该 press；无匹配
owned press 的 release 不伪造 press，转换 checkpoint 会无条件解引用所存
correlation。无录音时 admit 失败；pre-fence、closure 后或 owner-lost 输入返回
`live_only`（公开镜像枚举 `facade::PatternAdmissionAdmit`），成功 retained 表示候选
已耐久 append，不代表可听接受。该公开面属于 staged source：C++ 静态库为兼容
追加，C ABI 与 api_version 不变，Module 版本与 Assembly 选择留待后续集成 Build。

依赖全部六个下层 Module；Native/CLI/MCP Host 只依赖本 Facade，浏览器 Host 只依赖封装本 Facade 的 Web Runtime Platform。Performance 协作者由 Host 或 Product Assembly 注入，Facade 只依赖其接口，不依赖任何具体平台实现。

同一 Module 内的 `lmdj::performance_runtime` 静态目标独立拥有
`performance_runtime.cpp`、`performance_replay.cpp`、`performance_engine_adapter.cpp`。
完整的 `lmdj::application` 单向 PUBLIC 链接它，保留旧调用方的链接入口；实现没有在
两个 archive 中重复编译。窄目标通过 Audio Runtime 依赖 Cooker、Authoring Domain
和 Foundation，不链接 Project IO / Provider SDK；这些仍属于完整 Facade 的依赖。
它不是新增的独立 Module；T3 的 `lmdj::runtime_facade` 是另一个同 Module 内的
窄目标，直接链接 Cooker/Audio Runtime，不依赖 Performance、Project IO 或 Provider。
完整 `lmdj::application` 单向链接两个窄目标，保留既有桌面入口。

`performance_ports.hpp` 提供原有 clock、input sequencer、Pattern launch 与 gesture
协作者声明，`application.hpp` 继续包含它，保持原 namespace、签名及配置布局。
`performance_runtime.hpp` / `performance_engine_adapter.hpp` 直接包含 ports 和既有
`performance_replay.hpp`，不再通过完整 `application.hpp` 获得声明。
## 4. 架构与数据流
Host 或 Web Runtime Platform 请求 → Facade → Domain/I/O/Cooker/Runtime/Provider SDK → typed response/stream result。Sequence session/receipt、pending-overlay projection、Sample import token、cache 与 Project writer lease 均由 Facade/Core 拥有；overlay projection 只复制当前内存事件，不扩大 JSON/C API 或持久化 surface。Performance 录制沿同一路径：Host 提交手势 → Facade 用 `PerformanceClock` 定 tick、用 `PerformanceInputSequencer` 定次序 → Project I/O 在 performance session kind 的 journal 上耐久 append → 返回权威 status；replay 则是 Project Truth → `cook_performance_replay` → `PerformanceReplayController` → Runtime sink 的单向派生流。
## 5. API 与 Contract 边界
C++ typed API 与严格 JSON/C API/MCP/CLI parity 保持跨 Host 边界；`sample.quota` 请求恰含 `operation/project_path/slot`，成功结果中的 `project_revision` 必须作为后续 `sample.import.begin.expected_revision`。Bundle/Sample streaming API 不暴露 Project internals；Assembly Loader 校验锁定身份。
## 6. 状态、错误与并发
窄 `RuntimeFacade` 的开发源码增加 `stopped_peak_voices()`，返回当前已停止运行的
实际峰值 voice 数。它只供串行 control caller 使用：`finish_stop()` 的既有
回调 gate 排空且 phase 为 stopped 后才返回值；empty、ready、running、draining
以及 unload/reset 后均不可用。不可用不同于成功测得零。查询不分配、不修改
Runtime 或 Project Truth。下一次 start 重置峰值；Host 若需卸载后保留观测，必须
在卸载前把值与当次内容身份一起复制，不能给旧值附上新内容身份。
该观测没有直接增加 USB/JSON/C API，不能代替 Cardputer 的物理声部与时延验收。
模块版本与 Assembly 选择随后续集成 Build 分配，此处描述未发布的源能力。

当前 source 追加 typed `export_runtime_content(RuntimeContentExportRequest)`：Host
提供绝对 Project 路径、期望 Project ID/revision、一个 Pattern ID、额外 live Pad 列表
及显式 codec limits，只得到不透明字节和完整 SHA-256/byte length identity。
Facade 对一次加载的确定版本取事件 Pad 与 live Pad 的并集，在 detached Project value
上清除无关绑定后 Cook/encode，不写回该选择、不发布 Runtime generation。
重复 live Pad、未分配素材、ID/revision 不符、无效内容或超限均拒绝。

ProjectStore 仍先检查所有 source Asset 的完整性，损坏的未选素材也会使加载失败；
codec limits 不限制此前电脑端 source load/WAV Cook 的内存峰值。
`facade.runtime_content_export` 通过真实 Facade 建 Project/导入/分配验证闭包、来源、
重复身份、重开、损坏拒绝及恢复重试，并逐文件比较 Truth 未被导出改写。
这项导出 API 未增加 CLI/UI 或 JSON/C API；MINOR 与 Assembly lock
在后续 B2 集成分配，新 Contract 尚未代表 desktop Assembly 已选择的能力。

### Runtime-only 生命周期（T3 source）

Cardputer 的 [R1 研究 #1127](https://github.com/endaye/lmdj/pull/1127) 得到负容量
结论：[紧凑存储设计 #1124](https://github.com/endaye/lmdj/issues/1124) 的 M1 source
已让显式队列 storage 随既有 pending 准入额度收敛。
M2 source 已让窄 Runtime 的 live Pad 与 Pattern 共享 decoded PCM16，完整 float
展开不再存在；桌面通用 Bank/codec 路径不变。Engine/Bank 布局是待后续 MAJOR
身份分配的 staged source，不分配 Product Build。设计 Closed、native
测试通过或修复合并都不能解除设备容量门槛，必须取得同口径的正向目标证据。

`runtime_facade.hpp` 只暴露不透明字节、完整内容身份、资源配置、进程内 opaque
epoch、Pad 命令、回执和只读 Pad 摘要，不暴露 Snapshot、Engine、Project 路径或 Provider 对象。
一个串行控制调用方负责 `load/start/submit/poll/request_stop/finish_stop/stop/unload/reset`；
一个音频调用方调用 `render`。生命周期为 empty → ready → running → draining →
stopped → empty；stopped 也可重启同一内容，running/draining 不接受 load/unload。
替换使用 stop → unload → load；坏内容、预算或分配失败不会发布半成品，保持 empty
并允许正确内容重试。`reset` 先停再卸载，不重置 epoch 耗尽计数。
`content_identity` 返回 Core 保存的完整 SHA-256/byte length 副本，成功 load 才存在，
卸载/reset 后为空；不是 Host 对最近一次请求的预测。该控制侧值复制可分配内存。

`content_summary()` 返回 Facade 自有的 `RuntimeContentSummary` 值副本：固定容量
64 个 Pad，按 bank/pad 的 canonical 次序排列，含各自 trigger mode 和有效 count；
未使用项清零。查询不分配内存、不借出 Snapshot 存储，仍属于串行控制侧。
empty、失败 load、unload/reset 后 count 为零；running/stopped 保留当前已发布内容。
这是兼容的 staged API 增量，Module 版本与 Assembly 的分配留给后续集成 Task。
Cardputer Host 用摘要映射实际 Pad Slots 并在自身边界拒绝非 One Shot 或超出
显式 Host profile 的内容；Core 摘要不裁成四 Pad，也不决定产品 profile。

每次成功 start 产生独立 epoch；命令必须带当前 epoch 和从 1 开始的精确下一序号。
旧 epoch、重复、跳号、非法命令与计数耗尽明确拒绝，既不重放也不绕回。
`accepted` 只表示已入队，`poll` 才报告 render 消费后的 applied、voice_started、
voice_capacity，或停止时未消费的 cancelled。applied 不等于可听声音：mute、release
和 stop 命令可能无新 Voice。队列/待取回执额度满不消耗序号，原命令可重试；回执
有界且按序只取一次，未取回执跨 unload/reset 保留，新 start 必须先取完。
opaque epoch 不是持久化或设备传输协议，跨 Facade 实例也不能复用。

Facade 用同一个 lock-free atomic32 的 OPEN/BUSY 位关闭回调 admission 并观察活跃
Core render 退出；`finish_stop` 在 BUSY 清除前只返回 draining，不调用 Engine stop
或回收内存。`stop` 在控制线程等待这个屏障；回调不等待，关闭或重入时输出静音。
Host 仍须负责自己的设备/DMA 回调生命周期，并在析构 Facade 前停止再次调用 render。

load 在分配 PCM 前复用完整内容校验，报告固定对象（含 Engine 与三个独立队列 cell block）、借入 encoded
bytes、去重 PCM、metadata 和准备临时空间，溢出或超总额度拒绝。
窄路径 `prepared_float_bytes` 为 0；codec 通用 footprint 仍报告其他消费者的
per-Pad float 需求。Bank owner table 包含在实际 `sizeof(PreparedSampleBank)` 中；
准备空间保留 Pattern event workspace、Bank/View 对象与解码重叠，只移除已消失的
largest-float 临时副本。现有 Snapshot 和 Pattern 的 PCM ownership 仍保留，不把
共享 owner 当作又一份 PCM，也不把移除 float 副本误报成移除 PCM。
配置还必须显式提供 platform reserve，覆盖 allocator/control-block/capacity rounding、
平台 stack、Host buffers 等；数值必须由平台测量，不是 Core 推断的可用 RAM。
完整校验与预算通过后，先构造候选 Engine 及其固定队列，再分配解码 PCM 与准备数据，
避免变量存储先切碎大块空闲区。所有候选仍在控制线程局部持有，全部准备成功才提交；
后续分配失败会完整回收并保持 empty/静音/可重试。总量 admission 不保证任意碎片化
平台都有足够大的连续块，实际分配失败仍返回 allocation_failed。
已取走并由 Host 保留的历史 epoch/回执内存属于 Host。此入口不准备 Master FX 动态
缓冲，不提供 FX 命令；资源报告不是 ESP32 map/stack/heap、DMA 或实时性能验收。

Runtime-only 将 `maximum_pending_commands` 的 N（1..1024）传入显式 Engine profile，
控制/结果容量各为 N，Voice-state 容量为 `2 × N + 128`；桌面默认和旧无参数
receipt-bounded 构造组合不变。每条 accepted 命令直到回执取走才释放名额；
`poll` 必须先 acquire 消费位置，再 drain 事件，最后取回执，从而把未读状态限制为
`2 × N + 128`（命令的
started/terminal 加既有 Voice 的 terminal）。空/部分回执 span 也保持该顺序。
128 Voice、完整事件、命令结果和 stop/drain/unload/reset 语义不变。三个独立 block
在 load 构造 Engine 时分配，各自包含一个 sentinel cell，全部计入 fixed_bytes；
Engine 内索引和 owner wrapper 不重复计费，分配器额外开销仍由 platform reserve 承担。
N=1/128/1024 的实际分配账本与预算差值均有断言，不是把占用移出 sizeof 后省略。
每个分配失败位置的完整回收、empty/静音/重试以及满额并发回执由组件和 stress 测试覆盖。

错误翻译保留公共类别与配额详情；查询和 Sample commit 共用 Audio Runtime 的 overflow-checked Bank/generation 账本，较小的 remaining 约束生效、相等时 Bank 优先。提交恰好允许 effective remaining frames，超一 mono frame 确定性返回 `BANK_QUOTA_EXHAUSTED` 或 `PROJECT_QUOTA_EXHAUSTED`；revision 漂移先返回 `REVISION_CONFLICT`，拒绝不会修改 Project Truth 或已发布 generation。Runtime Snapshot 准备复用同一账本，publication residency 仍是独立瞬态 Host/Attempt 状态。本地 Sequence mutex 只负责进程内 admission 排序，Project I/O 仍在 writer lease 内重判持久 authority；C API stress 验证并发生命周期。

窄消费者 `facade.performance_runtime_consumer` 包含四个 runtime/port 头文件，只链接
`lmdj::performance_runtime`，并调用三份实现的 factory；编译时拒绝泄漏的 Project IO /
Provider SDK include roots。现有 bridge/adapter 测试也使用窄目标，完整 Application、
Replay、Sequence 与 C API 消费者保留旧目标，验证单向传递链接兼容。
这项隔离只解决现有 Performance 的依赖组合：下层 archive 仍可能包含 offline 或文件
路径，engine adapter 仍暴露 Core 类型；单凭这项隔离不得宣称 wire Contract、设备
admission、无文件系统闭包、资源预算或 ESP32 编译已经实现。另行实现的 T2 内容

admission/lifecycle，但 T4 exact-revision ESP-IDF 完整闭包和静态预算探针、T5 真机
仍未由这些测试完成。

`facade.runtime_facade` 链接生产窄目标，覆盖完整生命周期、每个 load 分配点的失败

## 10. 版本身份
版本和完整依赖集由模块清单与 Product Assembly 固定。

## Provider owner API

`provider.run` 可追加 `input_owners`，每个输入恰有一个
`{port, occurrence, project_path, project_id, asset_id}`。Facade 在 SDK 完成权限、
绑定和预算门禁后才调用 Project I/O 的 verified owner read；未提供 owner 的输入仍以
`NOT_FOUND/input_artifact_unavailable` 形成失败 Attempt。读取的副本进入 SDK source，
Project 路径不会进入 Provider 参数或 terminal，且不创建持久 owner 索引。

`provider.permissions.configure` 接受严格的 `granted_permissions` 数组，替换当前
Application 会话的 grant。未知或重复权限拒绝且不改变旧策略；区域和分类保持原值。
重建 AttemptStore 保留已选择 Provider 和耐久 Attempt，重启不保留显式 grant。
它是可信 Host settings API，不是多租户鉴权边界。

`facade.provider_owner` 与 `host.provider_owner` 覆盖真实导入、输入读取、完整输出
identity、失败终态和重启；无 owner、错误身份、损坏及 busy 不修改 Project Truth。

## Workspace Slice Candidate Jobs

`candidate.job.run` 接受显式 Job/新 Attempt ID、source Project/Asset、
`expected_revision`、参数与执行策略。Facade 读取并绑定完整 source Artifact 与原始
revision。先通过 SDK selection/policy 预检，再以不触发恢复清理的 committed inspection
读取绑定；SDK 原子取得 Attempt reservation 后，回调耐久保存 intent 和预分配 Set ID，
最后调用已注册的 `sample.slice.v1`。普通 Provider 调用无法抢占这个 reservation，
重复 ID 的拒绝不会把别人的 terminal 发布到 Job。
`candidate.job.inspect` 返回有序 history、active Set 及其稳定 interval recipe IDs。
这些记录只属于 Workspace，不写入 Project Truth，也不增加 SDK terminal Candidate 数量。

成功终端的 slice points 经 SDK 校验输出字节、Facade 校验 source/参数/执行上下文后展开：
无 onset 为成功的空 Set；否则使用去重的 0、onset、EOF 边界生成所有非空相邻区间。
新 Set、active pointer、history 与旧 Set supersession 在一次 owner-state replacement
中发布。失败重试保留旧 active Set。每次查询重新核对终端和输出完整身份；损坏、篡改
配方或不一致状态会拒绝，不能用持久索引绕过验证。

每个 Job 的执行 lease 跨越 Provider run；短 Workspace mutation lease 串行化发布。
同 Job 并发执行以 `INVALID_ARGUMENT/job_busy` 拒绝。恢复只检查已记录 Attempt，
不扫描 blob：成功终端可发布一次，缺失终端记为 interrupted，显式重试必须用新 ID。
进程内互斥补足 storage writer 的可重入语义，跨进程使用既有平台 writer lease。

`facade.candidate_job` 验证真实 Slice Provider、区间、空结果、失败重试、重启及损坏拒绝；
`facade.candidate_store_recovery` 在独立进程退出后检查 intent/terminal/publication
三个边界，并验证 live Job 不会被误恢复或重入。全部拒绝路径保持 Project 文件不变。
采纳与持久谱系已接入下述原子命令；取消/丢弃具备持久生命周期，Host preview 由后续 L5 完成。

## Explicit Candidate adoption

`candidate.adopt` is a command with exactly `project_path`, `project_id`,
`expected_revision`, `command_id`, `job_id`, `set_id` and `selections` in addition
to `operation`. Each selection contains exactly `candidate_id`, `bank` (0–3),
and `pad` (0–15). The list must be nonempty, all recipes must belong to the one
active set, and targets must be unique. Targets sort by Bank/Pad before deterministic
Asset ID allocation. The same recipe on two Pads creates two Assets and incurs
two prepared-PCM charges; its materialized byte buffer can be shared transiently.

The Workspace mutation lease remains held across source verification,
materialization, complete final-binding quota preflight and the Project commit.
Project ID, current revision and source Asset/full ArtifactRef are checked before
materialization and under the Project writer. A relocated Project remains eligible
by identity; an unrelated edit requires the caller's current revision but retains
the original analysis revision in lineage. Every affected Bank and the whole
generation are checked after removing all replaced target charges. Runtime resident
publication limits remain a separate boundary.

Success persists exactly one revision, independent PCM16 WAV artifacts and closed
terminal-authoritative lineage, retaining the source Asset and bytes. Failure before
manifest publication changes no Project/Pad/Asset state. Adoption writes no Candidate
Index status and does not consume the set. An old-revision repeat is a conflict even
when its command receipt exists; a newly confirmed adoption uses the current revision
and a fresh command ID. There is no public idempotent replay promise: inspect the
Project after an unknown commit response before deciding to adopt again.

`candidate_adoption_test.cpp` exercises terminal-to-commit/reopen, identity and quota
refusals, source changes, storage failures and eligibility ownership.
The independent-process lifecycle suite verifies both ownership orders against
actual adoption, with committed artifacts and lineage checked after reopen.

## Candidate cancellation and discard

`candidate.job.cancel` requires exactly `job_id` and `attempt_id` in addition to
`operation`. It durably cancels that exact pending Attempt; repeating the same
cancellation succeeds. A completed succeeded/failed Attempt refuses with
`INVALID_ARGUMENT/job_already_completed`. Cancellation records an owner decision;
the Provider may still complete and retain its immutable terminal, but that
cancelled Attempt never publishes a set. Its live execution lease continues to
exclude a simultaneous retry until execution ends. A failed or cancelled retry
preserves the prior active set.

`candidate.set.discard` requires exactly `job_id` and `set_id`. It accepts only
the current active set and writes its discarded tombstone plus a null active
pointer in one durable replacement. Old terminal bytes, history and blobs remain;
there is no GC or automatic TTL. Discard can persist even when output bytes are
unavailable, while inspection/adoption continues to refuse unverifiable evidence.

Lifecycle publication and adoption share Workspace mutation ownership. If discard
or successful supersession wins first, old-set adoption refuses with
`NOT_FOUND/candidate_unavailable`. If adoption wins, competing discard/publication
refuses with `INVALID_ARGUMENT/job_busy` until the Project commit finishes. A
successful retry terminal delayed at that boundary remains pending and recovers
once; a cancelled terminal never replaces the active set. After adoption commits,
discard changes Workspace state without altering the adopted Project. Failed
Project publication releases eligibility and permits a later durable discard.

`facade.candidate_store_recovery` checks interruption before/after lifecycle
replacement, terminal retention, restart and the actual adoption interleavings.
`facade.candidate_store_stress` repeats synchronized independent-process ownership,
cancel, discard and retry/adoption cases 100 times. The test fence releases the
real Project input-reader lease before pausing the Provider, preserving the lock
behavior exercised by the product. Every completed adoption is reopened with its
full Artifact identity, retained source and terminal-derived lineage.

## Candidate audition

`Application::audition_candidate` 和只读 `candidate.audition` 验证 active Set、
terminal/output 字节、完整 source binding 与当前 expected revision，在 Workspace
eligibility 持有期间选择有界 PCM16 区间并准备 48 kHz PCM。返回独立的
`CandidateAuditionAudio`，其 Artifact/原采样率/帧数描述所选区间；准备完成后
再次验证源字节与 revision。查询不执行 Project recovery，不写文件、Asset、Pad
或 revision。CLI/MCP 只用元数据；Native/Web 把类型化 PCM 交给自己的试听池，
`played` 与停止属于 Host。源过期、丢弃、替换或损坏时拒绝且不改变 Project。
