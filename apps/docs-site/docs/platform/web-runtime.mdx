## 当前组成

Web Runtime Lab 继续作为独立实验与物理证据准备器，不在 Product Assembly。正式产品路径由 Web Runtime Platform、Diagnostic Web Runtime Host 与 Creator Web Host 组成，当前 Module/Host/Product 身份以上方清单投影为准。共享 Runtime Session 桥接 revision-bound Sample quota、manifest-bound Sample import total、多 chunk sidecar、Sequence recording、settings、next-Bar switch、receipt 与 recovery；Stage 10 起还桥接 Perform master tap 的 capture 状态与录制批次。Host 只呈现 authority state。

## 共享 Platform

加载同一 packaged Runtime 的 Session 会在保留的
`window.lmdjWebRuntimeHost` 上暴露冻结的 `inspection` namespace：
`inspectProject()` 和 `inspectSample(flatSlot)` 直接调用该 Session 的现有方法。
普通 Project Truth / Sample 读取与 UI 的恢复查询共用请求队列，不创建第二个
Session，也不绕过该队列直接发送 transport 请求。Project 返回完整 Facade
投影；Sample 的 slot 为 0–63，返回 `projectRevision`、`assetId`、`playback`
（包括 `triggerMode`、`pan`、`tone`）、metadata 和 waveform cache identity，
不包装成原始 `ok` / `result` envelope。读取保持现有校验、预算、取消/重读和
类型化失败。显式关闭中的或已关闭的 owner 拒绝保留的读取闭包；新 Session
发布自己的 namespace，旧闭包不能借用新 owner。native fatal transport 的
`HOST_TIMEOUT` / `HOST_PROTOCOL_MISMATCH` 保持原失败，不改成关闭拒绝。
原始 transport 仍供明确的协议、并发、触发/停止与 owner 故障证明使用；这些
低层证明不由普通 inspection namespace 替代。

两个 Host 使用同一 Runtime Session、input adapters、Control bridge、OPFS capability gate、Application Facade 与 AudioWorklet 接线。Pointer、Keyboard、MIDI 在共享 Audio Runtime frame clock 上取得时间戳并按 `input_sequence` 串行；BPM anchor 和 Bar boundary 来自 Core，JavaScript 不实现 quantizer、fingerprint 或 fallback sequencer。Project 路径只由 retained current Project 注入，Browser payload 不得携带 `project_path`。`project.duplicate` 只携带 `source_project_id`/`project_id`，在 Workspace 内按新身份发布源 Project 的副本，不改变当前打开的 Project；OPFS 上它与 Bundle import 走同一 copy → verify → commit 目录发布。全局 Pattern transport 由 session 显式 opt-in：`createRuntimeSession` 的 `patternTransport: true` 使 `project.open` 与 `project.create` 携带 `pattern_transport: true` 协商标记，`requestPatternTransport`/`inspectPatternTransport` 分别对应 Host 操作 `pattern.transport.request`/`pattern.transport.inspect`；request 返回 pending ticket 即释放 Promise tail，settlement 由 Control 侧 continuation cadence 推进并经 inspect 观察，未协商或未启用的 session 得到类型化拒绝，legacy Sequence 操作保持默认。跨身份 `snapshot.reload` 在 engagement 存活时与之协调：播放中拒绝，其余情况结算并注销后重新 engaged；Engine stop 抹除 transport generation，每次 activation 重新武装，epoch 随新 generation 从 1 重启。playing 状态下已在 Bar 边界应用的 Pattern switch 不再使 engagement 失效：Host 端口报告引擎当前 Pattern，下一次 Record 由 Facade 协调器重锚绑定后直接提交到当前 Pattern（#1403）。

播放中的全局 transport 切换 Pattern（#1958）由 `requestTransportPatternSwitch({patternId, requestId, snap?})` 对应 Host 操作 `pattern.transport.switch`，wire payload 可带 `snap: "beat" | "bar" | "pattern_end"`，省略时保持默认 `"bar"`。旧 Pattern 播到引擎为该 SNAP 推导的下一拍、下一小节或整个 Pattern 结束边界，新 Pattern 从开头开始，响应返回 `{patternId, activationFrame}`。时间由 native reservation-bound switch API 和实际 playing Pattern geometry 推导，Host 不用墙钟猜测。边界之前再次请求时以最新为准：未认领的排队以记住的 authority 取代；音频线程已认领的不再被覆盖，后来的目标在已认领 Pattern 的新 timeline 上按所请求的 SNAP 顺延。已认领 B 与排队 C 可同时由引擎拥有，Host 端口提供 strong observation，使 Stop 精确命名两项 authority；C 不依赖 Host tick 才发布。再按正在播放的 Pattern 即取消待切换，响应 `activationFrame: null`；Stop 在边界前取消待切换且当前 Pattern 不变。切换生效后 Host 的选中 Pattern 与 engagement 绑定跟随引擎当前 Pattern，后续 Record-off、Play 与重发布都以新 Pattern 为准；录音中（`pattern_transport_recording`）、transport 命令在途（`pattern_transport_busy`）、已停止（`pattern_transport_not_playing`）与无 engagement 的请求被拒绝，停止状态的选择仍走 `snapshot.reload`。显式 opt-in 全局 Pattern transport 后，audio 运行但 transport 已停止（或尚未开始）时，reload 的 Pattern view 使用立即发布，随下一次音频回调生效；连续 A → B → A 不会留下等到 Bar 才应用的 B，使下一次 Play 播放所选 A。legacy playback 的发布策略保持原有语义；播放中切换选择 native SEQ SNAP 边界，省略 snap 时仍为 1 BAR。切换仍在排队时，会重发布当前 Pattern 或另起 Pattern view 的操作在提交任何 Truth 之前即被拒绝并返回原因 `pattern_switch_pending`（提示切换落地后重试）：带 `bpm` 的 `sequence.settings.update`、播放中的 `pattern.events.edit`、播放中带 Record 意图的 `pattern.transport.request` 与 `performance.replay.begin`；仅 Swing/Quantize 的设置更新与 Stop（`play_stop`，在 cutoff 取消排队）不受影响。`pattern.transport.inspect` 相应新增 `current_pattern_id` 与 `pending_switch {pattern_id, activation_frame} | null`，映射为 status 的 `currentPatternId` 与 `pendingSwitch`。

Perform 的 master tap 由 Platform 自有：`performance_master_tap_worklet.js` 注册 `lmdj-perform-master-tap` processor，只接受同源 module URL。建立 AudioContext 时，若 manifest 同时给出两个正整数 Perform 上限且 tap URL 同源，Platform 先创建 tap 节点并把它注册为 Core AudioWorklet 的输出目的地，再由 tap 连往 Platform 的监听 gain，gain 才连接 `AudioContext.destination`；product 输出经过 master 总线上的同一个节点；S6 additive cue output 独立接到下游 monitor gain，Host 不另建音频图。capture 状态由 Runtime Session 通过 `subscribePerformanceMasterCaptureStatus` 发布，取值为 `unconfigured`（缺少上限或同源 tap URL）→ `configured`（tap 配置成立）→ `ready`（tap 与 AudioWorklet 均已启动），另有一个失败态；只有 `ready` 允许开始一次 capture。capture 通道上的每条消息都按精确 key 校验：`batch` 携带等长的双声道 `Float32Array`，单批不超过 4,800 帧，且 `sequence` 必须正好是上一批加一；`stopped` 只在已请求停止且 `finalSequence` 等于最后一批时被接受；`failed` 只接受 `post-message-failed` 原因并报告 `droppedFrames`；generation 不符的消息被忽略，其余任何形状都终止该次 capture。stop 确认使用 30 秒有界预算。tap 的 `processorerror` 一律 fail closed 为不可用 capture：Platform 先停止进行中的 capture，再把 Core AudioWorklet 接回同一个监听 gain 以保住实时音频及监听音量，接不回时以类型化 `HOST_STATE_INVALID` 终止会话，而不是静默降级。W1 起 tap 握手加入应用层 `started` ACK：start 消息携带 `{generation, binding}`（binding 为 `{control_epoch, session_id, begin_command_id}` 或 null），processor 实际应用 start 后、下个 process 前回同形状 `started`；capture controller 在发送前占有唯一 pending start，start promise 仅在严格匹配的 ACK 后 resolve 并返回不可变 receipt，错 binding/额外字段/重复 started/提前 batch 均以协议失败拒绝并走有界 stop 清理，旧 generation 的迟到 ACK 不复用，start ACK 复用既有 30 秒预算作独立计时器。headered 录制（`controlEpoch` 选择新 profile）的 begin promise 在 Core fence `coreControlReady` 与该 ACK 双 ready 前保持 pending，暂存录制输入零投递；SDK 的 Runtime action 通道为有界窗口（1 inflight + 1 普通 waiting + 每 open Pad 一条 release 位置至多 64 + 1 cleanup token），超额明确拒绝、不合并控制值、不丢 release，cleanup 显式 reject 未 admitted 输入。

Pattern 改长度与复制（#1823）经 `resizePattern`、`doubleUpPattern`、`copyPattern` 映射为 Host 操作 `pattern.resize`、`pattern.double`、`pattern.copy`，每次调用各自生成 `command_id`。Control 在提交前拒绝录音中（`sequence_session_active`）、transport 命令在途（`pattern_transport_busy`）与播放中（`pattern_transport_playing`）的请求，Truth 不变；停止时改的若是 Runtime 当前 Pattern，提交后立即重新发布 Pattern view，下一次 Play 按新长度循环；复制或改其他 Pattern 只提交、不发布。

Host preflight 的单次 Control Worker capability probe 使用 15 秒有界预算。CPU 或文件 I/O contention 可以推迟结果，但不能被解释成 OPFS primitive 缺失；明确 primitive 缺失、actual negative 或 Worker error 仍 fail closed 为 `UNSUPPORTED_WEB_RUNTIME`，deadline expiry 则为 `HOST_TIMEOUT`。无论 settle 原因如何，临时 Worker 与 Blob URL 都由 probe owner 清理。

Project I/O 的三个文件 mutation primitive（`append_durable`、`replace_complete`、`create_immutable`）都要求目标 Project 的有效 writer lease，且 lease 必须属于发起调用的同一 `ProjectStoragePlatform`；无覆盖 lease 时以 `IO_ERROR` + `storage_condition=invalid_state` 失败，不同 same-page platform 试图复用 owner lease 时以 `IO_ERROR` + `storage_condition=project_busy` 在打开 target 或 intent 前失败。Web OPFS 还把 `QuotaExceededError` 与 `InvalidStateError` 保留为 `quota_exceeded` / `invalid_state` 类型化条件，而不是丢失为空 details。


监听输出属于 Session/Host 状态，位于 master capture 下游。`monitorVolume()` 返回 0–100 的百分比，`setMonitorVolume(value)` 在未激活时先记录值，创建音频图时先应用；运行中用 20 ms ramp 调整线性 gain。`monitorDestination()` 在图未建立或会话终止时返回 `null`，其余时候返回同一监听节点，供 Host 的非录制声音接入。正常 master tap、tap 初始化失败和 processorerror 恢复路径均经过这个节点。录制批次、Project Truth、authoring history 与导出电平不受监听音量影响；关闭时断开节点并拒绝后续设置。设备记忆由 Host 实现。

## 分发与服务

独立音频实验台位于 `demos/web-runtime-lab/`，不依赖 Core 或 Product Assembly，
继续通过 `scripts/web-runtime-lab.sh` 单独运行与验证。它不是
`apps/web-runtime-host/` 诊断 Host，迁移不改变后者的 Cloudflare 部署路径。

两个 Host 都生成 canonical manifest 与内容哈希资产；固定 Emscripten `6.0.5`、512 MiB heap、协议仍为 `1`，以及九个精确资源上限：64 MiB/Bank、128 MiB/generation、256 MiB publication residency、100 MiB source、43,200,000 decoded frames、2 channels、65 MiB committed WAV，以及 Stage 10 新增的 `perform_recording_frames` 86,400,000 帧（48 kHz 下三十分钟）与 `perform_recording_queue_batches` 32。`decoded_frames_per_pad` 已退役。两份分发清单的资产集合不同：Creator Web 的 distribution contract 声明六项——`host_main`、`runtime_script`、`runtime_wasm`、`host_style`、`capture_worklet` 与新增的 `perform_master_tap_worklet`（`assets/perform-master-tap.*.js`），并声明兼容 Host `web-runtime-host 3.0.0`；Diagnostic Host 保持十五项且明确不声明 tap 资产。manifest gate 逐个校验两个新上限为正的安全整数且值精确，拒绝多余默认项、重复角色、错误前后缀、digest 不符，以及主包 URL 未落到精确 hash 资产的情况；更早的不可变包保留各自的精确身份，不被回溯要求携带 Stage 10 字段。proof-only server 在 bind 前验证完整 dist，并固定 COOP/COEP/CORP/CSP、MIME、cache、no-follow 与每请求 hash；它不是生产部署服务。CSP 按 manifest 的 `host_id` 选择：Creator 额外允许 `font-src data:`（内联的控制台字体，Desktop Final 计划 T1b），Web Runtime Host 不变；部署 smoke 两条都接受。

## 线程与生命周期

Engine 的 64 位 telemetry 值由固定三缓冲发布，观察者 mutex 仅供非实时读取。AudioWorklet 在 render 后通过内部 audio-owner accessor 读取 current Bank generation 和 Voice-stream health，以维持精确 generation acknowledgement 与 fail-closed 行为；callback 不调用 telemetry，也不获取观察者 mutex。此内部访问不扩大 Host 的 Application Facade 边界，生命周期仍要求 callback quiescence。

主线程负责 UI、用户手势和生命周期观察；Dedicated Worker/Control 串行驱动 Facade 与音频控制；S6 transport 的 Store/Journal/leases 在 Facade 自有单一 I/O worker 创建、执行、析构，其他 Project 操作仍走既有 owner；AudioWorklet 处理实时音频。消息、sidecar、queue 与 timeout 均有界。Project open/import 与 Sample mutation 共用可恢复 action tail；每次 Pad press 的 inspect→trigger admission 串行，避免并发 Facade query 进入同一 native owner，同时不会形成 inspect backlog。adverse lifecycle 会取消可安全重试的纯读请求，使 preview clear 与 `sample.stop(all)` 不被长查询阻塞；已提交 mutation 的 Project/Runtime 分离结果仍由后续权威 refresh 收敛，不重放 mutation。

运行中的显式 `snapshot.reload`/retry，以及 `sample.import.commit`、`sample.update_pad`、`sample.reset_pad` 触发的自动 Bank publication，只有在 AudioWorklet 精确确认其新 Bank generation 后才报告 Runtime publication 成功；旧的非零 acknowledgement 不构成成功。Sample mutation 若已提交 Project Truth，但 acknowledgement 超时，则仍返回已提交的 revision，同时以 `runtime_published=false` 和类型化 `snapshot_error` 表达 Runtime fail-closed，绝不把它误报成可回滚的 Project 失败；deadline 若在 Project commit 后、Runtime publication 前到期，同样 seal 运行中的 Runtime 并保留已提交 Project revision。首次 AudioWorklet bootstrap 完成后，Browser Main 在 callback baseline 与 `AudioContext.resume()` 边缘只为输出设备启动建立 5 秒上限：从 resume edge 到首个 AudioWorklet 回调是浏览器与设备的工作，不是 Runtime 的工作，不计入 Control 预算（2026-10-01 决策，#1704）。在用户手势内新建的 AudioContext 一经创建即为 running，Platform 先将其 suspend，Core 与 master tap 两个 AudioWorklet module 都在这个 parked context 上加载：Chromium 会在 module 就绪时重启 running destination，而这第二次输出设备启动恰好落在 activation 预算内，蓝牙输出的冷启动单次即可耗去其大半（#1696）。parked bootstrap 使输出设备只在 resume edge 启动一次。lock-free paused-callback heartbeat 前进后，Browser Main 才建立一秒 activation deadline 并以此请求 Control 开 gate；bootstrap 同样不消耗该预算。显式激活中，`resume()` 在上限内未 settle（浏览器尚未允许 context 启动时会一直 pending），或设备在上限内未回调，此时都尚未向 Control 提交任何请求：Platform 把 context 重新挂起（对仍 pending 的 resume 也以 `suspend()` 撤回），Session 保持 `audio-suspended`，并在 diagnostics 的 `activation_refusal` 记为 `audio_output_start_timeout`，下一次手势可直接重试，不再进入 `restart-required`。自动恢复沿用同一设备上限与回调后的一秒预算，但 Control 已先行 park，设备仍未回调时照旧 fail closed。Bridge 将 operation cutoff 与 caller cutoff 的较早者作为 absolute effective deadline 直接交给 Control，Control 不从 `submitted_at` 重建完整 operation window。Project mutation 若在 cutoff 前原子赢得 publication claim，则仅保留到 commit/abort 结算的 authority；未 claim 工作及其后的 Runtime-derived publication/acknowledgement 仍受 absolute cutoff 约束。Control 锁存已验证的 current generation，由首个 open-gate callback 确认同一 generation。timeout 或跨代 acknowledgement 会 fail closed，不增加 timeout，也不在 realtime callback 加锁、分配或调用 Host。

`pad.colour.set` 只改变 Pad 颜色 override，不改变音频：Control 在 Pattern transport 播放时照常提交、录制或 transport 命令未结算时于提交前拒绝，且不 prepare、不发布任何 Bank 或 Pattern 视图，提交前已 current 的 Runtime 在提交后仍为 current。每个 Pad 的有效颜色只由 Core 解析并经 `project.inspect` 投影，Host 与 Session 不重新计算（#1207）。

AudioWorklet 的 terminal quiescence 在首个 caller budget 超时并锁存 fatal 后，只再等待一个同长度的 terminal budget；callback 仍未退出时返回类型化 `INTERNAL_ERROR`，不再无限 futex 等待。Transport 收到无法关联到 pending request 的未知或重复 response 时会原子 fail closed：仅终止一次、以 `HOST_PROTOCOL_MISMATCH` 拒绝其余 pending request，并清空 pending/active identity。真实 Chromium Browser Main conformance 会在 unknown response 进入 scheduled production poll 前保持另一个 production request pending，并直接观察该 promise 被同一 terminal error 拒绝且 ID 清除。Manifest mismatch、publication outcome unknown、Voice ring overflow、终止与重启恢复同样 fail closed；`HOST_RESTART_REQUIRED` 不得被页面重试掩盖。

S6 的异常退场路径分别保留原始操作失败与实际物理释放证据。Worklet 封闭新回调资源访问后，Control 仍须等已进入回调的 Engine/cue 消费与最后使用完成，才能实际 stop、撤销 held owner 或回收 Pattern/material；terminal gate、超时和 Native stop 均不代替 caller consume。正常 transport 失败后，已有 input/count-in 身份通过可选的 `sendRetained` 短查询继续结算，正常新请求保持封闭，未知已提交 count-in 不重放。原始 deadline 与 envelope 不变；`pending: false` 只证明当前新 RPC 未被接纳。

Worker owner 释放还要求原 Native、cue、caller、input、I/O 和 Bridge 响应释放回调全部结算，并在移交前封闭最后的 RPC admission。Browser 只接受 authenticated consume-release 的实际返回值 1；五秒 timer 仅重试原请求，channel failure 或返回 0 不能终止 owner。最后的 callback 使用结束也不等于后台节点或 AudioContext 已销毁；正式退场拒绝、后台关闭拒绝和未实际到达 `closed` 都保留失败。此源码草稿仍需当前构建的真实回调与端到端验证，不扩展任何已有 Product Build 的验收证据。

Runtime Session 是 input 与 terminal cleanup 的唯一 owner。每个终止或 replacement
generation 都必须释放 Worker/transport、MIDI listeners、BroadcastChannel、AudioContext
和 window lifecycle listeners；新 generation 不得在旧 generation 仍持有这些资源时
成为 owner。persisted page lifecycle 保留共享 Runtime，non-persisted terminal
pagehide 才进入 close。

替代实例还须取得同一旧 Session 的
`waitForTerminalCleanup(): Promise<boolean>` 正向结果。它仅观察已经发起的
清理；caller 的原始消费、Native full-owner、AudioContext 真实关闭以及 SDK
监听器/节点退出全部完成才允许 true。close 的 false/fatal 结果仍保留，
sealed、计时结束、清理拒绝或未知 owner 均不授予替换资格。Host 不能把
观察变成第二个清理 owner。加载中的部分 Host 由创建它的原 Module 配置
在发布前登记，不能借用其他实例的全局对象。默认 packaged 加载在同一窗口
拒绝重叠 Module 注入；原调用结束只释放加载保留，不证明物理释放。
当前源码修复仍需原 packaged 生命周期旅程验证。
