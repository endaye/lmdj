## 权威内容

`lmdj.soundset.v1 · 1.1.0` 是一个 Sound Set 的清单：`set_id`、`version`、`name`、
`publisher`、`license` 与 `slots` 必填，`description`、`bpm`、`key` 与 `demo` 可选。
`slots` 恰好覆盖一个 Bank 的 16 个槽位地址，每个槽位要么只带 `slot`（空槽），要么另
带 `role`、`name` 与内容寻址的 `artifact`；`role` 是封闭枚举。清单本身是内容寻址的：
Catalog 与 Set Store 都以其规范化字节的 SHA-256 指认它。

`1.1.0` 相对 `1.0.0` 只追加可选的 `demo` Artifact——一整个 Set 的试听素材，与槽位
Artifact 同为 `artifact_ref`，因此可以复用某个槽位已有的哈希；这是向后兼容的追加。

## 与 Project Truth 的关系

Set 不是 Project Truth。安装把槽位内容写成普通 Asset 与普通 Pad 指派，来源记录在既有
的 Asset Lineage 载体上：`source.kind = soundset` 携带 `set_id`、`set_version`、
`manifest_sha256`、`slot_index` 与 `artifact_sha256`，`derivation.kind =
soundset_install` 不带负载。安装之后再编辑 Pad 是普通的创作动作，Set Store 的字节不
随之改变。Catalog endpoint、缓存与 Set Store 是 Workspace/Host 状态，永不进入 Project
Truth。

## 安全与发布

清单在成为可见的 Set 之前完整校验：Contract 形状、每个 Artifact 的哈希、`license` 的
SPDX 允许清单与署名要求，以及四项 Host 容量上限——单个清单对象、单个 Artifact blob、
一个 Set 去重后的总量，以及整个暂存区。任何一项不通过，该 Set 都不会变为可见，也不会
产生任何分配或下载。哈希不符的字节以 `soundset_content_mismatch` 上报，不会退化为静默
重试。

## 使用方与证据

Application Facade 暴露 `soundset.catalog.list`、`soundset.inspect`、
`soundset.map.preview`、`soundset.install` 与 `soundset.audition`。前四个在五个 Host
上都**已注册**；`soundset.audition` 现在在五个 Host 上都已注册——Web Host 的 bridge 与
protocol 由 [#999](https://github.com/endaye/lmdj/pull/999) 补齐，Creator 的两个试听控件
（set 级 demo 与每个已占用槽）与停止控件由
[#1023](https://github.com/endaye/lmdj/pull/1023) 补齐。Host 只传递字节与展示 typed
result，Core 保留全部 Contract、哈希与准入判定。Schema conformance、Set Store 单元测试、
Facade 写集测试与 Creator surface 测试固定该边界。

**注册不等于发声。** Web Host 把 Facade 交回的已重采样 PCM 发布进引擎保留的双槽 audition
池并起声（[#1001](https://github.com/endaye/lmdj/pull/1001)、
[#1003](https://github.com/endaye/lmdj/pull/1003)、
[#1009](https://github.com/endaye/lmdj/pull/1009)）；原生 Host 的播放接线仍未完成，
[#799](https://github.com/endaye/lmdj/issues/799) 追踪它。

Web 侧的自动化验收现在走到了一半，这一半的界线值得写清楚：
[#1059](https://github.com/endaye/lmdj/pull/1059) 起，`soundset.audition` 的回包带
`played`，说明这一次试听是否真的起了声；真实浏览器里有一条腿观察这个回包，并钉住
「会话刚起、音频未激活时 `played` 必须为 `false`」。也就是说，**有自动化检查观察到一次
Web 试听没有发声，但没有任何自动化检查观察到一次 Web 试听发出了声音。** 驱动可发声的
那一半时，Host 会在一秒内终止（`played: true` 之后 transport 即断），这是
[#799](https://github.com/endaye/lmdj/issues/799) 记录的字节通路缺陷，不是 `played`
这个字段的问题。不要把"操作已注册"读成"已听到"，也不要把 Creator lane 的绿读成试听
这条腿已经闭合。

**已注册不等于产品内可达。** Task 7 的验收在真实浏览器中对打包后的 Creator 实测出三个
缺陷，各自阻断链路上的一段；三个都已修复。[#900](https://github.com/endaye/lmdj/issues/900)
曾使本 Build 产出的任何 Project 都无法导入浏览器——浏览器侧 Bundle reader 的枚举停在
`1.1.0` / `lmdj.project.v3`，而导入 Bundle 是浏览器获得 Project 的唯一途径；修复见
`f1293997`。六腿浏览器 journey 自
[#978](https://github.com/endaye/lmdj/pull/978)（`b5d8ca93`）起无援转绿。[#901](https://github.com/endaye/lmdj/issues/901) 的
`connect-src 'self'` 曾拦截一切跨源 Catalog，而真实 Catalog 必然跨源：现在 Creator 通过
同源前缀 `/soundset-catalog/` 取用 Catalog，由 Host 转发，该指令不再需要写入任何外部
origin。它保护的不是 Creator 自己那两个同源 fetch，而是 OPFS 中 Project 与音频的外泄
边界，因此保持原样。[#902](https://github.com/endaye/lmdj/issues/902) 使 Workspace Set
Store 以裸 `IO_ERROR` 拒绝发布每一个合格 Set，也已修复。三者都是既有缺陷，不是本 Build
引入。原生 Host 与 C ABI 侧的 list → inspect → map.preview → install `keep`/`replace`
journey 已有跨 Host 黑盒验收；Safari 与 iPadOS 上的目录浏览仍无物理验收。
