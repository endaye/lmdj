## 总体结论

**通过。** 单 commit、单一主题、tag 标题与内容完全吻合，延续了 1.0.8.0 的良好节奏。

这个 build 交付了第一个可分发的 Core 包：一个 relocation-safe 的 ZIP，
内含独立 CLI、MCP 启动器、C ABI 共享库、Assembly 与 Build Manifest，
并配一个从净化环境解压后真实运行两个 Host 的验收测试。

**打包实现本身的安全性与验收测试的严谨度是本仓库迄今最高的之一。**
发现集中在**发行治理**而非打包代码：产物无法字节复现、
`package` 命令不跑测试却打上 `canary` 标签、以及产物与源码修订之间缺少绑定。

发现汇总：**0 个高严重度、3 个中严重度、3 个低严重度。**

## 一、做得好的地方

### 无 rpath 依赖的重定位设计

包布局把两类消费者彻底分开：

```
bin/lmdj-core          POSIX sh 启动器
bin/lmdj-core-mcp      Python 启动器
libexec/lmdj-core      真正的 CLI 可执行文件
lib/liblmdj_core_c.*   C ABI 共享库
python/lmdj_core_mcp/  MCP Host 源码（4 个文件）
share/lmdj/            assembly.json / assembly.lock.json / version.json / 契约 Schema
build-manifest.json
README.md
```

CLI 自包含在 `libexec/`，共享库只被 MCP 启动器以
`--library <绝对路径>` 显式加载。**没有任何一处依赖 rpath 或
`DYLD_LIBRARY_PATH` / `LD_LIBRARY_PATH`**，包可以解压到任意路径直接运行。
这是分发包最容易出错的地方，这里绕开得很干净。

### 启动器正确镜像了 CLI 的严格位置文法

`bin/lmdj-core` 只在 `$1 = --workspace` 时注入 Assembly：

```sh
if [ "$#" -ge 2 ] && [ "$1" = "--workspace" ]; then
  workspace=$2; shift 2
  exec "$package_root/libexec/lmdj-core" \
    --workspace "$workspace" --assembly "$package_root/share/lmdj/assembly.json" "$@"
fi
```

初看像是"参数顺序敏感"的缺陷，核对 `apps/core-cli/src/main.cpp` 的
`parse_invocation()` 后确认**不是**——CLI 本身就是严格位置文法：

```cpp
if ((argc != 6 && argc != 8) || std::string_view(argv[1]) != "--workspace") return std::nullopt;
if (argc == 8) { if (std::string_view(argv[3]) != "--assembly") return std::nullopt; ... }
```

注入后恰好构成 `argc == 8` 且 `argv[3] == "--assembly"`。启动器与 CLI 文法严格对齐。

MCP 启动器的 `"--assembly" in arguments` 判断同理：即便用户使用
`--assembly=X` 等号形式导致判断落空而重复注入，argparse 后者胜出，用户值仍然生效。

### 打包实现的安全性

| 防护 | 位置 |
|---|---|
| 拒绝 symlink 输入 | `require_file()` / `require_directory()` 显式 `is_symlink()` 检查 |
| 拒绝 symlink 入包 | `create_zip()` 遇到 symlink 抛 `PackageError` |
| 路径穿越检查 | `relative.startswith("/") or ".." in Path(relative).parts` |
| 原子落盘 | 临时归档 + `os.replace()`；临时目录以 `dir=output_dir` 创建，保证同文件系统 |
| 输出目录不得为 symlink | `package()` 开头显式检查 |
| 确定性文件模式 | `shutil.copyfile` + 显式 `chmod`，不继承源模式 |

### 验收测试是本仓库迄今最扎实的一个

`tests/distribution/package_acceptance_test.py` 做的事：

- **精确清单**：`assert actual == expected`，失败时打印对称差（多了什么/少了什么）
- 解压后断言无 symlink、启动器有可执行位
- **逐文件复核 Build Manifest**：每个 artifact 的 `sha256` 与 `byte_length`
  都对解压出来的真实文件重算比对
- 断言 `manifest["assembly_lock_sha256"]` 与源 lock 一致、`git_revision` 为 40 字符
- **在净化环境下真实运行两个 Host**：`PYTHONNOUSERSITE=1`、清除 `PYTHONPATH`，
  从解压目录之外调用 CLI 建 Project 并查 `provider.list`，
  再走 MCP `initialize` + `tools/call`，**断言两者输出一致**
- 打包时注入 `PYTHONPATH=/nonexistent/lmdj-poison`，证明打包器不依赖环境
- `assert str(REPO_ROOT) not in launcher.read_text(...)` —— 启动器不得烘焙仓库绝对路径

最后一条是很好的重定位断言，通常要等到用户报 bug 才会想到。

### TDD 顺序是真实的

实施计划 Task 1 明确要求"在打包器存在之前写下失败的验收测试"，
Step 3 要求跑 RED 并期望"非零退出，因为 `scripts/package-core.py` 不存在"。
Task 2 才实现打包器。这不是事后补测试。

## 二、发现

### 发现 1【中】`scripts/core.sh package` 不跑任何测试，产物却标记为 `canary`

新增命令的全部内容：

```sh
package)
  cmake --preset release
  cmake --build --preset release
  python3 scripts/package-core.py \
    --build-root "$build_root/release" \
    --output-dir "$build_root/dist"
  ;;
```

配置 → 构建 → 打包，**没有任何测试环节**。
而 `package-core.py` 调用 `generate_manifest(..., "canary", ...)`，
产物的 `build-manifest.json` 里写着 `"channel": "canary"`。

`docs/governance/version-management.md` §3 对 canary 的门禁写得很清楚：

> | `canary` | 每个可构建候选，供自动化和开发者快速发现问题 | **编译成功、基础单测通过** |

"基础单测通过"没有被执行。任何人跑一次 `scripts/core.sh package`
就能产出一个自称满足 canary 门禁、实际只满足"编译成功"的分发包。

`scripts/core.sh proof` 确实新增了 package acceptance 调用，
但 `proof` 与 `package` 是两条独立命令，后者才是产出可分发产物的入口。

建议：`package` 至少串上 `ctest --preset release -L '^(unit|component)$'`，
或者在未通过测试时把 channel 降级标记。

### 发现 2【中】归档无法字节复现，`create_zip` 的确定性努力被 manifest 抵消

`create_zip()` 为可复现做足了功夫：

```python
for source in sorted(package_root.rglob("*")):          # 字典序
    info = zipfile.ZipInfo(relative, date_time=(1980, 1, 1, 0, 0, 0))  # 固定时间戳
    info.create_system = 3                               # 固定为 Unix
    info.external_attr = (stat.S_IFREG | mode) << 16     # 显式模式
```

但 `build-manifest.json` **在归档内部**，而它包含：

```python
"build_time": datetime.now(timezone.utc).isoformat(timespec="seconds")...
```

于是同一份源码、同一台机器、连续两次打包产出的 ZIP **字节必然不同**。
可复现构建的核心价值——"下载方可以自己重建并比对 hash 来验证产物未被篡改"——
无法实现。

需要说明的是，`build_time` 是 **policy 要求的**：
version-management.md §4 明确列出 Build Manifest 必须记录"构建时间与构建平台"。
所以这不是打包器写错了，而是**两个正确要求放在了同一个容器里**：
归档要可复现，manifest 要记录构建时刻。

建议：把 `build-manifest.json` 同时（或改为）**作为 detached 文件**与 ZIP 并列发布。
归档本身去掉可变字段后即可字节复现，manifest 仍然满足 policy 的记录要求。
另可支持 `SOURCE_DATE_EPOCH`（当前仓库全无相关支持）。

### 发现 3【中】产物与源码修订之间没有绑定

两个独立缺口叠加：

**(a) `--build-root` 完全不受校验。** 打包器只要求它是一个真实目录，
里面有 `bin/lmdj-core` 和平台共享库。没有任何检查证明这些二进制
是由当前源码树构建的。指向一个陈旧的 build 目录，打包器会愉快地把
旧二进制、新的 `assembly.json`、以及标着 `1.0.9.0` 的 manifest 打进同一个包。

**(b) `_git_revision()` 不检测脏工作树：**

```python
result = subprocess.run(["git", "rev-parse", "HEAD"], cwd=REPO_ROOT, ...)
```

只取 `HEAD`。在有未提交修改的工作树上打包，manifest 会记录一个
**干净的 40 字符 SHA，而该 SHA 并不描述包内实际内容**。

合起来的后果：Build Manifest 的 `git_revision` 字段
——policy §4 称之为"这个 Build 对应 Monorepo 的哪一个精确提交"——
可以在两个方向上撒谎，且没有任何门禁会发现。

验收测试只断言 `len(manifest["git_revision"]) == 40`，不验证其真实性。

建议：`_git_revision()` 增加 `git status --porcelain` 检查，非空则拒绝打包
（或在 manifest 中标记 `dirty: true`）；打包器校验 `build_root` 下的
构建产物与当前源码的一致性，最简单的做法是要求 `build_root`
内存在由构建系统写入的、含当前 SHA 的标记文件。

### 发现 4【低】归档本身没有 detached 校验和或签名

`build-manifest.json` 记录了包内每个文件的 sha256，但它自己在包内。
下载方拿到 `lmdj-core-1.0.9.0-macos-arm64.zip` 之后，
**没有任何带外信息可以验证这个 ZIP 未被替换**——
篡改者可以同时改文件和 manifest。

policy §3 把"签名"列为 `stable` 的门禁，而 M1 上限是 `dev`，
所以缺签名在当前阶段是合规的。但一个 detached `.sha256` 文件成本近乎为零，
建议现在就加上，不必等到 stable。

### 发现 5【低】channel 硬编码为 `canary`

```python
manifest = generate_manifest(..., "canary", ...)
```

`generate_manifest` 本身支持 `{canary, dev, beta, stable}` 并会校验，
但打包器没有暴露任何参数。而 policy 明确 M1 Headless Core Proof
**可以进入 `dev`**。当前实现要产出 `dev` 包必须改代码。

建议加 `--channel` 参数，默认 `canary`，并把非 canary 值与相应门禁绑定
（这与发现 1 是同一件事的两面）。

### 发现 6【低】`validate_manifest` 的 lock 比对近乎恒真

```python
staged_lock = package_root / "share/lmdj/assembly.lock.json"
expected_lock = json.loads((REPO_ROOT / "products/lmdj/assembly.lock.json").read_text(...))
if json.loads(staged_lock.read_text(...)) != expected_lock:
    raise PackageError("staged Assembly lock does not match source")
```

暂存副本正是几行之前由 `copy_file()` 从这个源文件复制出来的。
这个断言只能发现复制过程损坏，无法发现任何有意义的不一致。

真正有价值的比对是"暂存的 lock 与暂存的 `assembly.json` 是否互洽"，
而那个校验已经由 `verify()` 在更早的位置做过了。此处可以删除或改写。

## 三、一个连带观察

本 build 把 `contracts/assembly/lmdj.assembly.v2.schema.json` 打进了发行包。

结合 1.0.8.0 review 的发现 2——**本仓库没有任何 JSON Schema validator，
Schema 从未被执行过**——这意味着分发给外部消费者的是一份
**从未被验证过能否正确拒绝非法输入的 Schema**，
且运行时（`assembly_loader.cpp`）也不用它做校验。

它作为文档是有价值的，但包内只有 assembly schema、没有 capability v2 schema，
而后者才是第三方 Provider 作者真正需要的。这个取舍看不出依据。

## 四、版本治理核查

**无发现。判断准确。**

| 域 | 处理 |
|---|---|
| Product Build | `1.0.8.0` → `1.0.9.0` |
| Core Modules | unchanged —— "No Module API or ownership change" |
| Hosts | `core-cli` / `core-mcp` 保持 `1.0.0` —— "Host protocols are unchanged; packaging is Product-level" |
| Contracts | unchanged |
| Providers / Models | unchanged |

把打包正确识别为 **Product 层面**而非 Module 层面的变更，
是这份 Version Management 最关键的判断——打包不改变任何模块的 API 或所有权，
不应触发 SemVer 波及。diffstat 也印证了这一点：没有任何 `module.json` 被修改。

计划同样明确区分了授权边界：

> This plan authorizes implementation, commit, branch push, and PR creation
> under the active user goal. Tag creation, tag push, Release, deployment,
> and Channel promotion remain separate post-merge gates.
