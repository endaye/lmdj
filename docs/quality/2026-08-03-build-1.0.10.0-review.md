## 一、无锁实现审查

### enter / drain 握手是正确的 Dekker 模式

```cpp
bool enter() noexcept {
  in_flight_.fetch_add(1, std::memory_order_seq_cst);   // A
  return enabled_.load(std::memory_order_seq_cst);      // B
}
void disable_and_drain() noexcept {
  enabled_.store(false, std::memory_order_seq_cst);     // C
  while (in_flight_.load(std::memory_order_seq_cst) != 0) {  // D
    std::this_thread::yield();
  }
}
```

关键在于 **`enter()` 先自增再查标志**，而不是先查标志再自增。
按 seq_cst 全序推演"回调在 B 处读到 `true`，同时控制线程在 D 处读到 `0`"这个危险组合：

- 若 D 在 A 之前：全序为 C → D → A → B，则 B 在 C 之后，必读到 `false`，矛盾。
- 若 D 在对应 `leave()` 的 `fetch_sub` 之后：该回调已经结束，无危险。

两个方向都不成立，握手成立。天真写法（先 `load(enabled)` 再 `fetch_add`）会在两者之间留出窗口——这里没有踩。

`render_callback` 用 RAII `CallbackExit` 保证 `leave()` 一定执行，
包括早退路径（`enabled == false` 时走 `silence_render_buffers`）。

### SPSC 队列实现正确

```cpp
static constexpr std::size_t kStorage = Capacity + 1;   // 留一个空槽区分满/空
```

- 生产者：relaxed 读自己的 `write_`、acquire 读 `read_`、写 cell、release 发布 `write_`
- 消费者：对称，relaxed 读 `read_`、acquire 读 `write_`、读 cell、release 发布 `read_`
- `alignas(64)` 分离两个索引，避免伪共享
- 三条 `static_assert`：`Capacity > 0`、`is_trivially_copyable_v<T>`、
  `std::atomic<std::size_t>::is_always_lock_free`

没有 ABA 风险（单生产者单消费者、索引单调递增取模）。

### render() 是真正 RT-safe 的

逐行核对，回调路径上**没有分配、没有锁、没有异常、没有系统调用**：

- `voices_` 是 `std::array<Voice, 128>` 固定容量，`samples_` 是预分配 vector，
  回调内只读 `.data()` / `.size()`
- 只用 `std::fill_n` / `std::find_if` / `std::clamp` 与原子计数器
- 时钟经注入的 `MonotonicClock`，遥测经 `fetch_add(relaxed)`

`update_max()` 的 CAS 循环也是 relaxed，正确（只是最大值统计，不承担同步职责）。

## 二、发现

### 发现 1【中】Apple-only 代码无法被本项目的 sanitizer 基础设施覆盖

本 build 新增约 833 行 Apple-only C++：

```
packages/audio-runtime/src/apple/coreaudio_output.cpp        417
packages/audio-runtime/src/apple/coreaudio_services.cpp      343
packages/audio-runtime/src/apple/coreaudio_output_state.hpp   73
```

内容是无锁握手 + 裸 AudioUnit 生命周期管理——风险等级最高的一类代码。

而项目的全部验证基础设施都在 Linux：

| CI job | `runs-on` | 对 CoreAudio 代码 |
|---|---|---|
| `core (macos-latest)` | macOS | ✅ 唯一执行环境（`scripts/core.sh proof`，普通 Release） |
| `core (ubuntu-latest)` | Ubuntu | ❌ 不编译 |
| `core-asan` | `ubuntu-24.04` | ❌ 不编译 |
| `core-coverage` | `ubuntu-24.04` | ❌ 不编译 |
| `core-nightly / core-tsan` | `ubuntu-24.04` | ❌ 不编译 |
| `core-nightly / core-stress` | `ubuntu-24.04` | ❌ 不编译 |

结论：这 833 行在 PR 上**唯一的执行环境是 macOS job 的 proof——
无 ASan、无 UBSan、无 TSan、无覆盖率测量**。

最刺眼的一点是：**TSan 恰恰是验证 enter/drain 握手的正确工具，
而它跑在这段代码根本不编译的平台上。** 我上面是靠人工推演确认握手正确的，
CI 没有任何机制能在它被改坏时发现。

覆盖率门禁也在结构上看不见这些行——Linux 上不编译 → 不进 LLVM export →
不进分母。于是 `packages/audio-runtime/` 的 80%/67% 地板实际只衡量
offline renderer 与 realtime engine，新增的 833 行既不拉低指标也不被要求覆盖。

建议：增加一个 macOS ASan/UBSan job。TSan 在 macOS 上对 Apple 框架支持有限，
但 ASan + UBSan 已能覆盖大部分生命周期与越界问题。

### 发现 2【中】`audio.realtime_spsc_stress` 在 PR 上零门禁执行

新增的 SPSC 并发压测在所有 PR-blocking job 上都不跑：

| job | 命令 / filter | 结果 |
|---|---|---|
| `core` | `scripts/core.sh proof` → `-LE '^stress$'` | ❌ 排除 |
| `core-asan` | `scripts/core.sh test asan full` → `-LE '^stress$'` | ❌ 排除 |
| `core-coverage` | **本 build 新增** `exclude.name ^audio\.realtime_spsc_stress$` | ❌ 排除 |
| nightly `core-tsan` | preset 已扩展纳入 | ✅ 但不在 PR 上 |
| nightly `core-stress` | `-L '^stress$'` | ✅ 但不在 PR 上 |

1.0.7.0 review 里我记录过：`facade.c_api_stress` 至少还能通过 coverage job
进入 PR 门禁。**本 build 为新的 SPSC 压测显式关掉了那最后一条路径**——
注意 `facade.c_api_stress` 仍在 coverage 里跑，只有 audio 这一个被单独排除。

于是一个全新无锁原语的并发测试，无法阻止任何一个 PR 合入。

组件级 `audio.realtime_engine`（TIER component）确实在所有 job 上跑，
所以不是完全无覆盖；缺的是**多线程**那一层。

### 发现 3【中】`RealtimeEngine` 的线程契约完全未声明，而违反它是 use-after-free

`packages/audio-runtime/include/lmdj/audio/realtime_engine.hpp` 是公共头文件，
全文关于线程只有一句注释，还是给 telemetry 的：

```cpp
// Counters are exact after quiescence and a best-effort snapshot while running.
```

但这个类的危险面远不止 telemetry：

- `stop()` 从控制线程写 `voices_`（**非原子**数组）和队列的 read 索引，
  而 `render()` 也读写这两者
- `load_sample()` 执行 `samples_[slot].assign(...)`，**可能重分配 vector**
- 而 `render()` 把 `sample.data()` 裸指针存进 `Voice`

也就是说：**如果 `render()` 仍可能执行时调用 `stop()` 或 `load_sample()`，
就是数据竞争加 use-after-free。**

当前实现是安全的，因为 `CoreAudioOutputStateMachine::stop()` 严格按
`services_->stop()` → `disable_and_drain()` → dispose → `engine_.stop()` 排序，
`engine_.stop()` 一定在 drain 之后。

问题是**这个前提只存在于调用方，被调用的类一个字都没写**。
`load_sample()` 里的 `state_ == stopped` 检查不足以支撑安全性——
一个直接使用 `RealtimeEngine` 的新 Host 完全可以先 `engine.stop()`
（把 state 置为 stopped）、而自己的音频线程仍在跑 `render()`，
接着 `load_sample()` 通过检查、vector 重分配、活跃 Voice 的指针悬空。

这正是 2026-08-01 core review 对 facade 提出的
"**`Application` 线程安全契约未声明**"【中】级问题，
在一个后果严重得多的领域重演。而且 1.0.11.0 已经在此之上加了
"formal native realtime host"——第二个消费者已经存在。

建议：在头文件上写明每个方法的调用线程与前置条件
（"`start` / `stop` / `load_sample` / `clear_sample` 必须在保证 `render`
不可能并发执行时调用"），并考虑用类型或断言把它变成可检查的约束。

### 发现 4【低】`disable_and_drain()` 无超时，可无限自旋

```cpp
while (in_flight_.load(std::memory_order_seq_cst) != 0) {
  std::this_thread::yield();
}
```

设备卡死或回调线程被永久阻塞时，`stop()` 永不返回。
它在公共 API 路径上（`CoreAudioOutput::stop()`），
调用方没有任何手段中止。

建议加自旋上限，超时后转 `failed` 终态并把 context 送进 quarantine
（后者已有机制，正好适用）。

### 发现 5【低】每次 start/stop 循环无条件泄漏一个 callback context

```cpp
void CoreAudioOutputStateMachine::retire_callback_context() noexcept {
  callback_context_->disable_and_drain();
  preserved_telemetry_ = callback_context_->telemetry();
  auto* const context = callback_context_.release();
  context->quarantine();     // 插入永不回收的无锁栈
}
```

对 **dispose 失败**的路径这是正确的——CoreAudio 可能仍持有回调指针，
宁可泄漏也不能 use-after-free，这个判断是对的。

但 dispose **成功**时也照泄不误。每个 start/stop 周期约 64–72 字节，
一个反复启停音频的 DJ 应用会无界增长。

建议：drain 完成且 dispose 成功时直接释放，只对失败路径 quarantine。

### 发现 6【低】render 回调单次工作量无上界

```cpp
while (queue_.try_pop(event)) {
  ...
  auto voice = std::find_if(voices_.begin(), voices_.end(), ...);  // O(128)
}
```

队列容量 1024，voice 容量 128，最坏情况单次回调 131,072 次迭代。
按 48kHz / 256 帧算 deadline 约 5.3ms，实际大概率跑得完，
但这是一个**没有硬上界**的模式。

已有 `record_deadline_overrun()` 作为可观测性兜底，是好的，
但观测不等于约束。建议加"每回调最多处理 N 个事件"的上限，
剩余事件留到下个回调——反正队列本来就是为跨回调缓冲设计的。

## 三、其他做得好的地方

**平台条件编译有负向 CI 断言。** Ubuntu job 显式验证 Apple-only target
**不存在**，并且尝试构建它们必须失败：

```yaml
for target in lmdj_audio_coreaudio lmdj_native_audio_probe; do
  if grep -Fq "$target" "$evidence_dir/targets.txt"; then exit 1; fi
  if cmake --build build/core/dev --target "$target" >...; then exit 1; fi
done
```

为条件编译写负向测试的团队不多。这直接防住了"Apple 代码悄悄泄漏到通用构建"。

**CoreAudio 服务层被抽象为可注入接口。** `CoreAudioServices` 与
`MonotonicClock` 都经 `unique_ptr` 注入，使得 1517 行的
`coreaudio_output_test.cpp` 能在**没有真实音频设备**的情况下
穷举状态机与各条失败路径。这是让平台代码可测的正确做法，
也是本 build 测试量最大的部分。

**启动/停止的失败路径逐级回滚。** `created_` / `listener_added_` /
`initialized_` / `unit_started_` 四个标志追踪已完成的步骤，
配 `retain_first_error` 保留首个错误并继续清理，
无法干净收尾时进入 `failed` 终态而不是假装成功。

**tsan preset 已纳入新压测**——但用的是继续追加硬编码测试名的方式：

```json
"include": { "name": "^(facade\\.c_api_stress|audio\\.realtime_spsc_stress)$" }
```

1.0.7.0 review 把"用名字而非语义做门禁选择"记为【低】级陷阱，
这里正是它第一次需要人工维护。（1.0.11.0 已改为 `label: ^native$`。）
