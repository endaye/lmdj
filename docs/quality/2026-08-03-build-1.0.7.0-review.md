## 一、JSON 深度限制（fix #69）

### 做对的地方

**边界数学是准确的，我核对过 nlohmann 3.12.0 的实现。**
`json_sax_dom_callback_parser::start_object()`（`detail/input/json_sax.hpp:544`）
以 `ref_stack.size()`（push 之前）作为 callback 的 `depth`，所以最外层对象 depth = 0。
`depth >= 64` 判定 ⇒ 接受"外层对象 + 63 层嵌套"= 总共 64 层容器，
与常量名 `kMaximumJsonContainerDepth = 64` 和测试断言（63 accept / 64 reject）完全自洽。

**三个边界对称覆盖**，无遗漏：

| 边界 | 位置 |
|---|---|
| CLI request | `apps/core-cli/src/main.cpp:120-141` |
| C ABI request | `packages/application-facade/src/c_api.cpp:119-140`（`invoke_application`） |
| C ABI config | 同上（`lmdj_engine_create`） |
| Product Assembly | `packages/application-facade/src/assembly_loader.cpp:53-68` |

**回归测试扎实**：三条路径各有 200,000 层崩溃回归
（`tests/host/cli_test.py:252,364`、`tests/core/facade/c_api_test.cpp:723`），
CLI 与 C ABI 另有 63/64 边界用例。

**MCP Host 早已设防**：`server.py:566` 与 `c_api.py:186` 都显式捕获 `RecursionError`，
Python 侧不是缺口。

**修复了自查报告的头号高危项**——`docs/quality/2026-08-01-core-review.md`
列出的 **【高】#1 JSON 嵌套深度无限制 → 栈溢出 DoS**。

### 发现 1【中】深度限制未覆盖磁盘 JSON 读路径

同一崩溃类别在 7 处仍然裸奔，全部是不带 callback 的 `nlohmann::json::parse`：

```
packages/project-io/src/project_store.cpp:540    读 project JSON 文件
packages/project-io/src/project_store.cpp:1739   读 active take journal 首行
packages/project-io/src/take_journal.cpp:431     读 journal header
packages/project-io/src/take_journal.cpp:469     读 journal event 行
packages/project-io/src/take_journal.cpp:834     读 sealed take
packages/provider-sdk/src/attempt_store.cpp:572  读 host settings
packages/provider-sdk/src/attempt_store.cpp:1040 读 attempt 记录
```

这些点**都套了 try/catch**，但 try/catch 对这个漏洞无效：
深嵌套的杀伤来自 DOM 析构的递归栈溢出，栈溢出不是 C++ 异常，捕不住。

威胁模型上这不是"内部可信数据"：`.lmdj` bundle 是可以被分享、拷贝、手工构造的文件，
而且**本仓库自己的审查报告已经把 project bundle 当作信任边界处理了**
（该报告 #3 就是 project-io JSON 读路径的符号链接 TOCTOU）。
同一份文件，符号链接被当作安全问题，嵌套深度却不算——标准不一致。

实现计划 `2026-08-01-lmdj-json-depth-limit.md` **完全没有提到这些路径**，
既没修也没记为"已知延后"。建议：把深度限制下沉为 `foundation` 的一个函数，
在所有反序列化入口统一使用。

### 发现 2【中】"拒绝"不是提前中止，输入仍被全量消费

nlohmann 的 `start_object()` **无论 callback 返回什么都 `return true`**，
并且 `ref_stack.push_back(val.second)` 无条件执行（不保留时 push `nullptr`）。
也就是说：callback 返回 `false` 只阻止**建 DOM**，不阻止**继续解析**。

后果：一个 16MB 全是 `[` 的 request，仍会被完整词法分析，
并让 `ref_stack` 增长到约 800 万个指针条目（≈64MB 瞬时堆），外加同规模的 `keep_stack`。

崩溃确实被消除了（这是主要目标，达成了），但**资源消耗放大没有被消除**。
对当前单请求 CLI/C ABI 模型这是可接受的；一旦 `workers/` 落地成为长驻 Provider Host，
就需要重新评估。建议至少在代码注释里写明这是"不建 DOM"而非"提前中止"，
避免后来者误判其防护强度。

### 发现 3【中】`parse_bounded_json` 逐字复制三份，常量独立定义三份

```
apps/core-cli/src/main.cpp:30                            constexpr int kMaximumJsonContainerDepth = 64;
packages/application-facade/src/assembly_loader.cpp:24   同上
packages/application-facade/src/c_api.cpp:60             同上
```

三个 `parse_bounded_json`/callback 实现是字面级重复（仅输入适配器不同）。

这一点值得单独指出，因为**本仓库自己的审查报告刚刚把 `valid_utf8` 在
`main.cpp` 和 `c_api.cpp` 之间的双份实现列为【中】级问题，
并在"横向观察"里点名"重复实现是最常见的系统性问题"**。
这次改动没有修那个问题，反而在同样的两个文件里又制造了一份同类重复——
而且这次重复的是一个**安全常量**：三处之一被单独改动就会造成静默的边界不一致。

应下沉到 `packages/foundation`（连同 `valid_utf8` 一起）。

## 二、测试质量门禁基础设施

这部分工程质量明显高于平均水平，值得肯定：

- **`cmake/LmdjTesting.cmake`**：`lmdj_add_test()` 强制每个测试声明 tier，
  tier 决定 timeout 上限，risk label 与 tier 正交。42 处注册全部迁移完毕，
  并有 `tests/build/test_test_taxonomy.py` 做元测试守护。
- **`tests/quality/coverage_union.py`**：按源码身份对 per-object 的 LLVM LCOV
  分片做并集，解决了同一 `.cpp` 被多个 target 以不同编译变体编译时覆盖率丢失的问题。
  这是一个真实且不好解的问题，解法是对的。
- **`scripts/core-coverage.sh`**：`llvm-profdata merge` / `llvm-cov export`
  的 stderr 被当作失败条件（"emitted unexpected diagnostics"），
  杜绝了"覆盖率报告悄悄基于残缺数据生成"。
- **覆盖率诚实度**：`docs/quality/core-test-policy.md` 明确把
  **强制棘轮**（overall 76%/64%）与**长期目标**（80%/70%）分开写，
  并注明棘轮值是在 Mac 与 CI 等价的 Ubuntu 24.04 / Clang 18 双环境上实测得出的。
  比常见的"先设一个好看的数字再豁免一堆文件"高明得多。
- **`test_active_tree.sh` 新增泄漏守卫**：`*.profraw` / `*.profdata` /
  `coverage-objects.txt` 出现在 `build/core` 之外即失败。
- **project-io fault injection**：`FaultPoint` 枚举穷举 fsync/rename/remove 失败点，
  配 `project_io_test_hook_symbols_test.py` 用 `nm` 断言生产库不导出测试符号。

### 发现 4【中】`scripts/core.sh test` 的默认语义被静默改变

```diff
-    ctest --preset "$1"                      # 原来：跑全部
+    test_mode="${2:-full}"
+    full)  ctest --preset "$test_preset" -LE '^stress$' ;;   # 现在：默认排除 stress
```

`proof` 同时也加了 `-LE '^stress$'`。

`CLAUDE.md` 里作为稳定入口点记录的 `scripts/core.sh test dev`，
现在不再运行全部测试，而文档没有同步说明这一点。

顺着看 PR 阻塞路径上 `facade.c_api_stress`（本 build 新增的 C ABI 并发生命周期压测）
到底跑不跑：

| CI job | 命令 | 是否跑 stress |
|---|---|---|
| `core` (ubuntu + macos) | `scripts/core.sh proof` | ❌ `-LE '^stress$'` |
| `core-asan` | `scripts/core.sh test asan full` | ❌ `-LE '^stress$'` |
| `core-coverage` | `ctest --preset coverage` | ✅（coverage preset 无 filter） |
| `core-nightly / core-tsan` | — | ✅ 但**不在 PR 上** |
| `core-nightly / core-stress` | `--repeat until-fail:20` | ✅ 但**不在 PR 上** |

结论：这个并发测试在 PR 上**唯一的执行环境是 coverage instrumented 构建**
（clang-18 profiling，仅 Linux）。它**不在 ASan 下跑**，TSan 只有 nightly。
用 profiling 插桩后的时序去暴露 data race，是所有可选方案里信号最弱的一个。
建议把 `facade.c_api_stress` 单独加进 `core-asan` job。

### 发现 5【低】tsan test preset 用硬编码测试名过滤（已在后续 build 修复）

`CMakePresets.json` @ 1.0.7.0：

```json
{"name": "tsan", "filter": {"include": {"name": "^facade\\.c_api_stress$"}}}
```

在 1.0.7.0 当时这是正确的（当时只有这一个 stress 测试），
但它意味着**任何后续新增的 stress 测试都会被静默排除在 TSan 之外**。

这个陷阱确实被踩到了：后续 build 新增的 `audio.realtime_spsc_stress`
（一个 lock-free SPSC 队列压测——正是 TSan 最该覆盖的东西）曾被此 filter 挡在门外。
HEAD (1.0.11.0) 已改为 `{"include": {"label": "^native$"}}`，问题已解决。
在此记录，是因为它是"用名字而非语义做门禁选择"的典型代价。

## 三、生产代码中的测试钩子

`c_api.cpp`、`project_store.cpp`、`take_journal.cpp` 现在合计带有约 15 处
`#if defined(LMDJ_*_TESTING)` 块，其中 `write_new_file()` 的**函数签名本身**
变成了条件编译的（多一个 `std::optional<FaultPoint>` 参数）。

这是一个真实的取舍。fsync/rename/close 失败路径除了故障注入基本没法测，
而这些正是 project-io 崩溃一致性的核心；他们选择注入并配了符号泄漏守卫，
判断是合理的。但成本也是真实的：`commit_loaded()` 现在被 6 个 `#if` 块切碎，
主干逻辑的可读性明显下降。

建议后续收敛：用一个集中的故障点分发函数替代 11 个内联调用点。

### 发现 6【低】宏守卫风格不一致，且缺少与 project-io 对称的符号守卫

```cpp
// packages/application-facade/src/c_api.cpp:23
#if defined(LMDJ_C_API_TESTING)

// packages/project-io/src/testing_hooks.hpp:3
#if defined(LMDJ_PROJECT_IO_TESTING) && LMDJ_PROJECT_IO_TESTING
```

facade 只判 `defined`，所以 `-DLMDJ_C_API_TESTING=0` 会**打开**钩子而不是关闭它。
project-io 的写法没有这个问题。

另外，project-io 有 `tests/build/project_io_test_hook_symbols_test.py` 用 `nm`
断言生产库不导出 `FaultPoint` / `set_fault_hook`，
但 facade 的 `set_invoke_gate` / `block_invoke_if_selected` **没有等价守卫**。

当前实际是安全的（`LMDJ_C_API_TESTING=1` 只在
`packages/application-facade/CMakeLists.txt:175` 的 stress target 上定义，
且 `testing_hooks.hpp:4` 有 `#error` 兜底），
但两个模块对同一风险采取了不同强度的防御，属于不必要的不对称。

### 发现 7【低】Assembly 路径缺少 63/64 边界测试

计划本身就只为 Assembly 安排了 200,000 层崩溃回归，没有安排边界用例
（CLI 和 C ABI 两条都有）。所以这不算偏离计划，但覆盖是不对称的——
Assembly 的深度常量若被单独改坏，没有测试会发现。
