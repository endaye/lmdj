## 一、修掉的既有问题

### 1.0.10.0 发现 3（悬垂指针）—— 结构性修复

1.0.10.0 的风险是：`load_sample()` 的 `samples_[slot].assign()` 可能重分配 vector，
而 render 线程的 Voice 持有 `sample.data()` 裸指针 → use-after-free。

本 build 引入 RCU 式的 Bank 发布，从机制上消除了它：

- **`PreparedSampleBank`**：move-only、不可拷贝，由 `from_snapshot()`
  在**控制线程**从 `RuntimeSnapshot` 离线构建。构建好之后内容不再变化。
- **4 个固定 Bank Slot**，状态机 `empty → pending → current → retiring → reclaimable`
- **Voice 持有 `bank_slot` index**，audio thread 在起音时 `++active_voices`、
  在 `release_voice_bank()` 里 `--active_voices`
- **只有控制线程释放内存**：`reclaim_retired_banks()` 只处理 `reclaimable` 状态的 slot

也就是说 audio thread 不再析构 vector、不再 delete——spec 第 200 行明确写了这条约束。

我核对了引用计数平衡，**没有找到泄漏或提前释放路径**：

| 路径 | 处理 |
|---|---|
| Voice 自然播完 | `release_voice_bank()` 递减；归零且 `retiring` → `reclaimable` |
| `stop()` | **对每个 active voice 调用 `release_voice_bank()`**（1.0.10.0 只是清零，会漏计） |
| `stop()` 时 publish_queue 里的 pending slot | 逐个 pop 并标记 `reclaimable`，同时回退 `pending_publications_` |
| 发布失败回滚 | `bank.reset()` + `generation = 0` + 状态回 `empty`，计数回退 |
| 当前 bank 跨 stop/start | 保持 `current`，不被回收——样本在停启之间存活，符合预期 |

`publish_sample_bank()` 在 slot 上的写入（`bank.emplace` / `active_voices = 0` /
`generation`）都发生在状态还是 `empty` 时，render 不会触碰 `empty` slot；
随后 `state.store(pending, release)` 与 `publish_queue_.try_push()` 建立 happens-before。
顺序是对的。


## 二、部分修复：线程契约仍未上头文件

1.0.10.0 发现 3 的另一半——**公共头文件不声明线程前提**——只改善了一点点。

`realtime_engine.hpp` 现在有两行注释：

```cpp
// Publication and enqueue share one serialized control-thread producer.
// Counters are exact after quiescence and a best-effort snapshot while running.
```

而完整线程模型写在 496 行的
`docs/superpowers/specs/2026-08-02-lmdj-formal-native-realtime-host-design.md` 里，
写得很扎实：Audio Thread 不写文件/不分配/不释放/不加锁/不输出日志、
Bank Slot 状态机、Capture Ring 的生产者消费者方向、control-thread reclaim、
Host 用非 Audio Thread mutex 串行化同一 `Application` 的控制面。

**设计是想清楚了的**，这点必须肯定。问题只是：读 `realtime_engine.hpp` 的人看不到。

而且这个前提在本 build 变得**更加 load-bearing**：

- `stop()`（控制线程）会 `publish_queue_.try_pop()`，而 `render()` 也 pop 同一个队列
  —— **同一个 SPSC 队列出现两个消费者**
- `stop()` 还调用 `queue_.clear_quiescent()`（写 `read_`），`start()` 调用三个队列的
  `clear_quiescent()`

在"`stop`/`start` 与 `render` 不并发"的前提下这些都正确。
但前提一旦被破，后果比 1.0.10.0 更重：那时是数据竞争，
现在是 **SPSC 队列的内部结构被两个消费者损坏**。

建议：把 spec 里已经写清楚的那几条前提，以注释形式搬到每个方法上方。
这是低成本、纯收益的一步——设计已经存在，只是没暴露给 API 的读者。

## 三、新发现

### 发现 1【中】名为 "test host" 的组件进入了 Product Assembly 与分发包

`products/lmdj/assembly.json`：

```diff
   "hosts": [
     { "id": "core-cli",  "version": "1.0.2" },
     { "id": "core-mcp",  "version": "1.0.2" },
+    { "id": "native-test-host", "version": "1.0.0" }
   ],
```

`scripts/package-core.py`：

```diff
+    copy_file(
+        build_root / "bin/lmdj-native-host",
+        package_root / "bin/lmdj-native-host",
+        0o755,
+    )
```

`tests/distribution/package_acceptance_test.py` 也把 `bin/lmdj-native-host`
加进了精确清单，并断言 `--no-device` 返回 64 且 stderr 以 `usage: lmdj-native-host ` 开头。

所以：**一个模块 id 叫 `native-test-host` 的组件，现在是 Product Assembly
的正式成员，并且随每一个分发包发给下游。**

CLAUDE.md 对 `apps/` 的定义是 "thin Core Hosts that use only the Application Facade"，
没有"测试 Host"这一类。这里二者必有一错：

- 要么**名字错了**——它其实是正式的原生 Host / 诊断工具，
  那就该叫 `native-host`，module id 与二进制名统一；
- 要么**边界错了**——它是验收工具，不该进 Assembly 和发行包，
  应该像 `lmdj_native_audio_probe` 那样留在 `tests/` 下。

从内容看（1122 行 main.cpp + capture writer + 物理验收留证）它更像前者，
但名字里的 "test" 会持续误导后来者判断它是否属于产品面。

这一条要与 1.0.9.0 发现 1（`package` 不跑测试却标 `canary`）合看：
**发行包的内容边界正在扩张，而没有一条书面准则说明什么该进、什么不该进。**

### 发现 2【低】`publish_sample_bank` 的 `events_pending` 门槛可能在持续演奏时永不放行

```cpp
if (running && queue_.size_approx() != 0) {
  return PublishResult::events_pending;
}
```

方向是安全的：控制线程是 trigger 队列的唯一生产者，render 只会让计数减少，
所以读到 0 就确实是 0（或刚变成 0）。不会误放行。

但它意味着**只要 trigger 队列非空就无法发布新 Bank**。
持续演奏时队列几乎总是非空，新 Bank 可能长时间——甚至永远——发布不出去。

spec 提到不允许 Voice"跨越尚未完成的 Bank 边界"，看得出这是有意设计，
但**没有任何退避、超时或优先级机制**，也没有把这个可用性后果记为已知限制。
调用方拿到 `events_pending` 之后除了轮询没有别的手段。

建议：至少把"换 Bank 需要演奏间隙"写进 API 文档或 open-questions；
如果这会成为产品问题，需要一个明确的过渡策略。

### 发现 3【低】RT 路径上无校验解引用 `std::optional`

```cpp
const auto& sample = bank_slot == kLegacyBankSlot
                         ? samples_[event.slot]
                         : bank_slots_[bank_slot].bank->sample(event.slot);
```

`bank->` 直接对 `std::optional<PreparedSampleBank>` 用 `operator->`，不检查 `has_value()`。

当前不可达——`current` 状态的 slot 必然持有 bank。但这是 `noexcept` 的实时函数，
一旦状态机被改坏，得到的是 UB 而不是可诊断的失败。

建议：加一条 debug 断言，或在 RT 路径上用 `*` 前先做一次 `LMDJ_ASSERT`。
（注意不能在 RT 路径上抛异常或分配，所以只能是断言或静默降级为静音。）

### 发现 4【低】render 单次工作量上界问题未处理，且面积略有扩大

1.0.10.0 发现 6 未处理。本 build 还给 render 增加了：

- `while (publish_queue_.try_pop(...)) apply_published_bank(...)`
  ——publish_queue 容量只有 4，`apply_published_bank` 是 O(1)，新增量很小
- 每次 voice start 多一次 `capture_voice_start()`（写 capture ring）

主要成本仍是原来的触发事件循环：最坏 1024 事件 × O(128) 找空闲 voice。
仍然没有"每回调最多处理 N 个事件"的硬上界。

## 四、做得好的地方

### `native_host_source_boundary_test.py` 是本仓库最好的架构守卫

它不只是查 include，而是四层同时约束：

```python
FORBIDDEN = ("lmdj/project_io/", "project_store.hpp", "take_journal.hpp",
             "std::ifstream", "std::ofstream", "filesystem::directory_iterator")
```

1. **源码级**：Host 源码不得出现上述任何 token——直接执行
   "Hosts must not parse Project bundles"
2. **单一生产者**：断言只有 `main.cpp` 里出现 `.enqueue(`
3. **清单级**：断言 `module.json` 依赖精确等于
   `{application-facade 1.1.0, audio-runtime 0.3.0}`
4. **链接闭包级**：断言 CMake 链接依赖精确等于
   `{lmdj::application, lmdj::audio_runtime}`（darwin 上加 `lmdj::audio_coreaudio`）

第 4 条最有价值——它把 CLAUDE.md 的 "Hosts use Application Facade"
从一句约定变成了**链接期可执行断言**。绕过 Facade 直连 `project-io` 会在 CI 失败，
而不是等到 review 时靠人眼发现。

### Facade 新增 typed API 而 JSON / C ABI 一个字未动

三个新方法：

```cpp
foundation::Result<std::shared_ptr<const cooker::RuntimeSnapshot>>
    prepare_runtime_snapshot(const RuntimeSnapshotRequest&);
foundation::Result<void> append_realtime_take_events(..., std::span<const domain::RawTakeEvent>);
foundation::Result<std::filesystem::path> seal_realtime_take(...);
```

计划明确写 "exposes typed in-process Host methods **without changing its
JSON/C ABI**"，版本表记 `application-facade 1.0.1 → 1.1.0`、`api_version` 保持 2。

实时路径不能容忍 JSON 序列化开销，为它开一条进程内 typed 通道是合理取舍；
关键是**旧 Contract 完全没动**，CLI / MCP / C ABI 消费者零影响。
返回的是 `shared_ptr<const RuntimeSnapshot>`，不可变，符合
"Runtime Snapshot is immutable derived state" 不变量。

### Capture Ring 的方向与握手正确

- producer = audio thread，consumer = control thread，固定 4096 容量
- `arm_capture()` 只发布 `arm_pending`；audio thread 在 callback 边界
  用 CAS 切到 `active` 并记录 `capture_origin_frame`
- **Host 只有观察到 `active` 才接受录制中的事件**

最后这条避开了"以为已经在录、其实还没开始"的经典错误——
录制起点由 audio thread 而不是控制线程定义。

### 其他

- **`TakeJournal::append_batch()`**：批量落盘，避免每事件一次 fsync
- **物理验收留证**：`docs/quality/2026-08-03-formal-native-host-acceptance.md`
  加 `evidence/*.jsonl`（54 requests / 55 responses）
- **`RuntimeSnapshot` 新增 `pads`**：Bank 需要按 Pad Slot 预备全部 64 个样本，
  而不是只有 Pattern 用到的；这是 `ResolvedPad` 存在的原因，符合
  "Pattern events reference Pad Slots" 不变量
