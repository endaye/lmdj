## 一、缺陷修复本身

### `.front()` 高危缺陷已彻底修复

`packages/provider-sdk/src/attempt_store.cpp`：

```cpp
// 旧（1.0.7.0）：只看第一个端口，其余端口的 required/max_count 静默失效

  const auto& port = capability.input_artifacts.front();
  if (request.inputs.size() < minimum || request.inputs.size() > port.max_count)

// 新（1.0.8.0）：逐端口独立计数
for (const auto& port : capability.input_artifacts) {
  const auto count = std::count_if(request.inputs.begin(), request.inputs.end(),
      [&port](const auto& input) { return input.port == port.name; });
  if (count < minimum || count > port.max_count)
```

输出侧对称重做为 `valid_output_bindings()`，同样逐端口执行 required / `max_count` / media type。
`find_port()` 按名字解析端口，未声明的端口一律拒绝。

### 顺手补上了第二个更隐蔽的洞

`media_type_allowed()` 的签名从"接收整个端口列表"改成"接收单个端口"：

```cpp
-bool media_type_allowed(const std::vector<ArtifactPortDescriptor>& ports, ...)
+bool media_type_allowed(const ArtifactPortDescriptor& port, ...)
```

旧实现只要求 media type 被**任意一个**端口接受；新实现要求被**它自己绑定的那个**端口接受。
这个洞上一份 core review 没点出来，本次借重构一并关闭。

### 同时修掉了 1.0.7.0 review 的一个中危项

`registry.cpp` 的 `valid_capability()` 新增 `!capability.output_artifacts.empty()`，
Schema 侧 `output_artifacts.minItems: 1` 对齐。
这关闭了原报告"空输出端口注册/执行校验不一致"的问题。

### 持久化格式做了规范形式强制

- `format` 从 `terminal-attempt` 升为 `terminal-attempt-v2`
- 读回时用 `std::is_sorted(..., binding_less)` 强制 binding 数组的规范序
- `exact_binding_shape()` / `exact_artifact_shape()` 精确键集校验，多一个键即拒
- 成功态额外断言 `same_bindings(candidate_outputs, minted_outputs)`；
  失败态断言两者皆空

## 二、发现

### 发现 1【中】端口名校验规则在四个层次上不一致，只有注册层符合 Contract

Contract `contracts/capability/lmdj.capability.v2.schema.json` 规定：

```json
"port_name": { "type": "string", "pattern": "^[a-z][a-z0-9_]*$" }
"artifact_binding": { "properties": { "port": { "$ref": "#/$defs/port_name" } } }
```

实际四个层次各行其是：

| 层次 | 位置 | 实际规则 | 是否符合 Contract |
|---|---|---|---|
| Provider 注册 | `registry.cpp: valid_port_name()` | `^[a-z][a-z0-9_]*$` | ✅ |
| Host 请求边界 | `application.cpp: safe_file_id(port)` | alnum + `.` `_` `-`，≤128，含大写 | ❌ 更宽 |
| Attempt 读回 | `attempt_store.cpp: valid_file_id(binding.port)` | 同上 | ❌ 更宽 |
| MCP 工具 Schema | `server.py: "port": file_id` | `FILE_ID_PATTERN`，≤128 | ❌ 更宽 |

这**不是安全问题**——`find_port()` 对未声明端口返回 `nullptr`，请求 fail-closed 被拒。
但有三个实际代价：

1. **MCP 向客户端公布了错误的取值域。** 客户端按公布的 input schema 生成 `Port-1`
   在结构上完全合法，却永远无法匹配任何 Capability。公开 Contract 表面与真实接受域不一致。
2. **错误信息退化。** 端口名不合法与"artifact 本身有问题"合并成同一句泛化消息
   `"capability request artifacts are invalid"`，调用方无法区分。
3. **语义错位。** 用**文件名**校验规则（含 Windows 保留名、尾部点空格检查）去校验
   **端口名**，在概念上就是错的。端口名不落盘，不需要文件名约束；
   反过来它需要的小写约束又没被执行。

建议：把 `port_name` 规则下沉为单一实现，facade、attempt_store 读回、MCP schema 三处统一引用。

### 发现 2【中】Contract Schema 从未被真正执行过

`git grep jsonschema` 在整个仓库无结果——**没有任何 JSON Schema validator**。

`tests/conformance/schema_contract_test.py` 做的是两件事：

1. 对 Schema **文档本身**做结构断言
   （`assert capability_v2["properties"]["output_artifacts"]["minItems"] == 1`）
2. 对 fixture 断言"它**含有**这些违规"
   （`assert invalid_descriptor["output_artifacts"] == []`）

也就是说：`tests/fixtures/contracts/capability-v2-invalid.json`
**从来没有被 v2 Schema 校验过哪怕一次**。没有任何测试证明这个 Schema 会拒绝它。

后果是 Schema 退化为纯文档件，与 C++ 实现的漂移**无任何自动检测手段**。
发现 1 正是这个缺失机制的直接产物：Contract 写了 `^[a-z][a-z0-9_]*$`，
三个代码层次实现了别的规则，而没有任何门禁会发现。

这也解释了为什么 invalid fixture 把四处违规（`max_count: 0`、`output_artifacts: []`、
binding 缺 `port`、candidate 空输出）揉在一个文档里：
既然没有 validator，就无法逐条断言"这一条被哪条规则拒绝"，只能整体标记为"无效"。

注意这个约束是有来由的：本仓库刻意保持 Python 侧零第三方依赖
（MCP Host 甚至用 `ast` 强制 stdlib-only import）。
所以建议不是"装 jsonschema"，而是**写一个覆盖本仓库 Schema 所用子集的最小校验器**
（`type` / `required` / `pattern` / `enum` / `const` / `minItems` / `minimum` /
`additionalProperties` / `$ref` / `uniqueItems` 即可），让 valid/invalid fixture 真正跑一遍。

### 发现 3【低】Schema 的 `uniqueItems` 抓不到重名端口

`input_artifacts` / `output_artifacts` 上的 `uniqueItems: true`
只能阻止**完全相同的对象**。两个都叫 `source`、但 `media_types` 不同的端口
在 Schema 上合法，在 `registry.cpp: valid_ports()` 的
`names.insert(port.name).second` 处才被拒。

Schema 比运行时弱，且 invalid fixture 没覆盖这个 case。
若 Provider Manifest 由外部按 Schema 生成，会出现"Schema 校验通过但注册失败"。
与发现 2 同源——有了 validator 之后，这条应作为独立负向 case 加入。

### 发现 4【低】重复 mint 从静默去重变成硬失败，未列入版本影响表

```cpp
// 1.0.7.0：幂等，二次 mint 同一 sha256 被静默忽略
if (!contains(minted, described.value())) { minted.push_back(described.value()); }

// 1.0.8.0：硬失败 + 清理临时文件
if (std::any_of(minted.begin(), minted.end(), [&](const auto& b) {
      return b.artifact.sha256 == described.value().sha256; })) {
  std::filesystem::remove(temp_path, cleanup_error);
  return failure(invalid_argument("output Artifact was already minted"));
}
```

方向是对的（显式优于静默）。但这是 **Provider 可观察行为的变更**，
而实施计划的 Version Management 表在 `provider-sdk` 一行只写了
"Request, Candidate, Sink, and private persisted Attempt semantics are incompatible"，
没有单列这条。因为 v2 本身就是 breaking，不构成实际兼容性问题——纯属记录颗粒度。

## 三、已记录的设计约束（非缺陷，但需盯住）

**同一 ArtifactRef 不能绑定到多个端口。**
`validate_request()` 的 `input_hashes` 与 `valid_output_bindings()` 的 `artifact_hashes`
都是**跨端口的全局 set**，同一 sha256 出现在两个端口上即判非法。

这**是明确的决策**，`docs/prd/decision-log.md` 写得很清楚：
"初始 v2 禁止同一 Artifact Ref 绑定多个端口"。所以不算缺陷。

但值得提前记入 open-questions：真实用例会撞上它——
比如同一段音频同时作为 `reference` 和 `target` 输入，
或同一份 stem 同时输出到 `preview` 和 `master`。
届时放宽这个限制虽然对请求侧是向后兼容的，但会改变 Attempt evidence 的语义
（`artifacts` 去重数组与 binding 数组的关系变了），需要走 v2 minor 而非无声修改。

**更值得肯定的是主动划清了"没做的事"**：

decision-log 的"限制"段直白写着：

> 当前 `ArtifactRef` 没有 Schema provenance，v2 先验证 binding 选择的端口和该端口声明的

这是很高的诚实度——避免了"端口身份校验被误当作 Schema 校验"这类日后极难纠正的误解。
