# Global Pattern transport — architectural design

Date: 2026-09-11. Architectural proposal for [capability #1230](https://github.com/endaye/lmdj/issues/1230), prerequisite to Creator migration U2. Product behavior below is confirmed by the user in this conversation; interfaces and concurrency mechanics below are proposed, not implemented. Source checked at `8338b7cd0334b441a39be099e9a9d02ae3b0022e`. This does not complete U0 or validate a Figma flow. See the [U0 design](2026-09-11-creator-hardware-migration-design.md).

## 1. Confirmed behavior

Separate global Play/Stop and Record keys control one coupled session, regardless of page. Record means Pad actions into the current Pattern for sequencing/overdub, never microphone or performance/master WAV.

| Current state | Play/Stop | Record |
| --- | --- | --- |
| stopped | playing only | playing and recording |
| playing only | stopped | playing and recording |
| playing and recording | stop both | stop recording, keep playing |

Every stopped-to-running start begins the current Pattern at its beginning, without count-in. Record on/off while playing never restarts playback. Ending recording commits/retains events. No recording-only steady state or arm-and-wait mode. Busy/error/recovery are truthful operation phases, not additional successful steady states. Normal navigation neither changes key duties nor stops transport. Sample capture, performance recording and saved replay remain separately named workflows.

## 3. One owner and public seam (proposed)

Use one Facade-owned Pattern transport coordinator per active runtime/project session, supplied with a runtime transport port implemented by the existing control runtime. It orchestrates journal ownership and effects; the audio engine owns the applied clock and scheduler state. Creator keeps only a projection and pending command identity. This is a small coordinator, not a new session, engine, event subscriber or replacement application framework.

Proposed public Facade operations: `request_pattern_transport(request)` and `inspect_pattern_transport(session)`; matching bridge operation names `pattern.transport.request` and `pattern.transport.inspect`, plus JS `requestPatternTransport`/`inspectPatternTransport`. Names are design proposals, not existing APIs. Request contains session/project identity, unique command ID, expected transport epoch, intent `play_stop` or `record`, and expected Project revision when journal creation needs it. Coordinator resolves the toggle once against authoritative stable state; retrying the same ID returns/reconciles the original operation, never toggles twice. Reject reused IDs with different payloads and stale epochs. While an operation is pending, reject a new transport mutation with explicit busy status rather than accumulating ambiguous clicks.

Status carries applied state, operation phase (`preparing`, `awaiting_audio`, `flushing`, `reconciling`, `error`), command ID, runtime generation/transport epoch, active Pattern identity and publication generation, applied frame/origin/BPM, journal ID/admission cutoff, pending switch identity/authority, committed revision if present, and structured failure/recovery information. Distinguish last applied audio state from requested target and durable journal outcome. A Promise resolution or timer is not an audio acknowledgment.

All control mutations enter the existing serialized session lane, but an entire transport operation must not occupy its JS Promise tail. `pattern.transport.request` reserves the command/epoch and returns a pending ticket; the tail is released on that response, not after audio acknowledgment or journal flush. Preparation/IO completion and receipt inspection reenter as short, epoch-checked continuation steps; asynchronous waits occur outside the lane and outside Facade/Project locks. Triggers/releases continue through their existing serializer and result path between steps. Conflicting transport/publication mutations remain reserved, not live input. A synchronous long-running prepare/flush cannot be disguised as this split: its runtime port must provide completion continuations before opting in. Existing trigger journal-append work/result semantics are not made fire-and-forget. Engine playback is never a second live input subscription.

An engine-only toggle is smaller but cannot own journal durability or cross-page state. A Creator-only composition leaves a race between journal and playback clocks. The coordinator plus runtime port is the smallest coherent option covering both; no separate service is proposed. The unresolved-admission persistence dependency identified in §5 requires a separately assessed storage seam.

## 4. Audio boundary, clock and voice ownership (proposed)

Add a bounded control-to-audio transport command handoff and coherent audio-to-control receipt. Each command contains runtime generation, monotone epoch, expected Pattern/publication identity, desired playing state and publication policy. The audio thread applies it at a defined render-block boundary before scheduling that frame; receipt records the actual effective frame, origin, playing state, applied Pattern and canceled/already-applied publication identity. Queue admission is not application. Queue full rejects before changing state; a missing receipt is unknown, not success. Never allocate, perform IO, wait on a mutex or spin on the audio thread. Control may poll an immutable observation; stale generations cannot satisfy acknowledgment after restart.

Stopped-to-playing sets origin to the acknowledged boundary frame, cursor to the beginning and playing=true: no count-in. A Record-only transition during playback uses a boundary/clock fence without restarting or resetting origin. Pattern scheduling checks playing independently of engine running. Stop sets playing=false before scheduling the cutoff frame and stops Pattern-owned voices using `pattern_voice` plus validated slot/generation ownership, not `origin==performance_replay`. Preserve held/live Pad voices, release routing and unrelated replay ownership. Apply the existing bounded release/ramp policy; report the stop boundary separately from any bounded audio tail. Slot reclamation still waits for its last voice/reference.

Publication gets explicit policy: `restart_at_boundary` for a true new start or existing authorized Pattern switch, versus `preserve_phase` for a same-Pattern overlay/committed replacement. The latter retains musical origin, does not re-trigger earlier events, and positions the cursor at the first not-yet-scheduled event for the application frame. It must bypass both the current unconditional origin reset AND the outgoing-slot voice-stop loop in `apply_published_pattern` (`realtime_engine.cpp:457`). Events already heard before publication are next-loop material, not replayed retrospectively. Reject preserve-phase publication with incompatible Pattern identity/tempo/length authority; do not silently reinterpret it. Existing tempo-edit boundaries retain their own authoritative re-anchor rules and serialize with transport.

For preserve-phase replacement, only future event scheduling changes slots. Each already-started Pattern voice keeps its old immutable slot/material reference, generation, cursor, envelope and absolute `scheduled_release_frame`; neither terminate it nor migrate/re-trigger it from the new view. Mark the old slot retiring and decrement its voice references through normal voice completion. Reclaim only when all voice and publication/audio references are gone. Multiple retired generations may coexist within the existing fixed slot/voice bounds. Pattern Stop and true switch terminate all applicable Pattern-owned voices, including retired generations, using ownership rather than the current-slot-only test. A sustained old voice must not escape Stop just because an overlay changed the current slot.

If no slot is reclaimable, refuse/defer the replacement before publishing; keep the current scheduler and sustained voices intact. Retain the latest desired immutable revision on the control side (coalesce only not-submitted same-Pattern overlays), never force-reclaim a sounding slot, steal a voice to make room, or grow audio-thread storage. Durable Record-off commit can therefore be known while its runtime replacement is pending/failed: report that split and retry the same desired revision when resources retire. Journal events remain durable, not dependent on an overlay slot being available.

## 5. Journal alignment and transition ordering (proposed)

Separate journal preparation from admission. Reuse journal creation/lease/recovery and add an internal activation seam taking acknowledged Pattern identity, origin, BPM, effective admission frame and monotone input watermark. Journal tick zero is the Pattern origin, not the button frame. Extend the Facade runtime setup to preserve `TransportAnchor{pattern_origin, 0, bpm}` while setting `last_runtime_frame`/admission lower bound to the activation frame. Before activation, an internal prepared journal is busy infrastructure, not a recording-only user mode. A durable prepared journal must remain recoverable if activation fails.

For stopped Record: prepare the journal and Pattern first, then apply one start/admission boundary and activate journal admission from its receipt. For playing Record: prepare the journal, obtain a clock/admission fence for the current epoch/Pattern, and activate without changing origin. Serialize switches around this fence; if identity changed before the boundary, reconcile/reprepare rather than attach the journal to the wrong Pattern. Admission candidates use the runtime-side contract below, never Creator intent timestamps.

### Admission/result contract and bounded retention

Current `runtime_session.mjs:1886,2053` serializes trigger dispatch; `control_runtime.cpp:3487–3499` attempts engine enqueue before journal append, and `record_sequence_pad` (`:1158`) samples runtime telemetry. Preserve this ordering and its successful, failed and unknown outcomes under #725. At the existing post-enqueue/pre-journal point, retain a candidate only when the press returned `EnqueueResult::accepted`, or release passed the existing `enqueue_sample_control` success path. Stamp it there with runtime generation, monotone control-event watermark, telemetry frame, slot/kind and the existing press sequence or release correlation. This is enqueue eligibility, NOT proof of audible acceptance. The existing JS admission ledger, outcome event and release route stay authoritative and unchanged; do not wait for an audible outcome to decide journal eligibility or promote `enqueued` to `heard`.

Use two distinct identities: the original live input/gesture identity for routing, and the journal input sequence for ordered durable append. Only assign/advance the latter when its append is known successful, matching the existing `record_sequence_pad` rule. Keep a bounded journal-owned-press map by slot and live correlation; repeated presses retain the current per-slot retrigger/finalization behavior, not a new multi-gesture model. A press qualifies only within the acknowledged admission/cutoff interval. A release qualifies only if that journal owns the matching press. Thus a held pre-admission live press followed by a post-admission release stays entirely live-only; never fabricate a press or submit an orphan journal release (`application.cpp:2784`). Correlation reuses current release ownership; it must not change which live gesture is released.

| Boundary/outcome | Recording adapter action; unchanged live result |
| --- | --- |
| Known enqueue refusal | No candidate/owned press. Return the existing failure; do not enqueue again. A later release cannot create a journal press. |
| Enqueue succeeded, journal/staging append failed | Preserve the existing error/partial-effect path: the live press may already be queued. No success synthesis, live replay or automatic retrigger; retain any known durable prefix and expose the recording error. |
| Response/outcome unknown | Preserve unknown status in the original ledger. Reconcile only retained runtime/journal command identities; never infer absence from a timeout or resubmit the live trigger. A late audible rejection does not retroactively invent a different journal-admission rule. |
| Duplicate completion/receipt | Consume its watermark/journal receipt once; do not call live enqueue again or append the same known-success event twice. An ambiguous append must be reconciled before advancing the ordered drain. |
| Owned press before cutoff, physical release at/after cutoff | Forward the real release through the existing live route only. Terminal journal stop uses existing `finalize_unreleased` (`application.cpp:2810,2946`), including its current sixteenth-tick completion rule; do not synthesize a release at cutoff, clamp duration, or change #725. Clear the journal-owned map only after known terminal closure. |

An unknown fence cannot be covered by an unbounded RAM queue or a promise of crash-safe recovery. **Additional required dependency within #1230's recording-adapter slice:** a bounded, durable unresolved-admission staging capability in Facade/Project IO, plus command/epoch-bound fence-outcome retention. It stores the post-enqueue candidates and their watermarks before claiming successful journal retention, separately from normal Pattern events until the admission identity/frame is known. Drain in watermark order, select eligible presses and their releases, and append through existing journal validation; a retained transfer receipt prevents duplicate append after restart. Live enqueue is never part of replay. This is a proposed storage/recovery seam, not an existing `append_tail` feature or an implemented format; its schema/API/version impact must be assessed explicitly. Without it the lossless unknown-fence path is not implementation-ready.

Reserve the staging capacity and terminal/error record before submitting the fence. On deadline or the last reserved candidate slot, close *recording* candidate admission at a control watermark B before processing the next candidate; persist the terminal reason and last retained watermark using that reserved record, and request/reconcile the same epoch's closure. All already-retained candidates remain in the bounded durable store; after the original fence resolves, drain only its eligible prefix through B and use ordinary journal stop/recovery. Subsequent live input continues with its unchanged outcome path, but is explicitly outside the failed recording attempt; display recording error/closure pending, not continued recording. No eviction of eligible candidates, indefinite buffering, or silent successful overflow. If storage itself fails, retain the known durable prefix and report the uncertain/failed suffix with identities; do not claim that suffix recoverable. If the runtime is lost before the fence is known, preserve unresolved staging as such rather than guess a Pattern/tick origin.

This dependency must preserve #725's current successful/failed/unknown classification, even where it records an enqueue that never becomes audible. If a platform cannot expose the existing post-enqueue identity/release correlation or completion steps without redefining those results, the exact additional dependency is an admission/outcome contract change under #725; stop that adapter slice and report the conflict. Transport approval does not authorize that change. No Creator-intent buffer, success-on-RAM-insertion shortcut or new admission policy is an acceptable substitute.

For ending recording, establish an acknowledged cutoff F and drain eligible input with runtime stamps before F, preserving the journal-owned-press rules above. The control watermark orders equal telemetry-frame observations; never replace their runtime stamps with UI intent time or acoustic onset. Events stamped at/after F remain live input only. Then invoke terminal journal stop with the stable command identity and F, after applying the cutoff-relative switch decision in §6. Record-off keeps playing; Play/Stop from both applies scheduler stop at the same cutoff before IO flush. Flush latency must not continue Pattern scheduling after an acknowledged Stop. Success is reported only when the audio effect and journal durable outcome are both known. A new Record cannot overtake unresolved closure.

Publish the committed same-Pattern view with preserve-phase policy when playback continues; if stopped, install/update the view without enabling scheduling. Update/show committed revision only when a Project exists and receipt revision is non-null; otherwise retain current revision and inspect authority. Stop is not discard. Playback-only Stop needs no journal; playback-only start must not create one.

## 6. Pending switches, failures and lifecycle (proposed)

Use the existing exact replacement authority `(generation, Pattern identity, activation frame)`, augmented by transport epoch, not best-effort cancellation or guessed current identity. At a Stop boundary the audio owner determines whether the switch applied before the cutoff. If not applied, cancel/suppress it and prevent stale queued publication from re-enabling playback. If already applied, acknowledge the winning identity/frame, reconcile the existing journal switch boundary first, then finalize at the stop cutoff. Stop wins over a publication due at the same frame by processing the stop fence first; this new ordering must be tested against the existing claim/cancel protocol, not replace it with unsafe slot reuse. A failed control-side cancellation alone cannot select either result.

Record-off uses the **same audio-owned cutoff/publication decision fence**, with playing left enabled. Its command names the exact pending authority and epoch. At F, before the per-frame publication claim/apply step, resolve queued, audio-local pending and claimed ownership: a switch applied at S < F is retained; a switch due at S >= F is canceled/suppressed, including the S = F tie. Freeze competing publication submissions until this decision is acknowledged. A control cancellation CAS losing to claim is not an outcome; the audio owner finishes that claim and records its actual application frame before it can acknowledge the fence. A fence arriving too late to precede a claim takes its actual effective F; never backdate F to the requested frame. Retire canceled views only after their actual owners release them.

The immutable per-command receipt retains F, origin/active Pattern at F, exact switch authority, result `applied_before_cutoff` with S or `canceled_at_cutoff`, and playing=true. Store it until the control coordinator durably retains the decision and closes/reconciles the journal; a current-status snapshot cannot overwrite it. Backpressure subsequent mutations rather than evict an unresolved receipt. Timeout inspection/retry returns this same historical decision, not the Pattern observed later. If that receipt is irretrievably unavailable, report unresolved recovery and do not finalize from guessed current identity.

When S < F, flush/reconcile that journal switch at S before draining its target segment up to F, then terminal-stop at F. When S >= F, remove the journal's pending switch using the acknowledged cancellation before terminal stop at F; never create a segment at S. Hence a delayed read after S cannot advance a canceled switch or close a segment later than its terminal cutoff. Publish the committed view for the receipt's active Pattern with preserve-phase policy; do not republish an old request-time Pattern or reset the still-running origin. Playback Stop uses the same durable cutoff-relative record with playing=false.

| Failure boundary | Required result/recovery |
| --- | --- |
| Prepare/queue refusal before effect | Keep prior applied transport; close or expose prepared journal through existing recovery as warranted; show refusal, never fake started state. |
| Audio effect acknowledged, journal flush fails | Keep the known audio state (stopped or playing); show recording closure error/recovery and retain journal identity/events. Do not resume playback to disguise failure or label commit successful. |
| Facade commit durable, publication fails | Keep committed revision/command identity separately from stale runtime view; retry/reconcile publication from durable receipt. No duplicate commit, reopened journal or engine-wide emergency Stop as the normal recovery. |
| Receipt/bridge timeout | Inspect epoch, audio receipt and journal status; retry exact command identity where supported. Do not issue inverse toggles or infer not-applied. Block conflicting writes until resolved. |
| Runtime restart/crash | New runtime generation starts transport stopped, never auto-replays stale commands. Recover durable journal with existing original/alternate existing Pattern routes; transport metadata is not Project Truth. |

Normal mode navigation only changes presentation and separately owned audition/capture cleanup; remove automatic global journal Stop on Sample entry. Explicit Suspend audio, runtime disposal or Project replacement uses a transport shutdown barrier: stop scheduling/admission, settle/recover journal closure, release required input, then suspend/dispose/replace. Failed/unknown closure prevents claiming a clean replacement; abrupt platform loss exposes recovery on reopen. Keep existing broader shutdown policies, not a new unrelated lifecycle design.

## 7. Compatibility and boundaries

Add explicit transport capability negotiation; global-enabled sessions use the coordinator exclusively. Keep existing Sequence APIs as legacy journal operations for consumers that have not opted in; do not silently change `stopSequence` to stop audio. In global-enabled sessions reject conflicting direct legacy writes, rather than let two journal owners race. Default legacy Pattern publication/start behavior must remain covered until each existing consumer explicitly adopts transport control. Creator opts in at its single session owner; all pages use that same projection.

Existing saved-performance replay and sample capture controllers retain their own ownership. Do not stop their voices by reusing the replay origin enum, bypass their established busy guards, or introduce new simultaneous-workflow guarantees. Shared public changes require native/other Host compatibility assessment. No new user capability or Project Truth schema is proposed. The unresolved-admission staging/receipt persistence dependency in §5 does require an explicit storage/API/version assessment; it must remain separate from Project Truth and preserve existing journal recovery and #725 outcomes.

The earlier scoped local search of `docs/prd/questions/` found no transport/Sequence clock or publication conflict; that directory stores historical context, not live issue status. Round-1 review identified the explicit #725 boundary in §5; the earlier search does not clear that dependency. No remote status audit was performed. Existing exact cancellation/claim ownership is an invariant this proposal must preserve; any inability to express the proposed fence within it is a concrete implementation-design conflict to report, not permission to weaken concurrency guarantees.
