# LMDJ 上传任务可见性与单槽队列需求

日期：2026-07-26

状态：需求已确认，待实施计划

产品归属：Stage 1 Creator Core 可用性与可靠性补强

## 1. 背景

当前 Creator 上传链路可以连续接受多次上传，但 `apps/api` 实际只有一个处理槽：

- 一个 Job 持有执行锁并运行 Pipeline；
- 其他上传通过内存线程等待，没有对用户可见的可靠队列；
- API Job 状态不保存原始文件名，也不提供任务列表、容量或队列位置；
- 浏览器只记住当前页面中的一首歌，收到网络错误或刷新后可能失去 Job 关联；
- 服务重启后，旧的非终态 Job 可能长期停留在 `separating`；
- 相同音频可被重复提交为多个 Job。

因此，用户无法判断当前正在处理哪首歌、还有多少首等待、是否可以继续上传，也无法确认网络失败后的上传是否已经被接受。

## 2. 用户故事

作为上传歌曲制作 Patch 的 Creator，我希望看到本次提交的歌曲、处理状态和队列容量，并能在刷新或暂时断网后恢复任务关联，从而知道系统正在做什么，避免重复上传。

## 3. 目标

本需求交付后：

1. 用户能识别正在处理和等待处理的每一首歌；
2. 用户明确知道当前最大并发为 `1`，以及正在处理数和等待数；
3. 同一次用户提交在重复点击或网络重试时只对应一个 Job；
4. 页面刷新不会丢失本浏览器提交的未完成任务；
5. 服务重启不会让遗留任务永久伪装成仍在处理。

## 4. 功能需求

### 4.1 任务身份

每个用户可见任务至少显示：

- 原始文件名；
- Job ID；
- 提交时间；
- 当前状态；
- 等待时的队列位置。

原始文件名是用户识别来源的显示信息，不替代基于音频内容建立的 source identity，也不进入 `patch_id`。

### 4.2 容量与队列可见性

上传界面和处理界面必须明确显示：

```text
最大并发 1 · 正在处理 1 · 等待 N
```

只有持有执行槽的任务可以显示为正在处理。等待任务必须显示为 `queued`，不能提前显示 `separating`。

### 4.3 提交幂等

前端在开始上传前生成并持久化一次提交标识。API 对同一提交标识重复接收上传或重试时，必须返回同一个 Job，不得创建重复 Job。

本需求只约束“同一次用户提交”的幂等，不禁止用户主动重新处理同一份音频。

### 4.4 刷新恢复

浏览器必须保存本地提交与 Job 的关联。页面刷新后，用户仍能看到未完成任务并继续查询状态。

本需求不要求账号级或跨设备任务历史。

### 4.5 中断状态

API 启动时必须识别无法自动恢复的旧非终态 Job，并将其转为明确的中断终态。UI 必须说明任务因服务中断而未完成，允许用户主动重新提交。

旧任务不得无限期保留为 `queued`、`separating` 或 `patchifying`。

## 5. 验收标准

1. 连续提交歌曲 A、B 后，界面显示 A 正在处理、B 等待、最大并发为 `1`。
2. A 完成后，B 自动进入处理槽；状态和队列计数同步更新。
3. A、B 始终显示各自的原始文件名、Job ID、提交时间和状态。
4. 对一次提交快速双击或在响应丢失后重试，只产生一个 Job。
5. 处理期间刷新页面，A、B 仍可见并继续更新。
6. 服务在任务处理中重启后，无法恢复的任务进入明确的中断终态，不继续显示为处理中。
7. 未知或不可恢复状态必须显示真实失败信息，不能只显示无上下文的 `Failed to fetch`。
8. 现有单首歌曲 Upload → Patch → Creator Export 链路继续通过。

## 6. 非目标

- 多 Worker 或多槽并发；
- Redis、SQS、Cloud Tasks 等生产队列选型；
- 任务优先级、暂停、继续或取消；
- 自动恢复 Pipeline 的中间计算；
- 账号级历史、跨浏览器或跨设备同步；
- 多用户配额、鉴权、限流、对象存储或 Postgres；
- 对内容相同但由用户主动发起的不同提交进行全局去重。

## 7. 与 API 队列生产化的关系

完整的 `apps/api` 生产化包含分布式队列、鉴权/限流、对象存储、Postgres、多用户容量和 durable workflow，目前没有绑定到固定 Stage，而是随真实产品流量推进。

本需求不是完整生产化队列。它是 Stage 1 Creator Core 的小型可用性与可靠性切片：在保留单槽执行约束的前提下，让用户能够理解、恢复并安全重试当前上传流程，为“非开发者无口头指导完成 Upload”提供可信产品行为。
