# WikiSkill：把 Agent 经验编译成持久知识

> 研究日期：2026-09-09。对象：Liyan Tang 等人的论文《WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution》，arXiv:2608.27454v1。
> 文档性质：论文解读、证据边界与对 LMDJ 的研究启发；不是模型选型、产品立项或实现承诺。
> 论文于 2026-08-27 提交，本文以 arXiv v1 为准；后续版本可能改变实验和结论。

## 1. 核心判断

WikiSkill 解决的问题是：Agent 在任务执行中积累了很多成功/失败经验，但传统的 Skill 演化流程通常把这些经验散落在轨迹、历史提案和评测结果里，下一轮不容易系统地复用。论文提出在“原始执行轨迹”和“当前可执行 Skill”之间加入一个持续累积的 Wiki 层，把经验整理成结构化模式、演化日志和 Skill 影响记录，再让后续 Skill 更新读取这些材料。

最重要的设计不是“多加一个 Markdown 文件夹”，而是把两种状态分开：

- **Skill 状态可以回滚。** 候选修改只有在验证集上优于当前最佳结果时才接受；否则恢复到上一个有效 Skill。
- **知识状态不回滚。** Wiki 保留已发现的模式、被拒绝的提案、证据和影响记录，为下一轮提供长期历史。

论文在五个基准、五个模型上报告了相对无 Skill 基线和三种 Skill 演化方法的改进；消融实验也支持“持久知识层是主要增益来源之一”。但这些结果是在受控的离线迭代实验中取得的，不能直接等同于生产 Agent 的长期自主学习、在线记忆或安全自动更新。

## 2. 论文要回答的问题

论文把 Agent 表示为带工具集合 `U` 和当前 Skill 集合 `S` 的 LLM 系统。Agent 在任务上执行会产生轨迹 `τ`，轨迹包含观察、动作、工具调用、工具输出和最终答案；任务得分由领域评分函数计算。

每次演化都有训练集、验证集和测试集。训练轨迹用于发现问题，验证集决定候选 Skill 是否接受，测试集用于最终报告。论文的状态可以抽象为：

```text
系统状态 k = (当前 Skill S_k, 持久 Wiki W_k)

S_k：当前允许 Agent 执行时读取的程序性知识，可接受或回滚
W_k：从历史经验编译出的知识，跨迭代保留并继续累积
```

这比“把上一轮完整上下文塞回下一轮 Prompt”更明确：经验先经过归纳，再以可追踪的知识对象参与 Skill 设计；执行时只注入当前 Skill，避免把 Wiki 本身变成任务求解捷径。

## 3. 三层工作区架构

论文将工作区分成三个层次：

| 层 | 作用 | 论文中的典型内容 | 状态语义 |
| --- | --- | --- | --- |
| Raw Layer `raw/` | 保存完整执行证据 | 推理、工具调用、工具输出、最终答案 | 不可变，作为后续分析原料 |
| Wiki Layer `wiki/` | 把轨迹整理成可复用知识 | `patterns/`、`index.md`、`logs.md`、`skill-impact.md` | 持续累积，不因 Skill 回滚而删除 |
| Skill Layer `skills/` | 保存当前可执行程序性指导 | `SKILL.md`、`PURPOSE.md` | 候选更新经验证后接受或回滚 |

其中 Wiki 的 `patterns/` 记录具体失败模式或成功策略及 workaround；`logs.md` 保留演化历史；`skill-impact.md` 记录提案的差异、验证得分和 Accepted/Rejected 结果。Skill 的 `PURPOSE.md` 则把当前 Skill 连接回促成它的 Wiki 模式。

这个分层把三件常被混在一起的事情拆开了：

1. **发生了什么：** 原始轨迹。
2. **从中学到了什么：** 结构化 Wiki 模式。
3. **当前要怎么做：** 可执行 Skill。

## 4. WikiSkill 的演化闭环

每一轮大致经过四个组件：

```text
Inference Agent
  └─ 使用当前 Skill 执行训练任务，写入不可变 Raw traces
       ↓
Wiki Maintainer
  └─ 抽样读取成功/失败轨迹，做根因分析，更新 Wiki patterns/logs
       ↓
Skill Proposer
  └─ 读取 Wiki 索引、影响历史和按需选择的轨迹，提出 Skill diff
       ↓
Gating & Rollback
  └─ 在验证集运行候选 Skill；提升则接受，否则只回滚 Skill
       ↓
保留 Wiki 更新与本轮提案结果，进入下一轮
```

### 4.1 Inference Agent

论文实验将当前 Skill 的完整内容直接注入系统 Prompt。这是一个有意的实验控制：研究重点是 Skill 的质量，而不是 Skill 检索、触发或路由是否失败。Inference Agent 可以使用任务环境提供的工具，但在默认 WikiSkill 配置中不能直接读取 Wiki。

这意味着论文验证的是“演化后 Skill 能否帮助执行”，不是“生产系统能否从海量 Skill 库中找对 Skill”。检索、权限、版本兼容和 Skill 冲突仍然是另一个问题。

### 4.2 Wiki Maintainer

Maintainer 从当前训练轮次抽样成功和失败轨迹，以避免一次性把全部历史塞进上下文。它对失败做根因分析，对成功提取策略，然后用增量、补丁式编辑创建或更新 Wiki 模式，并更新目录和演化日志。

论文没有把所有轨迹都永久压缩成一段摘要；Raw 层仍保留原始证据，Wiki 是它之上的结构化解释层。这为之后检查“某条模式由哪些任务支持”留下了可能性，也降低了知识整理后无法追责的风险。

### 4.3 Skill Proposer

Proposer 不是只拿固定轨迹批量改 Prompt，而是以 Wiki 索引、历史 Skill 影响记录和训练任务结果摘要为入口，再通过 `read_file` 按需读取具体模式和原始轨迹。它可以新建 Skill，也可以修改已有 Skill。

一个重要效果是，失败提案不会只被丢弃：拒绝的 diff 和验证结果会进入 `skill-impact.md`，下一轮可以知道某种修改已经尝试过且没有带来收益。

### 4.4 Gating 与 Rollback

验证逻辑是严格的单调门槛：只有验证集分数高于历史最佳分数才接受候选 Skill；否则恢复上一个 Skill 配置。Wiki 永远保留本轮整理结果和接受/拒绝记录。

这产生一个很有价值的状态组合：**执行策略是可逆的，经验账本是累积的。** 但它不等于知识内容天然正确。错误归因、错误模式或验证集过拟合仍可能被永久写入 Wiki，因此持久层需要来源、审查、版本和失效机制。

## 5. 论文的主要实验结果

### 5.1 实验范围

论文覆盖五类任务：数学推理 LiveMathematicianBench、网页搜索 SealQA、电子表格操作 SpreadsheetBench、长上下文文档问答 OfficeQA，以及交互式具身任务 ALFWorld。模型包括 Qwen-3.5-4B/9B-Instruct、Qwen-3.6-27B、Gemma-4-31B-It 和闭源 Gemini-3.5-Flash。

对比方法包括 Trace2Skill、EvoSkill、SkillOpt，以及不使用 Skill 的基线。每种方法的完整演化过程独立运行三次，论文报告平均测试表现，并使用配对 bootstrap 检验评估差异。

### 5.2 代表性结果

下表摘录论文 Table 1 的跨任务平均准确率（百分比）：

| 推理模型 | No skill | 最强基线 | WikiSkill | WikiSkill 相对 No skill |
| --- | ---: | ---: | ---: | ---: |
| Qwen-3.5-4B | 26.2 | 35.2 | 38.5 | +12.3 |
| Qwen-3.5-9B | 29.9 | 42.3 | 47.4 | +17.5 |
| Qwen-3.6-27B | 39.4 | 53.3 | 63.3 | +23.9 |
| Gemma-4-31B | 41.3 | 49.1 | 54.9 | +13.6 |
| Gemini-3.5-Flash | 49.5 | 56.1 | 68.1 | +18.6 |

论文报告的趋势比单个平均数更重要：

- WikiSkill 在五个模型上都取得最高的平均成绩，并且在大多数模型—数据集组合上超过无 Skill 基线。
- Qwen-3.6-27B 在 ALFWorld 上从 52.8% 提升到 77.6%，在 SpreadsheetBench 上从 40.8% 提升到 81.7%。
- WikiSkill 不是“Skill 让所有模型都同样变强”：OfficeQA 的小模型在执行长上下文、多步搜索流程时反而可能退化。
- Qwen-3.5-9B + WikiSkill 的平均准确率为 47.4%，高于 Qwen-3.6-27B 无 Skill 的 39.4%。这说明程序性知识在部分任务上可以弥补模型规模差距，但不能据此宣称“小模型普遍超过大模型”。

### 5.3 跨模型迁移

论文还测试一个模型演化出的 Skill 能否给另一个模型使用。结果显示，迁移后的 Skill 经常超过目标模型的无 Skill 基线，甚至超过目标模型自己演化的 Skill。例如，Qwen-3.6-27B 演化的 Spreadsheet Skill 让 Qwen-3.5-9B 达到 50.5%，高于其无 Skill 的 24.3% 和自演化 Skill 的 33.6%。

但迁移并不保证正收益。论文也观察到明显的负迁移：某些 Skill 包含模型特定的 workaround，而不是任务本身的通用程序。例如，同一类表格 Skill 从 Qwen-3.5-4B 迁移到 Gemini-3.5-Flash 时可能把表现从 50.5% 降至 18.1%。因此，“Skill 可迁移”应理解为可测的候选能力，不是无条件复用契约。

## 6. 消融实验说明了什么

论文在 Gemini-3.5-Flash 上改变两个开关：Inference Agent 在训练时是否能读 Wiki，以及 Skill Proposer 是否能读 Wiki。默认配置是 **Inference Agent 不读 Wiki、Proposer 读 Wiki**。

| Inference Agent 读 Wiki | Proposer 读 Wiki | 五基准平均 |
| --- | --- | ---: |
| 否 | 否 | 48.7% |
| 是 | 否 | 60.9% |
| 否 | 是 | 63.7% |
| 是 | 是 | 60.9% |

当 Inference Agent 不读 Wiki 时，给 Proposer 提供持久 Wiki 后，平均成绩从 48.7% 上升到 63.7%，提升 15.0 个百分点。论文据此认为，Wiki 的价值主要在于帮助 Skill 设计者跨迭代定位复杂、重复出现的失败模式。

相反，在 Proposer 已能读 Wiki 时，再让 Inference Agent 在训练轨迹中直接读 Wiki，平均成绩从 63.7% 降到 60.9%。论文的解释是：执行 Agent 可能直接利用 Wiki 解题，导致轨迹不再清楚暴露“仅靠当前 Skill 会失败的地方”，从而让 Skill Proposer 得到较弱的学习信号。

这不是说运行时永远不能读知识库，而是说明**用于发现 Skill 缺陷的训练轨迹**与**用于帮助 Agent 完成任务的运行时知识**应当有明确边界；两者混合会改变演化目标。

## 7. 一个具体案例：从循环失败到可执行规则

论文用 ALFWorld 的案例说明 Wiki 如何影响 Skill 演化：

1. 第 0 轮，Maintainer 发现 Agent 反复执行“拿起—检查—移动回原处”的循环。
2. Proposer 提出较抽象的 `goal-directed-action`，验证集没有提升，因此被拒绝。
3. Wiki 保留了这次失败提案及其 diff。下一轮 Proposer 因此提出更具体的 `break-repetition-loop`，包含“不要把物品放回原位置”的行动规则，并被接受。
4. 后续轨迹出现另一种多操作循环，Maintainer 将新证据追加到 Wiki；第 4 轮 Skill 进一步形成“每种操作类型对每个物品只执行一次”的规则。

这个案例展示了 Wiki 的真正作用：它保存“失败过什么、为什么失败、后来哪一种更具体的规则有效”，使后续提案不必重新从零猜测。它不是简单的对话历史，也不是把所有过去轨迹原样注入 Prompt。

## 8. 我对论文的技术评价

### 8.1 有价值的贡献

- **知识与策略分层。** 把不可变证据、可累积解释和当前执行规则分开，便于回溯、比较和回滚。
- **拒绝也成为资产。** 失败提案及验证结果进入历史，减少重复尝试，并为后续提案提供负证据。
- **把 Skill 发现与 Skill 执行分开。** 跨模型结果表明，能从轨迹总结出好规则，和能在复杂上下文中稳定执行规则，不是同一能力。
- **验证集门控是最小安全护栏。** Skill 的自动更新不是无条件覆盖，而是必须先通过可观测的验证指标。

### 8.2 不能过度解读的地方

- 论文测的是离线基准上的任务得分，不是持续运行系统的真实故障率、延迟、成本或安全性。
- Skill 内容被完整注入 Prompt，实验隔离了 Skill 检索和触发失败；因此论文没有解决 Skill 库变大后的路由问题。
- Wiki 内容由 LLM Maintainer 归纳，论文的验证门控主要检查 Skill 改动对验证集的效果，并不等同于人工审计事实正确性、权限安全或因果解释正确。
- 持久 Wiki 可能发生错误累积、过时规则、跨版本污染和数据泄漏。论文展示了保留历史的好处，但没有把这些治理问题完整解决。
- 结果依赖训练/验证/测试划分、模型版本、工具环境和提示词。不能直接把论文中的绝对准确率迁移到其他 Agent 或生产数据。

因此，WikiSkill 更准确的定位是：**一种用于离线 Skill 演化的知识编译与验证框架**，而不是“Agent 会自动安全学习”的完整方案。

## 9. 与 LMDJ 的关系

### 9.1 适合借鉴的抽象

LMDJ 当前的仓库已经有 `.agents/skills/`、`.agents/pitfalls/`、研究文档和治理规则。WikiSkill 对 LMDJ 最有启发的不是引入一个自动改写器，而是提供了一个可讨论的分层模型：

```text
任务执行证据 / 测试结果 / 失败记录
        ↓
结构化模式与根因记录
        ↓
经过验证、可审查的 Skill / 流程改进
```

对应到 LMDJ，可把以下关系作为研究假设，而不是现行架构决定：

| WikiSkill 概念 | LMDJ 中可能的对应物 | 需要保持的边界 |
| --- | --- | --- |
| Raw Layer | 测试输出、运行日志、失败证据、验收记录 | 原始证据应保留来源和上下文，不被摘要替代 |
| Wiki Layer | `.agents/pitfalls/`、研究文档中的模式与决策记录 | 只能记录可追溯的事实/判断；不能把猜测变成产品契约 |
| Skill Layer | `.agents/skills/` 与仓库治理文档 | Skill 更新仍需人工/自动化验证，不应凭模型自评直接生效 |
| Gating & Rollback | Task-specific tests、Portal 检查、当前头审查、Git 回滚 | 通过测试不等于物理验收、发布或部署批准 |

这与 LMDJ 的现有边界相容：Project Truth 仍是权威作者状态，Runtime Snapshot 仍是不可变派生状态；任何模型或 Skill 产出的建议都不能直接写入 Project Truth，也不能绕过 Application Facade、验证门或人工验收。

### 9.2 适合 LMDJ 的候选用法

如果未来要研究“从 Agent 失败经验改进仓库 Skill”，可以先做受限的离线流程：

1. 收集某一类任务的完整执行证据，包含命令、工具输出、失败点和人工处置。
2. 将重复失败归纳成带证据链接的模式条目，明确影响范围和未知项。
3. 让候选 Skill 只修改一个声明过的文件集合，并由最低层级的 Task-specific tests 验证。
4. 通过失败则丢弃、成功才保留的候选分支或提交来控制更新；保留提案 diff、测试结果和拒绝原因。
5. 由人审查是否把候选模式提升为仓库长期治理规则，尤其是涉及发布、删除、部署、权限和物理验收的内容。

这条路径借鉴的是“证据—知识—可执行规则”的分层，以及“规则可回滚、历史可追踪”的治理方式；它不意味着 LMDJ 应复制论文的多 Agent 编排、全量 Prompt 注入或自动修改现有 Skill。

### 9.3 明确不应直接迁移的部分

- **不能让运行中的 Agent 自行修改 LMDJ 治理规则。** 论文的验证分数不能替代仓库所有权、审查、当前头检查或用户授权。
- **不能把 Wiki 当作 Project Truth。** 经验模式是分析材料，不是项目内容、Provider 选择或运行时快照。
- **不能用平均 benchmark 分数替代物理验收。** 特别是浏览器、音频、人机交互和发布部署，仍需要对应的远端/物理证据。
- **不能默认跨模型或跨版本迁移 Skill。** 迁移必须按模型、工具版本、Host 和任务域分别验证，并保留负迁移证据。
- **不能把持久化等同于正确性。** 一条错误的模式如果没有来源和失效条件，持久化只会放大错误。

## 10. 建议的后续研究问题

如果要在 LMDJ 或其他 Agent 系统中进一步验证 WikiSkill 思路，优先研究以下问题：

| 问题 | 最小验证方式 |
| --- | --- |
| 结构化模式是否比原始日志更有用？ | 对照“只给原始失败日志”“只给模式”“模式+原始证据”三组离线演化 |
| Wiki 是否会累积错误？ | 给模式加入来源、置信度、失效条件和人工否决，比较长期迭代的误导率 |
| Skill 是否跨模型/Host 稳定？ | 固定任务集，按模型、工具版本、Host 分层做迁移矩阵 |
| 验证集门控是否过拟合？ | 轮换验证集，增加冻结的长期回归集和人工抽样审查 |
| 什么时候允许运行时读 Wiki？ | 分开评估“执行辅助知识”和“用于发现 Skill 缺陷的训练知识”，不要混用指标 |
| 成本是否值得？ | 记录 Maintainer、Proposer、验证执行的 token、时间、工具调用和人工审查成本 |

研究停止条件应是：先能证明某类可重复失败在结构化后更容易被稳定修复，并且不会降低既有不变量；在此之前，不应把 WikiSkill 自动化接入正式治理或发布路径。
