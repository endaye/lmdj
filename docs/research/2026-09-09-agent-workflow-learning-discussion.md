# LMDJ 开发 Agent 经验学习流程研讨

> 状态：待研讨；日期：2026-09-09。
> 跟踪 Task：[#1093](https://github.com/endaye/lmdj/issues/1093)。
> 范围：仅改善开发 Agent 的任务执行、经验记录、Skill 改进与验证。
> 本文提供讨论材料；候选方案、记录字段和试验设置均未批准实施。

## 1. 研讨目标

判断 WikiSkill 的经验积累方法能否降低 LMDJ 开发 Agent 的重复错误、人工纠正次数和无效执行成本，并确定是否值得开展一个有边界的离线试验。

本轮产出是决策与后续任务定义。音乐产品功能、编曲 Agent、运行时模型、Core/Provider 接口及音乐产品架构全部不在范围内。也不在本轮修改现有 Skill、pitfall 格式、CI 门槛或自动调度。

开发流程的初步适合度判断为 **8/10**，这是工程判断，不是实测收益：已有证据、pitfalls、Skills 与验证流程，迁移基础较好；可重复评测、成本和实际增量收益仍待验证。

## 2. 现有基础与待补问题

以下现状依据本次查阅的仓库规范，执行时仍以最新治理文件为准。

| 环节 | 已有机制 | 研讨需要回答的问题 |
| --- | --- | --- |
| 执行证据 | PR、提交、CI 运行和任务验证记录 | 如何绑定任务、修订、模型与工具环境？哪些历史记录足够用于复现？ |
| 经验模式 | `.agents/pitfalls/` 的 Why、How to apply、recurrences | 如何区分反复发生的问题与一次性环境故障？如何保留反证？ |
| 规则吸收 | `exit: skill` / `exit: gate`，复发升级流程 | 如何判断规则真正减少错误，而非仅增加阅读负担？ |
| 修改验证 | Task-specific tests、当前提交审查、Git 历史 | 如何保留被拒绝方案，以及验证旧问题之外有没有新退化？ |
| 多 Agent 协作 | 共享仓库文档、隔离 worktree | 如何避免重复提案、跨版本误用和集中日志写冲突？ |

[Pitfall Ledger](../governance/pitfall-ledger.md)已规定目录即索引、近似问题合并复发记录、产品逻辑缺陷优先由回归测试表达。候选设计应复用这些约束，不另建共享手工索引或平行 lessons 库。

## 3. 从 WikiSkill 借鉴的内容

WikiSkill 将原始轨迹、持久知识、当前 Skill 分层；候选 Skill 经验证决定接受或回滚，知识与提案结果继续保留。本文只借鉴这种证据组织方式。[论文 v1，§3](https://arxiv.org/html/2608.27454v1#S3)

对 LMDJ 的候选流程是：

```text
可追溯的任务证据
  → 归纳或补充已有 pitfall
  → 提出一个有依据的 Skill 修改
  → 用保留案例检查收益与退化
  → 经现有交付流程接受或拒绝
  → 保留结果，供后续提案查询
```

最有价值的增量可能是“修改效果记录”：每项提案能回答为什么改、改了什么、如何验证、为何接受或拒绝。是否需要新文件，还是利用现有 PR 记录即可，是研讨问题。

论文完整注入 Skill，并限制训练执行者读取 Wiki；LMDJ 要求任务执行时读取相关 pitfalls。候选试验应保持 LMDJ 当前检索方式，仅比较新增经验整理方式的价值，避免同时改变太多变量。[论文 v1，§3.2](https://arxiv.org/html/2608.27454v1#S3.SS2)

## 4. 候选方案

| 方案 | 内容 | 优势 | 代价 / 待验证点 |
| --- | --- | --- | --- |
| A：维持现状 | 继续现有 pitfall → Skill/gate 流程 | 无新增维护成本，可作为基线 | 是否已经足够解决主要复发问题？ |
| B：补充提案证据 | 利用 PR 和已有条目关联失败证据、候选 diff、验证及拒绝原因 | 增量小，容易审查和撤回 | 查询是否方便？是否减少重复修正？ |
| C：离线辅助提案 | Agent 读取选定证据并生成模式或 Skill 修改建议，进入普通任务审查 | 可测量经验归纳的帮助 | 需要样本、评分标准、运行预算和错误归纳处置 |

建议先讨论 B，再决定是否用一个小试验评估 C；A 是合法结论。自动持续修改 Skill 和生产式多 Agent 演化平台留待试验证据支持后单独讨论。

## 5. 必须作出的研讨决定

1. **问题选择：** 首个试验解决哪一种重复错误？由哪些真实案例支持？排除仅需直接补回归测试的问题。
2. **证据边界：** 可使用哪些 PR、日志和人工纠正记录？保留命令、输出、diff 和判断结果即可，不要求采集模型私有推理；凭据和私有内容需先移除。
3. **记录落点：** 提案记录放在 PR、已有 pitfall，还是分任务证据文件？如何关联拒绝结果并避免多分支共享追加点？
4. **适用与失效：** 哪些规则依赖模型、工具或仓库版本？发现反证后如何修正知识，同时保留原记录？
5. **评测标准：** 怎样判定任务正确完成、重复错误、人工纠正和新退化？哪些需要人工判断？
6. **预算与退出：** 允许多少样本、轮次、token、执行时间和人工审查？出现何种结果继续、修订或停止？
7. **决策责任：** 谁确认首个试验范围与结果？需要后续任务时，明确负责人、文件和验证方式。

## 6. 最小试验草案（待批准）

选择一个可以在隔离环境中重放的开发流程问题，例如 PR 关联表达或新文件所有权检查的遗漏。例子只是选题候选；已有确定性检查可以充分解决的问题，不值得额外建设学习流程。

先冻结案例清单，再按事件族划分归纳案例和保留评估案例。同一次事故的相似日志不得分到两侧，防止答案泄漏。候选修改者只能查看归纳侧证据；保留侧由评估者执行，避免为了提高得分不断改写案例。

对照组使用当前 Skills 和相同的 pitfall 检索；实验组只增加一项声明过的候选 Skill 修改。固定模型版本、提示词入口、工具、仓库修订和任务输入，记录随机性与重复运行设置。涉及 GitHub 写入的案例用沙箱或预录响应重放，真实平台行为未覆盖时明确保留缺口。

建议记录以下指标，不合成一个掩盖错误的总分：

| 指标 | 口径 |
| --- | --- |
| 同类错误率 | 出现目标错误的任务数 / 可评估任务数，同时保留原始计数 |
| 正确完成率 | 满足预先定义验收项的任务数 / 可评估任务数 |
| 人工纠正 | 每任务需要纠正的次数、原因与审查耗时 |
| 新退化 | 因新规则出现的错误、遗漏或不必要操作，逐项记录 |
| 执行成本 | 模型用量、工具调用、耗时及新增 Skill 上下文大小 |

缺失证据记为不可评估，不算通过。小样本只提供方向性证据，不能宣称普遍有效或统计显著。运行前先商定最低有用改善、允许成本与停止条件；本研讨文档不预设评分阈值。

如果规则引入明确新退化，先拒绝候选并保留原因；如果效果无改善或记录维护成本抵消收益，可以结束试验。验证通过仍须按现有 [Git Workflow](../governance/git-workflow.md) 和用户授权交付，不新增 CI 必选门槛。
