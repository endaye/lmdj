# LMDJ Stage 1「我的歌曲」与上传入口设计

- 日期：2026-07-27
- 状态：已实施；Web 自动化验证通过
- 目标落点：`apps/web/`
- 上游边界：[LMDJ 工作版 PRD](../prd/working-prd.md)
- 相关需求：[上传任务可见性与单槽队列需求](2026-07-26-upload-job-visibility-requirement.md)
- 相关 UI：[Stage 1 Creator Workspace UI 设计](2026-07-24-stage1-creator-workspace-ui-design.md)
- 相关首页方向：[Chameleon 展览式工作台设计](2026-07-26-chameleon-exhibition-workbench-design.md)

## 1. 设计结论

Stage 1 增加两个明确、并列的产品入口：

1. **我的歌曲**：用户返回产品后寻找、查看和继续处理已有曲目的稳定入口。
2. **上传新歌**：创建新曲目的动作入口，不再同时承担历史列表首页。

当前 `JobQueuePanel` 同时容纳等待、处理中、完成、失败和中断任务，却以
`Upload Queue` 命名并位于上传表单之后。技术上已经存在的浏览器恢复、重新打开
Patch 和手动删除能力，因此被包装成一个短期队列，而不是用户能识别的歌曲历史。

本设计将现有能力重组为：

```text
我的歌曲
  ├─ 正在处理：preflight / queued / processing
  └─ 最近歌曲：completed / failed / cancelled / interrupted

上传新歌
  ├─ WAV / MP3 上传
  └─ 高级入口：导入本地 Patch 包 / 打开示例
```

“上传”是动作；“我的歌曲”是用户回来寻找内容的地方；“Job”只作为曲目背后的
一次处理记录，不再成为页面的主概念。

## 2. 产品边界

### 2.1 本设计交付的是什么

- 使用当前浏览器 `localStorage` 保存的 submission / Job 关联展示曲目；
- 在页面刷新后恢复本浏览器提交过的未删除曲目；
- 把进行中任务和终态历史分组显示；
- 从任何主状态一键返回“我的歌曲”；
- 保留真实队列容量、队列位置、失败、中断和删除语义；
- 让“上传新歌”保持一键可达。

### 2.2 本设计不是什么

- 不是 Stage 2 的 Asset Library、Project Bin 或 Global Library；
- 不是账号级、跨浏览器或跨设备歌曲历史；
- 不提供服务器上所有 Job 的公共列表；
- 不引入账号、数据库、对象存储、搜索服务或同步；
- 不把重复提交自动合并成同一首歌；
- 不把 Job ID 当作歌曲或 Project 的长期产品身份。

在账号级持久化实现前，页面必须显示：

> 仅显示此浏览器提交的曲目

不得使用“云端全部歌曲”“你的所有作品”或其他超出真实能力的文案。

## 3. 信息架构

### 3.1 全局入口

在 Gallery、Processing、Failed 和 Creator Workbench 中提供稳定的全局动作：

```text
[LMDJ]  [我的歌曲]                           [＋ 上传新歌]
```

- **我的歌曲**始终回到歌曲列表，不清除任务、不删除当前 Patch；
- **上传新歌**打开独立的新建视图、Sheet 或 Drawer；
- Creator Workbench 当前的“上传新歌”返回按钮改为“返回我的歌曲”；
- “上传新歌”保留为旁边的独立主动作，不能让用户为了找历史先进入上传页。

Stage 1 不要求引入 URL Router；可以继续使用 React 状态机，但概念状态必须拆开：

```text
library → new-upload → processing-detail → workbench
   ↑             ↘ failed
   └───────────────────────
```

### 3.2 启动默认状态

| 本浏览器状态 | 默认进入 |
|---|---|
| 没有 submission 记录 | Gallery / Empty，主动作是“上传第一首歌” |
| 存在任意 submission 记录 | 我的歌曲 |
| 正在恢复未完成任务 | 我的歌曲，并在“正在处理”中显示恢复状态 |
| 用户通过明确链接打开某个 Patch | 对应 Creator Workbench |

Chameleon Gallery Stage 继续作为品牌化的新建/空状态入口，不被删除。区别是：

- 第一次使用时，Gallery 是首页；
- 已有曲目后，“我的歌曲”成为返回用户的默认首页；
- 点击“上传新歌”可再次进入 Gallery 的上传状态；
- Chameleon 不能替代歌曲列表、队列位置、错误或删除文字。

- 主操作占完整可点击按钮；

- Job ID 不在卡片首屏展示；
- 状态不能只使用颜色表达。

## 5. 歌曲分组与排序

### 5.1 正在处理

包含：

- 浏览器 preflight / 上传请求中；
- `queued`；
- `generating / separating / extracting / patchifying / rendering`。

排序：

1. 正在占用执行槽的任务；
2. `queued` 按真实 `queue_position`；
3. 还未被 API 接受的本地 preflight 记录。

分组标题右侧显示真实容量：

```text
正在处理 1 · 等待 2 · 最大并发 1
```

未知进度不得显示伪造百分比。

### 5.2 最近歌曲

包含：

- `completed`；
- `failed`；
- `cancelled`；
- `interrupted`。

按最近提交时间倒序。Stage 1 不要求分页；当真实使用量证明列表需要扩展时，再加入
搜索、筛选和分页，而不是预先引入空能力。

### 5.3 空状态

| 状态 | 文案与动作 |
|---|---|
| 完全没有记录 | “还没有歌曲。上传一首 WAV 或 MP3，把它变成可演奏 Patch。” |
| 没有处理中任务 | 不渲染空的“正在处理”大面板 |
| 只有处理中任务 | 显示“正在处理”，隐藏“最近歌曲”空壳 |
| 本地记录已失效 | 说明服务器记录不可恢复，并允许“从此浏览器移除记录” |

“从此浏览器移除记录”与“永久删除服务器曲目”必须保持不同语义。

## 6. 卡片信息与动作

卡片首层只显示用户决策需要的信息：

- 原始文件名；
- 产品化状态；
- 提交日期或相对时间；
- `queued` 时的真实队列位置；
- 一个与状态匹配的主动作；
- 一个低频动作菜单。

Job ID、API Base、Pipeline ID、原始状态字符串和详细错误进入“技术详情”，不与
歌曲名竞争视觉层级。

| 状态 | 主文案 | 主动作 | 次级动作 |
|---|---|---|---|
| preflight / upload | 正在上传 | 查看进度 | 暂无 |
| queued | 等待中 · 第 N 位 | 查看进度 | 取消并删除 |
| processing | 正在分离 / 提取 / 制作 Patch | 查看进度 | 处理完成后可删除 |
| completed | 已完成 | 继续创作 | 永久删除 |
| failed | 处理失败 | 查看原因 | 重新上传、永久删除 |
| interrupted | 服务中断 | 重新上传 | 永久删除 |
| cancelled | 已取消 | 重新上传 | 永久删除 |

英文 `Open Patch` 改为“继续创作”。处理中阶段继续映射真实状态，不用笼统的
“AI 正在思考”覆盖 pipeline 证据。

## 7. 上传新歌

“上传新歌”是独立的新建状态：

```text
上传新歌
  选择 WAV / MP3
  WAV / MP3 · 最大 200 MiB · 最长 600 秒
  [上传并制作 Patch]

  高级
  导入本地 Patch 包 · 打开示例
```

规则：

- 生产 UI 不直接暴露 API Base；
- API Base 仅在开发模式或显式“开发者设置”中出现；
- 文件通过 preflight 并被 API 接受后，立即进入对应处理详情；
- 用户离开处理详情后，完成事件不得强制抢走当前页面；
- 用户一直停留在该曲目的处理详情时，完成后可自动进入 Workbench；
- 后台完成时，在“我的歌曲”中更新状态并给非阻塞通知。

本地 Patch 包和内置示例不是“上传歌曲”，放入高级入口，避免与 Creator 主流程
争夺注意力。

## 8. Creator Workbench 行为

顶部稳定显示：

```text
[← 我的歌曲]  当前曲目名 / BPM / Key               [上传新歌] [Export]
```

- “我的歌曲”停止当前播放后返回列表，但不删除或卸载服务器产物；
- 再次点击“继续创作”恢复同一 Patch；
- “上传新歌”开始新的 submission，不覆盖当前曲目记录；
- 删除当前曲目必须使用已有确认对话框；成功后回到“我的歌曲”；
- 工作台内不嵌入完整历史列表，避免挤压 Pattern、16 Pad 和 Inspector。

## 9. 前端实施边界

### 9.1 第一阶段：只改 Web 信息架构

不改 API 和数据契约：

1. 将 `JobQueuePanel` 拆为歌曲列表容器和状态分组；
2. 使用现有 `trackedJobs` 派生 active / recent 两组；
3. 将 `SourcePanel` 重组为 Empty / New Upload，不再包住历史；
4. 为 `AppFrame` 或等价顶栏增加“我的歌曲 / 上传新歌”稳定入口；
5. 将 loaded 状态的“上传新歌”返回动作改为“我的歌曲”；
6. 保留现有恢复、轮询、重新打开、删除和队列容量实现；
7. 增加桌面与窄屏的可发现性、排序、状态动作和不误导文案测试。

建议的前端概念组件：

```text
MySongsView
  ├─ ActiveSongsSection
  ├─ RecentSongsSection
  └─ SongCard

NewSongView
  ├─ UploadPanel
  └─ AdvancedSourceActions
```

组件命名不构成强制代码结构；验收以行为为准。

### 9.2 后续：真正的跨设备歌曲库

当产品进入账号、Asset Memory 或 Project Bin 阶段时，再引入：

- 账号级 Track / Project ID；
- 服务端可分页列表；
- 一首歌下的多次 Job / Patch 版本；
- 重命名、搜索、筛选、跨设备同步和权限；
- 对象存储与数据库保留策略。

迁移时，当前 browser-owned submission 只能作为待认领或本机记录，不能直接
冒充账号所有权。

## 10. 验收标准

1. 本浏览器已有完成曲目时，启动应用直接进入“我的歌曲”，无需先经过上传表单。
2. 用户从 Gallery、Processing、Failed 和 Workbench 均能一键进入“我的歌曲”。
3. “上传新歌”始终一键可达，但上传表单不再压在歌曲列表上方。
4. 进行中任务与最近歌曲分组明确；完成曲目不再显示在名为 `Upload Queue` 的容器中。
5. 完成曲目的主动作是“继续创作”，点击后加载原有 Patch。
6. `queued` 显示真实队列位置；页面继续显示最大并发、正在处理和等待数量。
7. Job ID、API Base 和 pipeline 原始值不占据卡片主层级，但仍可在技术详情查看。
8. 页面明确说明“仅显示此浏览器提交的曲目”，不暗示账号级或跨设备历史。
9. 用户离开处理详情后，后台完成不会强制切换当前页面。
10. 360px 以上窄屏可完成查看状态、继续创作、上传新歌和删除曲目。
11. 当前刷新恢复、幂等提交、重新打开、手动删除和 Creator Export 回归测试继续通过。

## 11. 与 Stage 1 Release Evidence 的关系

这是首条 Creator Core 的可发现性补强，直接服务于“非开发者无口头指导完成
Upload → Play → Export”的 Release Gate。它不替代实体 MIDI、Ableton Live
导入或真实音频重复性证据。

当前状态必须报告为：

- **已确认**：信息架构方向与本文详细设计；
- **已实现**：browser-owned 恢复、队列、重新打开、手动删除，以及独立
  “我的歌曲”入口、返回用户默认首页、分组列表和独立上传状态；
- **已验证**：Web 单元测试、契约同步检查、生产构建，以及 360px–1440px
  Chromium 响应式回归；
- **非本阶段**：账号级、跨设备的真正歌曲库。
