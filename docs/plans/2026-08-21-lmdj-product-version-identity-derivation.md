# LMDJ Product Version Identity Derivation Implementation Plan

> **For agentic workers:** Follow repository `AGENTS.md` and execute the approved plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the committed Product Build authority drive every current consumer, isolate behavior tests behind stable synthetic identities, and make every unavoidable version mismatch actionable.

**Architecture:** Keep `products/lmdj/version.json` as the only current Product Build source and preserve reviewed exact identities in Assembly, release intents, Portal prose, and immutable snapshots. Add narrow diagnostics at each existing language boundary, add a Creator Host/package consistency checker to the existing module-graph gate, and replace current-looking behavior fixtures with a named synthetic Product Build without introducing a new generated constant.

**Tech Stack:** Python 3 standard library, C++20 test fixtures, Node.js ES modules and `node:test`, TypeScript/React with Vitest, Docusaurus MDX, CMake/Core shell entrypoints.

## Global Constraints

- Work only in the existing linked worktree on `docs/issue-207-version-identity-derivation-design`; never modify `main` directly.
- Treat Issue #207 as the first owner of the shared release-test surfaces. Issue #165 must start from fresh `main` after #207 merges.
- Do not modify `products/lmdj/version.json`, `products/lmdj/assembly.json`, `products/lmdj/assembly.lock.json`, `products/lmdj/src/compiled_assembly.cpp`, generated Runtime identity files, manifests, release intents, immutable Portal snapshots, historical plans, acceptance records, or release evidence.
- Do not allocate a Product Build or change Product, Module, Host, Provider, Contract, Model, Assembly, Channel, or public `HOST_PROTOCOL_MISMATCH` identity/semantics.
- Mismatch diagnostics must name authority, expected value, found value, consumer path, and a stable remedy where generated bytes are stale. Diagnostics must use repo-relative paths and must not expose tokens, environment variables, or absolute user paths.
- Pure behavior fixtures use the named value `TEST_PRODUCT_BUILD = "9.8.7.6"`; a mismatch variant uses `"9.8.7.5"`. Neither value may enter active manifests, generated artifacts, release intents, Portal facts, or snapshots.
- Version impact: none. This Task hardens derivation, fixtures, and build-time diagnostics without changing public product or component identity.
- Documentation impact: required for Portal routes `/operations/version-and-release/` and `/operations/testing-and-proof/`; do not create an immutable Portal snapshot or modify diagrams.
- The Task ends as one reviewable Conventional Commit. Stage only the files declared below and do not push, create a Pull Request, merge, release, deploy, or promote a Channel.

  ```python
  def _product_build_mismatch(
      *, expected: ProductVersion, authority: str | Path,
      found: object, consumer: str | Path, remedy: str | None = None,
  ) -> str:
      found_text = found if isinstance(found, str) else "<missing>"
      message = (
          f"Product Build mismatch: expected {expected} from "
          f"{_repo_relative(authority)}, found {found_text} in "
          f"{_repo_relative(consumer)}"
      )
      return f"{message}; remedy: {remedy}" if remedy else message
  ```

  Validate `assembly.product.version`, `lock.product.version`, and `lock.product_assembly.version` before hash/document equality.
